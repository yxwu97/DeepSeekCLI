# DeepSeek Harness Desktop 新设备 DSH-E203 与首次安装可靠性修复开发计划

## 1. 计划信息

- 关联需求：`prompt/prompt-20260819-07-新设备DSH-E203与首次安装可靠性修复需求.md`
- 编写日期：2026-08-19
- 当前基线：应用版本 `0.10.0`，`.NET Framework 4.8` 轻量 ZIP
- 目标版本：`0.10.1`；若实施时基线已变化，则递增届时 patch 版本
- 计划状态：开发与自动门禁已完成；阶段 7 的 Win10/Win11 干净设备、交互式 WebView2、企业代理/受限 ACL 与 DPI 人工验收待执行
- 计划原则：先复现、再冻结完整依赖图、再改生产代码；每阶段独立验证，禁止用已有缓存冒充全新设备验收

## 2. 实施目标

本计划解决两个相互独立但都会表现为 `DSH-E203` 的风险：

1. 新设备缺少可复用 DSH 时，当前 npx 动态解析完整传递依赖图，可能长期无输出、无监听并最终误报服务超时。
2. 已启动 DSH 的 loopback 健康请求可能继承系统代理，在特定设备上产生错误不可达结论。

最终产品保持轻量发布包，优先复用全局 DSH、Desktop 私有安装和严格 `_npx` 缓存；真正缺失时，经用户确认后用随 Release 发布的小型精确 lockfile 在线安装一次到当前用户私有目录，后续直接复用。同时恢复并保留旧版手动安装/启动区域，用户始终可以选择固定全局安装或固定 npx 手动启动，不被自动路径替代。

## 3. 基线与实施约束

### 3.1 当前基线

- Auto 顺序为全局 `dsh.cmd`、严格 `_npx` 缓存、固定版本 npx 回退。
- 固定顶层 `rc.6` 仍会在空缓存解析出大量 `rc.7` 传递包。
- 已知另一台机器执行 `npm install -g @deepseek-ai/dsh@0.1.0-rc.6` 成功，但尚未取得可比的 Node/npm、registry、cache、耗时和规范化依赖图；该案例是阶段 0 必须补齐的成功对照，不能直接推导为产品应执行全局安装。
- npx 准备和 HTTP 就绪共用最长 300 秒。
- npm 进程不退出时，现有 stderr 分类无法工作，最终成为 `DSH-E203`。
- 默认健康 handler 未显式设置 `UseProxy = false`。
- 当前 Release ZIP 约 1.5 MiB，EXE 约 0.35 MiB；本计划不得通过重新内置 Node/DSH 解决问题。
- 较早版本的安装引导包含固定手动命令复制、打开 PowerShell 和 npm 页面入口；当前实现已删除 ViewModel/XAML 入口但保留 `ITerminalLauncher` 注册。本计划将其视为必须恢复的兼容功能。

### 3.2 不得破坏的边界

1. 生命周期单门、取消令牌、generation 和合法状态迁移。
2. 仅回收 Desktop 创建并跟踪的安装/DSH 进程树。
3. Owned DSH 和安装子进程树使用 Job Object 或等价先约束后执行机制。
4. `RunningExternal` 不安装、不停止、不重启。
5. 工作目录结构化传递，受控 `.cmd` 继续走安全 builder，不接受用户 Shell 文本。
6. loopback 身份、重定向、响应上限和 WebView2 同源限制不放宽。
7. 发布 ZIP 不包含 Node、npm、npx、DSH 依赖目录、缓存或用户数据。
8. 用户真实 npm cache、配置和 API Key 不参与自动测试。

## 4. 冻结技术路线

### 4.1 发现与复用

实现统一的候选发现结果，按以下顺序短路：

```text
已确认外部 DSH
  -> PATH 全局 dsh.cmd
  -> Desktop 私有已激活安装
  -> 严格校验的标准 _npx 缓存
  -> 用户确认后的锁定首次安装
```

发现阶段不访问网络。全局和缓存来源继续使用当前安全规则；私有安装增加完成标记、固定入口、版本、lockfile 摘要和 reparse point 校验。候选不可用只记录有界诊断并继续，不自动删除未知目录。

手动路径与上述自动顺序并存：安装引导固定提供 `npm install -g @deepseek-ai/dsh@0.1.0-rc.6` 的持久安装命令，以及旧版 `npx @deepseek-ai/dsh@0.1.0-rc.6 web` 的临时手动启动命令。Desktop 只复制固定文本并打开可见 PowerShell，不自动执行。全局安装完成后重新检查并优先复用；手动 npx 服务经身份确认后作为 `RunningExternal` 连接。

### 4.2 锁定在线安装

在 `eng/` 维护最小根 `package.json` 和精确 `package-lock.json`，发布时把两者作为小型受信安装资源放入轻量 ZIP。用户确认后，将受信资源复制到唯一 staging，并以固定参数运行经过验证的 npm `ci` 流程。

阶段 0 必须先验证最终 npm 命令、必要 lifecycle scripts、Node/npm 兼容范围、registry 来源和 integrity。验证同时覆盖 npm 官方 registry 与至少一个受控镜像，记录 lockfile `resolved`、npm host 替换策略和实际请求 host，确认镜像不会改变依赖图或绕过 integrity。若 `npm ci --omit=dev` 无法从空缓存稳定构建并运行 DSH，本计划在阶段 0 阻塞，不允许退回无锁 npx 后继续交付。

### 4.3 私有安装事务

建议目录：

```text
%LOCALAPPDATA%\DeepSeekHarnessDesktop\dsh\
  active.json
  versions\<install-id>\
  staging\<transaction-id>\
```

- staging 和 versions 必须同卷，活动指针通过临时文件和 replace 原子更新。
- `install-id` 绑定顶层 DSH 版本和 lockfile SHA-256，不使用用户输入。
- 成功安装后先校验入口并执行真实 smoke，全部通过才提交活动指针。
- 失败、取消或超时只清理本次事务 staging；删除前验证解析后的绝对路径位于固定 staging 根。
- 正被 Owned DSH 使用的活动版本不得清理或覆盖。

### 4.4 两段超时

将当前单一等待拆为：

| 阶段 | 计时开始 | 成功条件 | 超时错误 |
| --- | --- | --- | --- |
| 准备 | 安装进程恢复执行 | npm 成功退出且安装校验通过 | `DSH-E221` |
| 服务 | DSH 进程恢复执行 | HTTP 双特征身份确认 | `DSH-E203` |

准备阶段另有无进展期限。进展信号必须有界、节流且不依赖 npm 必须输出日志；服务阶段保持当前短轮询和候选 URI 更新能力。

准备总期限和无进展期限在阶段 0 根据真实空缓存样本冻结为代码常量，不增加 `AppSettings` 字段，不修改 `SchemaVersion`。未来如确需用户配置，应作为独立需求补充取值验证、旧配置迁移和 UI 测试。

### 4.5 代理旁路

生产默认 `HarnessHealthMonitor` 创建 `HttpClientHandler` 时显式设置 `UseProxy = false`。该 handler 只服务于已验证 loopback DSH 地址。注入 `HttpClient` 的构造器不擅自改写调用方 handler，避免破坏测试与可替换边界。

## 9. 必测竞态

1. npm 退出与准备超时同时完成。
2. 安装成功与用户取消同时完成。
3. active 指针提交前应用退出。
4. 自动启动与用户重复点击同时请求准备。
5. 准备完成后、DSH 进程注册前立即退出。
6. DSH 健康确认与进程立即退出同时完成。
7. Stop/Restart 在安装阶段到达。
8. 新 generation 启动时旧安装结果返回。
9. 两个 Desktop 实例竞争同一私有安装根；单实例正常时次实例不得准备，异常残留需安全恢复。
10. 清理 staging 时存在 junction、文件锁或 ACL 拒绝。

竞态测试使用 `TaskCompletionSource`、受控 fake、有限超时和确定性信号，不使用长时间 `Thread.Sleep`。

## 10. 风险与控制
