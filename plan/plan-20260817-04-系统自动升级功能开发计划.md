## 2. 实施原则与发布阻断条件

系统更新会下载并执行新的 Desktop 二进制，风险高于现有 DSH npm 信息查询。计划采用以下不可降级原则：

1. 生产更新必须有客户端内置公钥验证的签名清单；HTTPS 和 GitHub 账号本身不替代代码签名协议。
2. 运行中的应用不覆盖自身，由受控外部更新器在正常退出后完成替换。
3. 替换是有 journal、有备份、有新版本启动握手的事务；失败必须自动回滚。
4. 用户明确确认退出安装；不静默升级、不强制升级、不静默提权。
5. 更新状态与 Harness 状态分离；Owned DSH 走现有退出清理，External DSH 不被停止。
6. 客户端、发布脚本和发布门禁使用同一清单 schema、资产命名和验证实现。

以下任一条件未满足时不得发布自动安装能力，可以只保留手动打开 Releases：

- 生产签名算法、受信公钥、私钥保管和轮换流程未冻结。
- 更新器的目标路径约束、替换原子性或回滚故障注入未通过。
- GitHub Release 资产和重定向行为没有真实证据。
- 无法证明 Owned/External DSH 在升级退出中的所有权边界。
- 发布门禁可在缺少生产签名或资产不一致时继续成功。

## 3. 当前实现基线与差距

| 范围 | 当前事实 | 计划差距 |
| --- | --- | --- |
| 发布 | single-file `win-x64` ZIP，内容为 EXE + README | 缺少签名清单、签名资产、可升级协议和客户端兼容字段 |
| 门禁 | 校验版本、ZIP 内容并在本地报告 SHA-256 | 哈希未签名、未作为 Release 资产、未按客户端路径反向验证 |
| 版本 | `AppVersion`、manifest、版本历史三处同步 | 缺少 Git tag/manifest/asset/EXE 五方一致性验证 |
| 关于窗口 | npm latest 仅表示 DSH；Desktop 只能打开 GitHub | 缺少 Desktop 独立检查、提示、下载和安装状态 |
| 配置 | schema v2，原子保存和 `.bak` 恢复 | 缺少自动检查开关、检查时间和跳过版本迁移 |
| 网络 | DSH npm、账户 API 等独立客户端 | 缺少固定 GitHub Release 客户端、限制、重定向和响应校验 |
| 生命周期 | 真正退出停止 Owned，External 不受控制 | 缺少“退出并安装”原因、更新器接管握手和操作门协调 |
| 单实例 | 当前用户 Mutex + 固定 `Activate` pipe | 更新器内部模式和新版本启动就绪握手尚未设计 |
| 文件更新 | 没有运行时自替换 | 缺少暂存、归档检查、事务替换、备份、回滚和崩溃恢复 |
| 测试夹具 | TestHarness 覆盖进程、HTTP 和 WebView2 | 缺少可替换版本的测试程序、更新 journal 故障注入和 fake release |

## 4. 总体设计

### 4.1 端到端状态流

```text
Idle
  -> Checking
  -> UpToDate | UpdateAvailable | Failed
  -> Downloading
  -> Verifying
  -> ReadyToInstall
  -> Installing (更新器接管，Desktop 正常退出)
  -> Replacing
  -> AwaitingStartup
  -> Committed
       或
     RollingBack -> RolledBack | RecoveryRequired
```

更新状态由独立 `DesktopUpdateCoordinator` 管理，不增加 `HarnessRuntimeState` 或状态事件。检查/下载失败不影响 DSH，安装只通过应用退出边界与 lifecycle 发生交互。

### 4.2 组件职责

具体名称以实施时现有模式为准，禁止为了照搬表格重复创建同义服务。

| 层 | 计划组件 | 职责 |
| --- | --- | --- |
| Models | `DesktopUpdateState`、`DesktopUpdateSnapshot` | 更新阶段、版本、进度、错误和命令状态 |
| Models | `DesktopReleaseCandidate` | 已校验的稳定候选 Release，不携带任意执行命令 |
| Models | `UpdateManifest` | 受版本化 schema 约束的签名清单字段 |
| Models | `UpdateTransaction`、`UpdateJournalState` | 本地替换/回滚事务与有限状态 |
| Services/Abstractions | `IDesktopReleaseClient` | 固定 GitHub 仓库的候选发现和有限发行说明 |
| Services/Abstractions | `IUpdateManifestVerifier` | 原始清单签名、key id、版本和资产元数据验证 |
| Services/Abstractions | `IUpdatePackageStore` | 流式下载、哈希、暂存、归档验证和清理 |
| Services/Abstractions | `IDesktopUpdateCoordinator` | 自动/手动检查、下载、取消、安装准备和快照事件 |
| Services/Abstractions | `IUpdateInstallerLauncher` | 创建受控事务并启动可信更新器，不承担网络下载 |
| Services/Abstractions | `IApplicationExitCoordinator` 或等价边界 | 统一普通退出与升级退出，不让 ViewModel 调用静态关闭逻辑 |
| Services | `DesktopReleaseClient` | 固定 owner/repo、HTTP 限制、稳定 Release/资产筛选 |
| Services | `UpdateManifestVerifier` | 内置公钥、原始字节签名、SemVer/RID/schema 一致性 |
| Services | `UpdatePackageStore` | `%LOCALAPPDATA%` 事务目录、流式校验、安全解压和过期清理 |
| Services | `DesktopUpdateCoordinator` | 单操作门、generation、timer、退避和状态提交 |
| Services | `UpdateInstallerLauncher` | 安装根预检、helper 复制、接管握手和升级退出请求 |
| Updater 内部模式 | `UpdateWorker` | 等待退出、复验、备份、替换、启动握手、回滚和恢复 |
| Utilities | Release/URI/ZIP/路径策略 | 无状态、确定性、可参数化边界校验 |
| ViewModels | 更新展示/设置编排 | Desktop 独立状态、命令与 Dispatcher 更新 |

### 4.3 DI 与生命周期

- Release client、manifest verifier、package store、coordinator 和 installer launcher 作为明确的 Singleton 注册；持有 timer、CTS、事件或 HTTP 资源的类型实现 `IDisposable`/`IAsyncDisposable`。
- 现有共享 `HttpClient` 不应被赋予互相冲突的重定向/Cookie 策略。Desktop Release client 使用专用 handler/client，关闭自动重定向与 Cookie，逐跳验证。
- `DesktopUpdateCoordinator` 在主窗口和初始生命周期初始化完成后启动 scheduler；应用退出先停止 scheduler，再处理下载或安装事务。
- 更新器内部模式在 `App.OnStartup` 正常日志、Mutex、DI 和 WPF 初始化之前路由，确保不会创建第二个主窗口或 DSH。

### 4.4 升级退出边界

将当前 `App.RequestApplicationExit` 的私有 UI 桥接重构为可测试的退出协调边界，退出原因至少区分 `UserExit`、`SessionEnding`、`InstallUpdate`。升级退出必须：

1. 验证更新器已启动并完成接管握手。
2. 将安装状态冻结为不可重入。
3. 禁止新的 Harness 生命周期命令和重复退出。
4. 复用当前设置保存、DI/WebView2/托盘释放、Owned Job Object 回收和单实例释放顺序。
5. External DSH 只解除 watcher/宿主引用，不向其发送停止或结束请求。

更新器只等待宿主退出，不能复制生命周期协调器或按端口/PID猜测停止 DSH。

## 6. 关键实现顺序与依赖

阶段 0 是硬门禁。阶段 1 的协议与验证完成后，阶段 2 和阶段 3 可在不改 updater 的前提下依次开发；阶段 4 必须在阶段 3 提供“已验证且安全解压”的输入后实施；阶段 5 依赖阶段 4 的接管握手；阶段 6 最后绑定稳定契约；阶段 7 贯穿准备但只能在全部行为冻结后完成正式签名和 Release 演练。

不建议同时修改 `App.xaml.cs`、退出路径、SingleInstance、更新 worker 和 WPF 命令。先用 TestHarness 证明 worker 事务，再接入正式 App 生命周期，可显著降低无法启动和无法回滚的风险。

## 9. 必测竞态与故障注入点

以下测试使用 `TaskCompletionSource`、可控 `TimeProvider`、fake stream、命名同步原语和有限超时，不依赖长时间 `Thread.Sleep`：

1. 自动检查已开始时用户手动检查，只完成一个请求且手动 UI 收到同一结果。
2. 检查返回新版前用户关闭自动检查，过期结果不能重新启动 timer 或弹提示。
3. 下载中用户取消、退出或点击第二次下载，只有一个文件流且临时文件被清理。
4. 下载完成与跳过版本同时发生，已验证包状态和 UI 选择具有确定顺序。
5. 用户确认安装时 Harness 正在 Starting/Restarting，安装等待合法稳定点或明确拒绝，不旁路 lifecycle gate。
6. updater 已接管但 Desktop 清理超时，不替换仍运行的 EXE，不结束 External DSH。
7. 旧 EXE 已备份但新 EXE 尚未提交时 worker 终止，下次恢复旧版本。
8. EXE 替换成功但 README 替换失败，恢复两者旧版本，不保留混合内容。
9. 新 EXE 启动后在发送就绪前退出/挂起/报告错误版本，worker 回滚且只结束自己创建的新进程。
10. 新版就绪与 worker 超时同时发生，只允许一次 `Committed` 或 `RolledBack` 终态。
11. 升级退出、托盘退出、Windows 会话结束和第二实例激活同时发生，清理与替换只启动一次。
12. updater 或 App Dispose 后，HTTP、timer、pipe、进程、文件句柄和事件回调均不再触发。

## 10. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| GitHub 账号或传输被攻破 | 恶意二进制被发现或下载 | 离线/CI 私钥签名清单，客户端内置公钥，签名失败无继续入口 |
| 生产私钥泄露 | 攻击者可签恶意更新 | Secret/离线保管、最小发布权限、key id、轮换和应急吊销流程；私钥不入仓库/日志 |
| GitHub 重定向 host 变化 | 合法下载突然失败 | 阶段 0 记录真实 host；结构化 allowlist；失败转手工，不放宽任意 HTTPS |
| 运行目录无写权限 | 自动替换失败 | 安装前完整预检；保持 asInvoker；提供固定 Releases 手工路径 |
| 路径/reparse/归档攻击 | 覆盖任意文件或提权 | 固定安装根和文件名、拒绝 reparse/UNC、ZIP 严格条目、无任意目标参数 |
| 文件替换中断 | 应用无法启动或版本混合 | journal、逐文件备份、同卷提交、新版握手和每阶段崩溃恢复 |
| 新版本可启动但立即故障 | 用户失去可用旧版 | 就绪握手与超时回滚；Release 演练；保留有限 recovery 信息 |
| 安装触发生命周期竞态 | Owned 残留或 External 被误杀 | 升级退出复用现有 coordinator/Job Object；worker 不管理 DSH |
| 自动检查影响隐私/离线启动 | 不必要联网或启动变慢 | 可关闭、延迟后台执行、24h 间隔、有限超时、失败不弹窗 |
| DSH 与 Desktop 更新文案混淆 | 用户误判升级对象 | 独立模型、按钮、区域、错误码和文档术语 |
| 杀毒软件锁定/隔离新 EXE | 替换或启动失败 | 有限等待、明确分类、回滚；不绕过安全软件 |
| 旧客户端不支持新 schema/key | 无法自动升级 | minimum updater、两阶段 key 轮换、保留手工升级入口 |

## 11. 文档与代码规则同步清单

实施阶段必须一次性同步以下事实，避免系统升级成为发布脚本外的孤立功能：

- `AGENTS.md` / `CLAUDE.md`：固定更新源、签名、无任意路径/命令、无静默提权、Owned/External 和 `UPD-E*`。
- `code_rule.md`：签名原始字节、私钥禁入仓库、安全 ZIP、journal、文件 flush/replace、故障注入和脚本 fail closed。
- 开发文档：自动检查时机、状态边界、LocalAppData 更新目录和网络隐私。
- 详细设计：类职责、manifest schema、状态图、退出/worker/回滚时序、错误表和密钥轮换。
- 安装说明/README：自动检查开关、受保护目录、升级确认、回滚结果和手工恢复。
- 发布脚本：确定资产名、签名输入、production key 注入、负向门禁和禁止输出私钥。
- 验证记录：命令、测试数量、签名 key id、公有资产哈希、Windows 环境、真实 Release 结果和残余风险。

## 13. 完成定义

只有同时满足以下条件，本计划才可标记完成：

1. Prompt 中所有 `AC-UPD-*` 均有自动化或明确人工证据，并能追踪到具体任务。
2. 生产签名协议、私钥保管、公钥轮换和客户端 fail-closed 验证已经进入实际发布流程。
3. 自动/手动检查、下载、验证、暂存、确认、退出、替换、启动和结果展示形成完整闭环。
4. 所有替换失败、新版启动失败和 journal 中断均能恢复完整旧版本，或明确进入经过验证的 `RecoveryRequired` 人工流程。
5. 更新器只处理固定安装根与精确文件，不执行 Shell、不接受任意 URL/目标、不静默提权。
6. 更新状态、Harness 状态和 Code/Chat 页面状态相互隔离；Owned/External 所有权边界保持不变。
7. 配置迁移、网络隐私、日志脱敏、资源释放、WPF/DPI 和真实 GitHub Release 演练全部通过。
8. 发布门禁验证客户端真正消费的签名资产，缺少签名或任一元数据冲突即失败。
9. 开发、详细设计、安装、维护规则、验证记录和版本信息与实现一致。
10. 未提交生成目录、更新缓存、journal、备份、测试 key、生产私钥、日志、配置或用户数据。
