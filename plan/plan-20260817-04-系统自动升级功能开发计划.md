## 2. 实施原则与发布阻断条件

系统更新会下载并运行新的 Desktop 二进制，风险高于现有 DSH npm 信息查询。以下原则不可降级：

1. 生产更新必须由稳定启动器和主应用共同验证内置公钥签名的清单；HTTPS 与 GitHub 账号不能替代签名。
2. net48 主应用是多文件发布，不做运行目录逐文件原地覆盖。新版本完整落入独立目录后，原子切换单一版本指针。
3. 根启动器只依赖 .NET Framework 4.8 BCL，不引用 NuGet 或应用版本 DLL；受控 Windows SDK P/Invoke 允许用于 Job、路径和耐久提交，并以 SafeHandle 和固定常量封装。应用目录损坏时仍能恢复事务。
4. 自动升级不替换根启动器和信任根。协议或公钥升级必须发布手工 Bootstrap。
5. 配置迁移在新版本探测提交前只读，避免回滚旧程序后无法读取更高 schema。
6. 用户明确确认退出安装；不静默升级、不强制升级、不静默提权。
7. 更新状态与 Harness 状态分离；Owned DSH 走现有退出清理，External DSH 不被停止。
8. 客户端、启动器、发布工具和门禁使用同一 schema、路径规范、文件库存和签名测试向量。
9. 发布继续保持 net48 轻量 ZIP，不携带 CoreCLR、Node、npm、npx、`node_modules`、DSH 缓存或用户数据。
10. RSA 清单签名与 Authenticode 代码签名职责分离；阶段 0 冻结 `Required` 或 `Advisory` 策略，不预先指定 EV/OV，也不以证书采购阻塞协议实现。

以下任一条件未满足时不得发布自动安装能力，只能保留手工 Releases 入口：

- 生产更新签名算法、公钥、私钥保管和 Bootstrap 轮换流程未冻结。
- 根启动器仍依赖版本目录中的 DLL，或无法在应用目录损坏时启动。
- 版本目录、指针原子替换、journal 恢复或配置写入屏障的故障注入未通过。
- GitHub Release 资产与重定向行为没有真实证据。
- 无法证明 Owned/External DSH 在升级退出中的所有权边界。
- 发布门禁可在缺少生产更新签名、文件库存冲突或现有轻量/DSH smoke 失败时继续成功。
- 没有完成真实 Bootstrap `N -> N+1` stable Release 自动升级。
- Authenticode 策略、产物状态、Windows 外部验证证据与发布说明不一致。

| 范围 | 当前事实 | 计划差距 |

## 4. 冻结的总体方案

### 4.1 安装布局与进程角色

```text
安装根
├─ DeepSeekHarnessDesktop.exe          稳定 BCL-only net48 launcher/worker
├─ README.md
├─ .desktop-update/
│  ├─ current.json                     当前版本指针
│  ├─ journal.json                     仅事务期间存在
│  └─ manifests/                       已安装版本的验证记录
└─ versions/
   ├─ 0.11.0/                          完整 WPF 主应用及所有依赖
   └─ 0.11.1/                          完整候选版本
```

建议新增 `src/DeepSeekHarnessDesktop.Launcher/`，输出根 `DeepSeekHarnessDesktop.exe`。现有 WPF 项目路径可保持不变，但 AssemblyName 调整为 `DeepSeekHarnessDesktop.App`，发布到 `versions/<AppVersion>/`。命名最终在阶段 0 冻结，不能让 launcher 与 WPF core 共用同一可执行文件。

Launcher 只链接经过审查的共享协议/参数源文件，引用 .NET Framework 4.8 系统程序集，不引用 NuGet 运行时包或版本目录 DLL。Job、reparse/path 和提交所需 Windows SDK P/Invoke 属于允许边界，但必须集中封装并释放原生句柄。它负责：

- 正常启动当前版本目录中的固定主应用。
- 更新 worker 模式下验证事务、签名、库存和目录。
- 等待旧主应用/Mutex 释放、切换指针、启动新版本探测。
- 探测失败或 journal 未完成时切回最后完整版本。

WPF 主应用负责 GitHub 检查、下载、用户交互和 Harness 协调，不直接修改当前版本指针。

### 4.2 事务状态

```text
Idle
  -> Checking -> UpToDate | UpdateAvailable | Failed
  -> Downloading -> Verifying -> ReadyToInstall
  -> PreparingVersion -> Prepared
  -> WaitingForExit
  -> PointerSwitched -> AwaitingStartup
  -> Committed
       或
     RollingBack -> RolledBack | RecoveryRequired
```

更新状态不进入 `HarnessRuntimeState`。网络和下载状态由 `DesktopUpdateCoordinator` 管理；`Prepared` 之后的持久事务由 launcher/worker 管理。

### 4.3 原子性边界

- 新版本目录使用 sibling 临时目录完整写入、`FileStream.Flush(true)`、库存校验后，以阶段 0 验证的同卷 Windows 原语改名为最终版本目录。
- `current.json` 使用 `.tmp`、`FileStream.Flush(true)` 和实测冻结的 `File.Replace`/`ReplaceFile` 或 `MoveFileEx(MOVEFILE_WRITE_THROUGH)` 适用路径更新；父目录句柄 flush 仅在目标系统确认支持时启用。
- 指针切换前旧版本目录不变；提交确认前不删除旧版本。
- 断电时指针只能指向完整旧目录或完整新目录。恢复入口是根 launcher，不依赖任一版本应用 DLL。
- README 更新不属于运行事务，可在提交后尽力执行。
- 自动升级不替换 launcher。单调递增的正整数 `minimumLauncherProtocol` 不满足时返回 `UPD-E711` 并打开手工 Bootstrap 路径；launcher 不实现 SemVer 比较。

### 4.4 配置写入屏障

新主应用由 worker 以升级探测模式启动：

1. 获取单实例 Mutex。
2. 只读加载设置并在内存迁移。
3. 建立最小 DI、日志和关键启动依赖验证。
4. 不启动 Owned DSH、不开放主操作、不保存窗口状态或新 schema。
5. 向 worker 报告事务 ID、Desktop 版本和 readiness。
6. 收到 `Committed` 确认后解除写入屏障并继续正常初始化。

失败时旧设置文件和 `.bak` 保持旧版可读，worker 切回旧指针并启动旧版。

若 worker 已耐久写入 `Committed` 但确认未送达，probe 超时后不得解除屏障或写入持久状态，并退出等待下次 launcher 启动已提交新版本。probe DI 采用显式无副作用集合；测试对安装根、AppData、LocalAppData、WebView2 profile 和私有 DSH 根做快照 diff，提交前仅允许事务 journal/握手标记和专用脱敏 probe 日志变化。

### 4.5 签名与库存

生产协议基线为 RSA-3072 + SHA-256 PKCS#1 v1.5 detached signature；阶段 0 必须在 net48、Windows 10/11 和发布环境实际验证后冻结算法 ID。主应用与 launcher 内置相同公钥。

`update.json` 的 `files[]` 是完整发布库存，包含规范化相对路径、角色、字节和 SHA-256。ZIP 条目必须与库存一一对应。自动事务只安装 `application` 角色；包内 launcher 只用于手工 Bootstrap，自动过程不能覆盖根 launcher。

发布清单使用固定字段顺序、LF、UTF-8 无 BOM。建议新增最小 `eng/ReleaseManifestTool`，由 PowerShell 脚本调用统一生成/验证字节，避免 Windows PowerShell 5.1 与 PowerShell 7 的 BOM、换行和属性顺序差异。

清单由 App、launcher 和门禁共享 `BoundedUpdateManifestReader`：使用 net48 BCL `JsonReaderWriterFactory`/`DataContractJsonSerializer` 与 `XmlDictionaryReaderQuotas`，在严格 UTF-8 解码前后限制原始字节、深度、键/值、数组/文件数和整数范围，并拒绝 BOM、重复/未知必需字段、溢出及非规范路径。不手写通用 JSON parser，也不建设独立长期 fuzz 平台；维护一套可复现的畸形输入和属性测试语料即可。

### 4.6 Authenticode 发布策略

RSA detached signature 继续是自动更新协议信任根。阶段 0 另行冻结 Authenticode 为 `Required` 或 `Advisory`，不预先限定 EV/OV：`Required` 时两个 EXE 的有效签名和可信时间戳进入发布门禁；`Advisory` 时不阻塞协议实现，但发布前必须记录 SmartScreen、Defender 和适用 WDAC/企业策略结果、残余风险与手工降级路径。证书采购、时间戳服务和外部信誉验证作为发布依赖跟踪，不能用 RSA 清单验签结果代替。

### 4.7 单实例与更新事务所有权

- 现有 WPF core 继续持有 `Local\DeepSeekHarnessDesktop-<CurrentUserSid>` 应用 Mutex 和固定 `Activate` pipe；正常 launcher 启动 core 后退出，不持有或继承该 Mutex。
- 第二次启动仍由 secondary core 通过现有 pipe 激活主实例。probe 获取同一应用 Mutex；worker 永不持有应用 Mutex，只等待旧 core 释放。
- worker 持有按当前用户 SID 与规范化安装根派生的独立更新 Mutex。根 launcher 正常启动前检查 journal/update Mutex，事务活跃或待恢复时先等待/恢复，不启动竞争的旧 core。
- Mutex/pipe 名称、ACL、超时、崩溃释放和第二实例语义在阶段 0 冻结；不向 launcher 复制新的激活协议。

## 10. 必测竞态与故障注入点

使用 `TaskCompletionSource`、仓库兼容 `TimeProvider`、fake stream、命名同步原语和有限超时，不依赖长时间 Sleep：

1. 自动检查中用户手动检查，只完成一个请求且两处 UI 收到一致结果。
2. 检查完成前关闭自动检查，过期结果不能重启 timer 或弹提示。
3. 下载中取消、普通退出或重复下载，只有一个流且临时文件清理。
4. 新目录准备完成与用户跳过/退出同时发生，状态提交顺序确定。
5. 用户确认安装时 Harness 正在 Starting/Restarting，等待稳定点或明确拒绝，不旁路 lifecycle gate。
6. worker 已接管但旧 core 清理超时，不切换指针，不结束 External DSH。
7. 新版本目录写到任意库存文件时终止，当前指针仍指旧完整目录。
8. `current.json.tmp` 写入、`Flush(true)`、冻结的 Windows 提交原语前后终止，下次 launcher 选择一个完整目录。
9. pointer 已切换但 probe 未启动/立即退出/挂起/错版本，launcher 回切旧指针。
10. probe 迁移到新 schema 后失败，磁盘上的 settings 与 `.bak` 仍由旧版读取。
11. probe ready 与 worker 超时同时发生，只允许 Committed 或 RolledBack 一个终态。
12. worker 已耐久写入 `Committed` 但确认未送达即退出，probe 超时不越过写入 allowlist；下次 launcher 启动新版。
13. 升级退出、托盘退出、会话结束和第二实例激活同时发生，只启动一个清理与 worker，且不启动竞争旧 core。
14. cleanup 删除旧版本时遇到未知文件、reparse 或 hash 不符，停止清理且当前版本不受影响。
15. launcher/worker/Core Dispose 后，HTTP、timer、pipe、进程、文件和事件不再回调。

| GitHub 账号或传输被攻破 | 恶意包被发现/下载 | launcher 和 App 双重内置公钥验签，签名失败无继续入口 |
| 生产私钥泄露 | 攻击者可签包 | Secret/离线保管；停止自动发布；信任根轮换走手工 Bootstrap |
| Authenticode 缺失、过期或信誉不足 | Windows 安全产品/企业策略拦截新 EXE | 冻结 Required/Advisory；验证签名和时间戳或记录 SmartScreen/Defender/WDAC 证据与手工降级 |
| launcher 自身缺陷 | 所有后续自动升级受限 | BCL-only、小职责、重故障注入；不自动替换；`minimumLauncherProtocol` 不足时手工 Bootstrap |
| 多文件跨版本混装 | 应用无法启动/行为未知 | 完整版本目录 + 单指针原子切换，不逐文件覆盖 |
| parser differential/资源耗尽 | App 接受而 launcher 拒绝或解析恶意清单耗尽资源 | 同一共享受限 BCL reader、固定 quotas 和畸形输入/属性测试语料 |
| rename 已完成但元数据未耐久 | 断电后指针或版本目录状态倒退 | 阶段 0 实测并冻结 Windows 提交原语；不支持目录降级手工安装；提交点故障注入 |
| PowerShell 字节不一致 | 签名在客户端失效 | 统一 ReleaseManifestTool，固定 UTF-8 无 BOM/LF/顺序 |
| 新 schema 破坏旧版 | 回滚后设置不可读 | probe 写入屏障，提交前不持久化，主/备份回滚测试 |
| 安装目录无写权限/reparse | 替换失败或越界写 | 完整预检，asInvoker，固定手工 Releases 降级 |
| GitHub host 变化 | 合法下载失败 | 阶段 0 精确 allowlist；失败转手工，不放宽任意 HTTPS |
| 杀毒软件锁定文件 | 准备/启动失败 | 新目录、有限等待、明确错误、指针不切换或自动回切 |
| 升级触发生命周期竞态 | Owned 残留/External 被杀 | App 统一退出；worker 不管理 DSH；所有权集成测试 |
| 应用 Mutex 与更新 Mutex 所有权漂移 | 双开、并行 worker 或恢复时启动旧 core | core 保持应用 Mutex/pipe；worker 独占按用户+安装根 Mutex；根 launcher 先恢复事务 |
| 新布局增加包大小 | 破坏轻量目标 | launcher BCL-only；保留 30 MB/5 MB 门禁和禁入扫描 |
| DSH lock 更新与私有安装不一致 | 启动下载漂移 | 库存验证 lock；两版本都运行 private install/reuse smoke |
| Desktop/DSH 更新混淆 | 用户误判对象 | 独立模型、按钮、区域、错误码和文档术语 |

## 12. 验证命令与发布门禁

各阶段运行相关测试。Bootstrap 和 N+1 完成后分别在仓库根执行：

```powershell
dotnet restore DeepSeekHarnessDesktop.sln
dotnet build DeepSeekHarnessDesktop.sln -c Debug --no-restore -m:1
dotnet test DeepSeekHarnessDesktop.sln -c Release --no-restore -m:1
.\eng\Verify-Release.ps1
```

扩展后的发布门禁必须确认：

- 0 warning、0 error，UnitTests、Windows IntegrationTests、WebView2 Interactive、private DSH smoke 和 updater 故障注入全部通过。
- launcher 不引用 NuGet/版本目录 DLL，仅使用 net48 BCL 与受控 Windows SDK P/Invoke；core 位于唯一版本目录；根入口能在 core DLL 损坏时运行。
- ZIP/json/sig 精确唯一，签名、ZIP hash、完整 inventory、RID、tag、版本目录、core 元数据一致。
- launcher 与 App 的受限 reader 对相同有效/恶意测试语料结论一致；超过 quota 或修改任一签名字节后门禁失败。
- 正式发布缺少生产更新签名时非零退出；测试 key 不被生产 launcher/App 信任；Authenticode 产物与冻结策略一致。
- ZIP 不含 CoreCLR、Node、npm、npx、`node_modules`、DSH 缓存、日志、配置、journal、备份或 WebView2 数据。
- ZIP ≤ 30 MB；launcher 与 core 分别有明确体积上限，主应用门禁不得因改名失效。
- `dsh-runtime/package.json`、lockfile 与固定 DSH 元数据一致；真实私有安装及二次免下载 smoke 通过。
- Owned DSH 无残留，External DSH 未停止；普通关闭仍隐藏到托盘。
- probe 失败或未收到提交确认时目录快照只命中 allowlist；回滚后旧版读取原 settings，Chat profile/private DSH 未改变。
- 应用 Mutex/Activate pipe 与更新 Mutex 所有权测试通过；`Committed` 后确认丢失能够确定恢复新版本。
- Bootstrap N 和真实 stable N+1 的 GitHub 资产、自动升级及失败回滚有独立记录。
- `AGENTS.md` 与 `CLAUDE.md` 完全一致；AppVersion、manifest 和版本历史一致。

真实 GitHub、生产更新 key、冻结策略要求的 Authenticode/SmartScreen/Defender/企业策略证据、受保护目录或 Windows 外部环境未完成时，必须列为发布阻塞或明确未验证风险，不能用本地单元测试替代并宣称发布完成。

## 13. 完成定义

只有同时满足以下条件，本计划才可标记完成：

1. Prompt 中全部 `AC-UPD-*` 可追踪到自动化或人工验证证据。
2. Bootstrap N 由用户手工安装，真实 stable N+1 从 N 自动升级成功；旧版本不虚假宣称可自动升级。
3. launcher 是独立 BCL-only 恢复入口，应用及依赖按版本目录隔离，提交只通过已验证耐久原语切换指针。
4. 生产更新签名、公钥、受限 reader、完整 inventory、Authenticode 策略和发布工具进入实际 Release 流程，任一协议冲突 fail closed。
5. 每个 journal 故障点都恢复到完整旧版或完整新版；没有跨版本 DLL 混装。
6. probe 收到提交确认前不越过显式写入 allowlist；`Committed` 后确认丢失和失败回滚均可确定恢复，旧版回滚后可读取原设置。
7. launcher 不执行 Shell、不接受任意路径、不管理 DSH、不静默提权、不自动更新自身或信任根。
8. 更新、Harness、Code/Chat 状态隔离；Owned 正常回收，External/private DSH/Chat profile 不受影响。
9. net48 轻量 ZIP、体积、禁入项、DSH lock、WebView2 和 private DSH smoke 门禁全部保留。
10. 文档、维护规则、验证记录和版本一致，仓库及产物不含生产/测试私钥、更新缓存、journal、备份、日志、配置或用户数据。
