## 2. 实施目标

本计划把用户设备上的实时 npx 准备替换为发布阶段冻结、随 Desktop 交付的私有 Node + DSH 运行时，并建立自动检查、原子准备、自修复和上一版本回退闭环。

实施必须遵守 `AGENTS.md`、`CLAUDE.md` 和 `code_rule.md`，尤其保留以下边界：

1. 生命周期操作保持单门串行、取消令牌和 generation 校验。
2. 只停止 Desktop 创建并跟踪的 Owned 进程树，`RunningExternal` 不受影响。
3. 私有 Node/DSH 进程立即加入带 `KILL_ON_JOB_CLOSE` 的 Job Object。
4. 工作目录通过 `ProcessStartInfo.WorkingDirectory` 传递；参数使用 `ArgumentList` 或精确受控 `.cmd` 模板。
5. 运行时准备只写 `%LOCALAPPDATA%\DeepSeekHarnessDesktop` 下固定私有根，不修改用户 npm、PATH、工作区或安装目录。
6. 外部文件名、归档条目、manifest、进程输出和异常都按不可信输入处理，结构化校验、限长和脱敏。
7. 修复缺陷先建立可重复测试，再修改生产实现；生成运行时、缓存、ZIP、日志和验证临时文件只进入 `output/`、`obj/` 或唯一临时目录。

## 3. 当前基线与故障模型

### 3.1 当前实现

- Auto 模式优先寻找 PATH 中的全局 `dsh.cmd`，否则执行 `npx.cmd -y @deepseek-ai/dsh@0.1.0-rc.6 web`。
- `DshPackageMetadata` 只固定顶层 DSH 版本，没有完整 npm lockfile 或运行时清单。
- `HarnessLifecycleCoordinator` 从 npx 进程创建后等待 DSH HTTP 身份确认，准备和健康检查共用最长 300 秒。
- `HarnessProcessManager` 可实时读取 stdout/stderr并管理 Job Object，但 npm 默认输出无法持续提供依赖解析进度。
- `NpmFailureClassifier` 只在进程退出后基于 stderr 分类 DNS、TLS、registry 和权限错误；进程不退出时最终成为 `DSH-E203`。
- 发布 ZIP 当前只包含 single-file EXE 和 README，不包含私有 Node、完整 DSH 运行时、lockfile、manifest 或许可证清单。

### 3.2 已确认根因

真实新设备使用 `Node 24.19.0 + npm 11.17.0`。顶层 `dsh@0.1.0-rc.6` 的范围型传递依赖被 npm 解析为大量 `rc.7` 子包，npm 停在 `idealTree buildDeps/placeDep`，没有错误退出，也没有启动 HTTP 服务。

因此开发目标不是增加超时或更多 stderr 关键字，而是消除客户端实时依赖解析。任何仍在用户机器执行无锁 npx 的方案都不能关闭该缺陷。

### 3.3 现有文档冲突

- 较早安装体验 Prompt/Plan 曾要求使用无版本 npx 跟随 npm 当前解析结果，已被后续实测否定。
- `code_rule.md` 仍写有“DSH 自动 npx 命令使用受控的无版本包名模板”，与当前 `0.6.1` 代码和目标 `0.7.0` 均不一致。
- README、安装、开发和详细设计当前仍把 Node.js/npx 作为 Auto 路径系统要求。

这些内容在功能实施完成时统一修订；本计划文档本身不提前宣称功能已上线。

## 4. 冻结设计决策

### 4.1 运行时交付

- 首期只实现完整离线运行时，不实现 slim/online/npx fallback。
- 发布构建使用固定 Node.js LTS x64、固定 npm 和提交到 `eng/` 下的精确 lockfile，从空缓存创建 DSH 运行时。
- 运行时 manifest 必须声明适用的 Desktop 兼容范围；构建、激活和回退均使用同一严格解析规则校验。
- 用户设备不执行 npm、npx 或 lifecycle script，只校验并展开随包资产。
- 阶段 0 在嵌入 EXE 和固定 sidecar 之间做一次有证据的选择。默认倾向固定 sidecar，避免每次 Debug 编译联网或把大体积二进制提交到源码；正式 ZIP 必须把 sidecar 作为不可缺少的受校验资产。
- 运行时生成物不提交 Git；只提交包描述、lockfile、固定 Node 版本/哈希、manifest schema、构建脚本和测试 fixture。

### 4.2 完整依赖图

- 从已经真实启动成功的 `rc.6` 环境提取依赖图只能作为取证输入，不能在生产代码中扫描或依赖 `_npx` 路径。
- 在 `eng/managed-runtime/` 维护最小根 `package.json` 和精确 `package-lock.json`。lockfile 必须列出所有精确版本、resolved 和 integrity。
- 若 lockfile 中确需出现部分 `rc.7`，必须逐项证明该组合可在固定 Node 上启动并通过身份验证；不能根据包名前缀粗暴强制版本，也不能接受 npm 当天重新解析的结果。
- lockfile 更新必须走真实运行时验证和代码审查，不由 npm `latest`、关于窗口或用户配置自动改写。

### 4.3 私有目录事务

冻结结构：

```text
%LOCALAPPDATA%\DeepSeekHarnessDesktop\runtime\
  active.json
  versions\<runtime-id>\
  staging\<transaction-id>\
```

- 该结构取代早期 Prompt 草案中的平级 `runtime\<runtime-id>` 与 `runtime-staging\<transaction-id>` 表达；实现和文档不得并存两套布局。
- `active.json` 采用原子临时文件 + replace/backup 策略，只保存当前和上一已验证 runtime id、manifest 摘要及提交时间。
- 运行时目录只有全量校验完成后才能进入 `versions` 并成为活动版本。
- 运行中的 runtime id 由生命周期协调器持有租约；清理器不得删除仍有租约或 Owned 进程的目录。
- 所有安全删除由一个窄职责组件完成，删除前解析绝对路径并确认位于 `runtime\staging` 或明确的非活动 `versions` 子目录。

### 4.4 运行时状态与 Harness 状态

不把所有准备细节塞入 `HarnessRuntimeState`。建议新增独立的 `ManagedRuntimeSnapshot`，表达环境预检、检查、解包、校验、提交、就绪、修复和失败；Harness 状态机仍只管理 Stopped/Starting/Running/Stopping 等进程与服务生命周期。

协调器在 `Starting` 内等待运行时 provisioner 完成，再解析启动命令、创建 Owned 进程并进入服务健康等待。所有异步结果在提交前同时验证 operation generation 和 runtime transaction id，避免旧准备任务覆盖新启动。

### 4.5 恢复预算

- 每个启动 operation 最多一次运行时重建。
- 每个启动 operation 最多一次上一版本回退。
- 重建与回退分别记录原因和次数，不能递归调用公开 `StartAsync` 形成新 generation。
- 用户取消、Stop、Restart、退出和新 generation 立即终止后续提交。
- 自动恢复失败后停在明确 Failed 状态，由用户触发新的重试 operation，不设置后台无限 timer。

### 4.6 启动方式

- 发布阶段从真实 DSH `package.json` 的 `bin` 字段解析 CLI 入口，规范化后写入受信 manifest。
- 客户端校验入口位于活动运行时根内且在文件清单中。
- 优先直接执行私有 `node.exe <cli-entry> web [--port n]`，使用 `ArgumentList`。
- 若真实验证证明只能通过生成的 `dsh.cmd` 启动，再增加只接受清单固定私有脚本与精确参数的 `CmdCommandLineBuilder` 模板，并保留所有 Shell 特殊字符测试。

## 10. 必测竞态与故障注入点

以下测试使用 `TaskCompletionSource`、可控 `TimeProvider`、fake stream/file system、命名同步原语和有限超时，不使用长时间 `Thread.Sleep`：

1. 两个 Start 请求同时发现无运行时，只创建一个 staging 事务和一个最终版本目录。
2. 解包最后一个文件时用户取消，完成标记和 active 指针均不能提交。
3. 校验成功与新 generation 同时发生，旧 transaction 只能清理，不能成为活动版本。
4. active.json 替换前/后进程崩溃，下次启动分别恢复旧指针或接受完整新指针，不出现半 JSON。
5. 新运行时进程创建后立即退出，退出事件早于 coordinator 注册时仍能触发一次回退。
6. 新运行时 HealthReady 与超时同时完成，只允许 Running 或回退之一。
7. 回退开始时用户 Stop/退出，上一运行时不能在过期 generation 中启动。
8. 运行租约释放与清理同时发生，仍运行的目录绝不被删除。
9. External DSH 正在运行时 Desktop 启动、修复或升级，External PID 始终不收到结束操作。
10. 第二实例激活、托盘隐藏和运行时进度同时发生，UI Dispatcher 不泄漏回调或重复窗口。
11. 文件锁在自动重建两次之间释放，只允许定义的一次重建，不因偶然成功突破预算。
12. Dispose 后 archive、hash、进度、进程、健康和 timer 回调均不能提交状态或访问已释放对象。
13. 上一运行时文件完整但 manifest 的 Desktop 兼容范围不含当前版本时，禁止创建其进程并直接进入 E219。
14. TestHarness 在入口第一时间派生子进程时，子进程仍受同一 Job 约束；若平台机制无法关闭窗口则阻塞发布。

## 11. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 运行时显著增大发布包 | 下载和磁盘成本增加 | 阶段 0 测量；只含生产依赖；公开大小；不以牺牲确定性换回 npx |
| 第三方许可证不允许再分发 | 无法随包交付 | 阶段 0 硬门禁；NOTICE；阻塞而非绕过 |
| lockfile 已混入不兼容 rc.7 | 打包后仍无法启动 | 从成功图取证、逐包审查、空缓存重建、真实 web/身份 smoke |
| Node/DSH 出现安全漏洞 | 随包运行时长期暴露 | 固定版本清单、CVE 维护、随 Desktop 受控发布更新 |
| sidecar 被删除或篡改 | 首次准备失败 | manifest/hash fail closed、明确 E216/E218；系统升级/完整包恢复 |
| ZIP 路径或解压炸弹 | 覆盖任意文件/磁盘耗尽 | 严格路径、数量/大小、流式校验、私有根和恶意归档测试 |
| 文件锁/杀毒隔离 | 提交或启动失败 | 有限重建、明确错误、上一版本回退；不关闭安全软件 |
| 活动目录被清理 | 运行中 DSH 崩溃 | runtime lease、Owned 退出确认、清理门禁和竞态测试 |
| 上一运行时与新 Desktop 不兼容 | 回退后再次失败或产生未知行为 | manifest 声明兼容范围；回退前严格校验；不兼容直接 E219 |
| 父进程加入 Job 前快速派生子进程 | Desktop 退出后遗留未拥有的 DSH 子进程 | 阶段 4 复现窗口；采用经验证的创建期约束；无法关闭窗口则阻塞发布 |
| 自动恢复无限循环 | 启动长期占用资源 | 每 operation 一次重建/一次回退，失败后等待新用户操作 |
| 状态模型过度耦合 | 生命周期竞态回归 | 独立 runtime snapshot，coordinator 编排，HarnessStateMachine 不承载文件细节 |
| 运行时包含凭据/缓存 | 发布敏感信息 | 空缓存构建、文件 allowlist、token/.npmrc 扫描和包内容门禁 |
| 旧规则继续要求无版本 npx | 维护者重新引入故障 | 阶段 6 同步 AGENTS/CLAUDE/code_rule 和测试断言无 npx |

## 13. 完成定义

只有同时满足以下条件，本计划才可标记完成：

1. Prompt 中所有 `AC-RUNTIME-*` 均映射到具体任务和自动化/人工证据。

9. 正式发布包通过许可、供应链、隐私、干净 Windows、离线和 WPF/DPI 门禁。
10. 规则、开发、详细设计、安装、版本历史和验证记录与实际实现一致；不提交生成运行时、缓存、日志或用户数据。
