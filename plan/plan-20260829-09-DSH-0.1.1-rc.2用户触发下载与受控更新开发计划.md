## 2. 实施策略

本次不实现无条件执行 npm latest 的更新器。实施分为三个结果：

1. 把 Desktop 的 Bootstrap 验证版本和完整生产锁图正式升级到 rc.2。
2. 在现有私有安装事务上增加用户可见的“下载并更新”入口，使已有旧 DSH 候选时也能主动准备 rc.2。
3. 一次性实现固定公钥的签名 DSH 更新目录；后续兼容 DSH 只发布已验证目录和 package/lock 资产，无需修改或重新发布 Desktop。

下载使用内置 Bootstrap lockfile 或签名目录指定且 hash 匹配的精确 lockfile 执行 `npm ci --omit=dev`。npm latest 只负责发现，不决定安装参数。成功条件是“目录验签 + 资产验证 + 下载 + 完整校验 + 真实 smoke + 原子激活”，而不是 npm 进程退出码为 0。

## 3. 关键取舍

| 事项 | 决策 | 原因 |
| --- | --- | --- |
| 更新位置 | Desktop 私有目录 | 不修改用户全局 npm，状态和回退可控 |
| 触发方式 | 用户点击并二次确认 | 满足手动更新，不静默访问 registry |
| 版本来源 | 内置 Bootstrap 描述符或签名更新目录 | 后续升级不改代码，同时防止 latest 和范围依赖漂移 |
| 下载命令 | 仅 `npm ci --omit=dev` | 复用现有受控命令和完整依赖锁定 |
| 激活方式 | staging smoke 后原子 active 指针 | 失败不破坏旧安装 |
| 旧版本 | 保留但不作为 rc.2 候选 | 避免扩大删除风险并支持故障调查 |
| 快速上游发布 | 自动发现、流水线验证、人工签名、用户手动采用 | 每个生产版本仍有锁图和真实验证，但不发布 Desktop |
| 不兼容 DSH | 目录标记最低 Desktop/协议并拒绝 | 无代码适配只覆盖既有 CLI 和身份协议 |

## 6. 测试矩阵

| 层级 | 场景 | 关键断言 |
| --- | --- | --- |
| Unit | 资源版本 | constant/package/lock/manifest 精确一致；错配 fail closed |
| Unit | latest | rc.2、更新版本、旧版本、失败均不改变安装目标 |
| Unit | catalog crypto | 有效签名接受；篡改、未知 key、sequence 回退、future schema、超限输入拒绝 |
| Unit | compatibility | 最低 Desktop、runtime protocol、Node 范围、撤销和 SemVer 判断正确 |
| Unit | trusted state | 只检查不切换；完整提交后原子切换；主/备份恢复确定 |
| Unit | 命令状态 | 用户确认前零网络；重复点击、取消、退出和重试确定 |
| Unit | npm environment | 恶意 user/global/project `.npmrc`、大小写不同 `NPM_CONFIG_*`、offline、registry、cache、script-shell 和 Token 均不能改变受控策略 |
| Unit | install scripts | `--ignore-scripts` 或签名脚本包集合与目录协议一致；增加/删除/换版本/integrity 漂移均拒绝 |

## 7. 必测竞态

1. npm latest 查询完成与用户点击下载同时发生，安装目标始终来自本次不可变的内置/签名描述符，不直接来自 latest。
2. 下载中用户重复点击、取消、退出或会话结束，只存在一个安装事务且子进程树回收。
3. npm 完成与取消同时发生，只允许“未提交”或“完整提交”一个终态。
4. smoke 通过与超时同时发生，active 指针不出现半提交状态。
5. active 提交后重新发现期间 PATH 被修改，最终候选仍需重新做版本验证。
6. Owned rc.7 立即退出与更新完成同时发生，状态迁移合法且只启动一个 rc.2。
7. External DSH 在下载期间占用或释放端口，Desktop 不结束它，也不把私有 rc.2误标为正在运行。
8. 应用退出与 UI 进度回调同时发生，Dispose 后不再访问 Dispatcher 控件。
9. npm latest 已更新但 catalog 尚未发布，检查结果只能提示，不能创建安装事务。
10. 旧 catalog 响应晚于新 sequence，旧结果不能覆盖缓存或当前可更新版本。
11. catalog 验签成功后资产被替换，长度/hash 失败且 npm 不启动。
12. 新版本提交与撤销目录到达同时发生，本次事务使用不可变快照，后续检查阻止再次安装。

## 8. 风险与控制

| 风险 | 控制 |
| --- | --- |
| rc.2 顶层精确但子包漂移 | 阶段 0 完整锁图审计和空 cache smoke；不接受动态 latest |
| `npm pack` 被误认为完整下载 | 文档明确其只含顶层 tarball，生产只用 lockfile `npm ci` |
| 用户已有旧全局版本 | 精确探测后跳过，显式私有准备 rc.2 |
| 更新失败破坏可用 rc.7 | staging + smoke + 原子 active，提交前故障注入 |
| 下载与 Harness 启停竞态 | 单操作门、CTS、generation 和状态机协调 |
| 外部服务被误杀 | 只使用 Owned 句柄/Job Object，端口只做身份和占用判断 |
| npm 输出泄露凭据 | 统一脱敏、限长，不记录 `.npmrc` 或完整环境 |
| 用户/系统 npm 配置改变下载或脚本 | npm 专用净化环境、受控空 config、固定官方 registry/cache/offline/scripts 策略和恶意配置测试 |
| 禁用 scripts 导致假成功，允许 scripts 又扩大执行面 | 阶段 0 A/B 真实 smoke；优先禁用，必须启用时签名固定脚本包集合并做威胁评审 |
| 上游继续快速发布 | latest 只提示；每个新版本重新生成可信锁图和验证记录 |
| UI 看似自动更新 | 明确“用户触发的私有下载”，确认前零网络、零全局修改 |
| 目录服务器或 GitHub 资产被替换 | 固定公钥验签、资产长度/hash、逐跳 URI 验证和回放防护 |
| 签名私钥泄露 | 离线/受控保管；停止目录发布；轮换信任根需 Desktop 更新 |
| DSH 改变 CLI/身份协议 | `runtimeProtocol` 与最低 Desktop 门禁，拒绝无代码适配 |
| 误把“无代码”理解为零审核 | 独立流水线与人工签名仍是发布门禁，只免除 Desktop 重编译 |
