- 适用项目：DeepSeek Harness Desktop
- 编写日期：2026-08-21

- 需求形成时 Desktop 代码版本：`0.10.1`
- 需求形成时锁定 DSH：`@deepseek-ai/dsh@0.1.0-rc.6`
- 目标锁定 DSH：`@deepseek-ai/dsh@0.1.0-rc.7`

## 2. 结论与适用边界

可以先手工安装全局 `@deepseek-ai/dsh@0.1.0-rc.7`，再由当前 Desktop 的 Auto 模式通过 PATH 中的 `dsh.cmd` 启动。当前候选顺序是全局 PATH、Desktop 私有安装、固定版本 `_npx` 缓存，因此重新检查 PATH 后，全局安装通常会优先生效。

但这不等于 Desktop 已把 DSH 固化为 `rc.7`：

- 当前 `DshPackageMetadata.ValidatedVersion` 仍是 `0.1.0-rc.6`。
- 发布包内 `eng/dsh-runtime/package.json` 和精确 `package-lock.json` 仍锁定 `rc.6`。
- 私有安装状态和 `_npx` 缓存发现只接受 `rc.6`。
- 全局 `dsh.cmd` 被发现后会直接成为候选；诊断会读取实际版本，但候选发现和启动前没有要求它必须等于锁定版本。
- 关于窗口的 npm `latest` 只是只读信息，不能直接改变启动版本。

因此需求分为两层：

1. 临时人工验证：用户在可见终端手工安装 `rc.7`，停止旧 DSH 后重新检查并启动，用于验证上游版本可用性。
2. 正式固化：随下一次 Desktop 代码发布，把元数据、完整 lockfile、私有安装、缓存校验、手动命令、全局候选版本门禁和发布验证统一切换到 `rc.7`。

只有第二层完成后，才能宣称 Auto 模式固定启动 `rc.7`。

## 3. 当前事实与风险

实施前必须重新读取当前代码和真实 npm 元数据，不得只因 npm `latest` 显示 `rc.7` 就直接替换字符串。

- Auto 当前按全局 `dsh.cmd`、已激活私有安装、标准 `_npx` 缓存、确认后的私有安装顺序选择 DSH。
- 私有安装使用发布包内精确 lockfile 执行一次 `npm ci --omit=dev`，真实 smoke 通过后原子激活；第二次启动不访问 registry。
- 当前 lockfile 的根依赖、顶层 DSH 和 DSH 系列依赖均固定为经验证的 `rc.6` 图。
- 过去真实故障证明，仅固定顶层包而让范围型传递依赖漂移可能造成 npm 安装长时间停滞，因此不能恢复动态 `latest`、无 lockfile 安装或自动 npx。
- 当前全局 PATH 候选的实际版本不参与候选接受条件。若不补门禁，即使常量改为 `rc.7`，PATH 中的 `rc.6`、未来 `rc.8` 或无法解析版本的 `dsh.cmd` 仍可能被启动。
- 更新全局包属于用户环境变更。Desktop 只能复制固定命令并打开可见 PowerShell，不得静默执行或自动提升权限。

## 4. 目标

1. 将 Auto 模式的唯一受支持版本统一为精确 `@deepseek-ai/dsh@0.1.0-rc.7`。
2. 用户可以通过固定、可见、手动执行的命令更新全局 DSH；Desktop 不自动运行 npm 命令。
3. 全局、私有和 `_npx` 缓存候选都必须在启动前证明版本精确等于 `0.1.0-rc.7`。
4. 全局候选版本不符或探测失败时，不执行它；继续尝试私有 `rc.7` 和缓存 `rc.7`，或进入经用户确认的私有锁定安装。
5. 发布包内 package/lockfile、代码常量、手动命令、私有状态、缓存校验和发布门禁使用同一版本事实来源。
6. npm `latest` 继续只读显示。以后出现 `rc.8` 时不得自动下载、安装、修改 lockfile 或切换启动版本。
7. 保持 Owned/External DSH 所有权、Job Object、loopback 身份检查、命令转义、轻量 ZIP 和隐私边界不变。

## 5. 非目标

- 不实现后台自动升级 DSH、静默下载、自动全局安装或自动执行 `npm install -g`。
- 不允许用户输入任意 npm 包名、版本、registry、Shell 参数或入口文件。
- 不把 npm `latest` 响应持久化为运行配置，不动态生成生产 lockfile。
- 不恢复 `npx -y @deepseek-ai/dsh@latest` 或无 lockfile 的私有安装。
- 不自动删除用户的全局 DSH、npm 缓存或旧私有安装目录。
- 不强制 Custom 模式或已确认 `RunningExternal` 服务使用 `rc.7`；版本固化范围是 Auto 模式创建的 Owned DSH。

## 6. 用户流程

### 6.1 当前版本的临时人工验证

在正式固化代码发布前，可以按以下方式验证 `rc.7`，但 UI 仍可能显示“固定版本 rc.6”：

1. 从托盘真正退出 Desktop，确保当前 Owned DSH 进程树已停止。
2. 在用户可见的 PowerShell 中手工执行：

   ```powershell
   npm install -g @deepseek-ai/dsh@0.1.0-rc.7
   dsh --version
   ```

3. 确认输出为 `0.1.0-rc.7`，重新打开 Desktop 并执行“重新检查”。
4. 确认实际来源为全局 PATH、实际版本为 `0.1.0-rc.7`，再启动并验证 DSH 身份和页面。

该路径不改变 Desktop 内置 lockfile；如果全局 `dsh.cmd` 不再可见，当前版本仍会回到私有/缓存 `rc.6`。

### 6.2 正式固化后的手动更新

1. 关于窗口手动查询 npm `latest`，分别显示“实际使用版本”“Desktop 验证版本”和“npm 当前发布版本”。
2. 当验证版本为 `rc.7` 且实际全局版本不是 `rc.7` 时，安装引导提供固定命令：

   ```text
   npm install -g @deepseek-ai/dsh@0.1.0-rc.7
   ```

3. Desktop 只允许复制命令和打开当前工作目录的可见 PowerShell，并提示先停止 Owned DSH；不代替用户执行。
4. 用户安装完成后点击“重新检查”。只有版本探测精确为 `rc.7` 的全局候选才显示可用并进入 Auto 启动。
5. 如果用户不更新全局版本，只要 Node/npm 可用，仍可经现有确认流程安装和激活 Desktop 私有 `rc.7`。

## 7. 版本固化设计

### 7.1 单一版本事实来源

`DshPackageMetadata.ValidatedVersion` 更新为 `0.1.0-rc.7`，其他代码引用 `ValidatedVersion`/`ValidatedPackageSpec`，不再散落新的版本字符串。以下资源必须一致：

- `eng/dsh-runtime/package.json` 根依赖。
- 重新生成并审查的 `eng/dsh-runtime/package-lock.json`。
- 私有安装 `install.json`、`active.json` 和 install id。
- `_npx` 顶层 manifest 的包名、版本和 bin/入口校验。
- 全局/手动安装与临时 npx 命令。
- 关于窗口、安装引导、确认提示、测试和发布门禁。

发布脚本必须继续从代码常量、package.json 和 lockfile 三方核对，不允许仅替换其中一处。

### 7.2 rc.7 依赖图验证

阶段 0 在一次性临时目录生成候选 lockfile，不直接覆盖仓库文件。至少验证：

- npm 官方 registry 返回的顶层版本、dist、integrity、bin 映射和 Node engine 要求。
- lockfile 根依赖与顶层 DSH 精确为 `0.1.0-rc.7`，全部条目包含确定的 version/resolved/integrity；不得保留范围型顶层输入。
- 在空 npm cache 下执行 `npm ci --omit=dev` 能在有限总时限和无进展时限内完成。
- 通过 PATH 中 Node.js 直接执行固定 `lib/bin.js web --port <数字>`，HTTP/HTML DSH 身份检查成功。
- 停止后 Owned 进程树无残留；第二次复用不运行 npm、不访问 registry。
- `dsh --version` 的真实输出格式已记录，能够被严格、有限时间的版本探测解析。

任一项失败时继续保留 `rc.6`，不得以 npm `latest` 代替验证证据。

### 7.3 全局候选版本门禁

- 把 `DependencyDiagnosticsService` 已有的有限时 `--version` 探测提取为可复用能力，供候选发现和诊断共同使用，避免一处接受、一处只显示警告。
- 找到 PATH `dsh.cmd` 后，在把它作为候选前执行固定 `--version`，保持 3 秒级有限超时、stdout/stderr 限长、取消和进程清理。
- 只接受可规范化为 `0.1.0-rc.7` 的输出。版本较低、较高、空输出、不可解析、超时或非零退出均拒绝该全局候选。
- 拒绝全局候选不意味着立即失败：继续按私有 `rc.7`、缓存 `rc.7` 顺序发现。只有全部候选不可用且不能私有安装时，才向用户报告版本不兼容。
- 不执行远程 manifest 提供的命令，不因版本探测放宽 `.cmd` 受控执行模板。

### 7.4 私有安装与旧版本

- 新 Desktop 只接受版本、lock hash、manifest、入口和状态均匹配新 `rc.7` lockfile 的活动私有安装。
- 旧 `rc.6` active/backup 状态不会被当作 `rc.7` 复用；若无有效全局/缓存 `rc.7`，走现有用户确认后的私有安装。
- `rc.7` 在 staging 完整安装并通过真实 smoke 后才原子激活，失败时旧 active 状态不得被覆盖。
- 不在本需求中自动删除旧 `rc.6` 私有目录；清理策略保持现状，避免扩大删除范围。

## 8. 状态、并发与所有权

- 手动更新命令只在 DSH 未处于 Starting/Stopping/Restarting 时提供；界面提示先停止 Owned DSH 或完全退出 Desktop。
- “重新检查”和 Auto 启动之间复用同一候选发现规则，避免检查接受 `rc.7`、启动却选择另一版本。
- 版本探测传递 `CancellationToken`，不在 UI 线程同步等待；重复检查由现有命令门抑制。
- Desktop 只停止自身创建并跟踪的 Owned DSH；手动 PowerShell 或已有外部 DSH 仍按 `RunningExternal` 处理，不因版本不符被结束。
- 版本不符只记录路径、规范化版本和错误分类，不记录完整 PATH、环境变量或 npm 输出正文。

## 9. UI 与错误语义

- 关于窗口区分：实际选用 DSH、Desktop 验证版本 `0.1.0-rc.7`、npm `latest`。不得用“latest”表示当前会启动的版本。
- 安装引导继续使用固定命令、复制按钮和可见 PowerShell，不新增任意版本输入框。
- 当 npm `latest` 高于验证版本时显示“上游有新版本，当前仍使用已验证版本”；不显示自动升级按钮。
- 全局 DSH 版本不符但已有私有/缓存 `rc.7` 时，显示实际选用来源，不把被跳过的全局版本报告为正在使用。
- 建议新增 `DSH-E222` 表示“已发现 DSH，但版本不符合 Desktop 验证版本且没有其他可用候选”；用户提示给出固定 `rc.7` 手动命令或私有安装路径。不得改变已有 `DSH-E203` 等错误语义。

## 10. 验收标准

- `AC-DSH-PIN-001`：代码常量、package.json、lockfile 根依赖/顶层包、手动命令和发布门禁精确一致为 `0.1.0-rc.7`。
- `AC-DSH-PIN-002`：空 cache 的 `npm ci --omit=dev`、真实 DSH smoke 和第二次免下载复用均通过后，才允许提交 rc.7 lockfile。
- `AC-DSH-PIN-003`：Auto 只接受实际版本为 `rc.7` 的全局、私有或 `_npx` 候选；`rc.6`、`rc.8`、未知和探测失败候选均不启动。
- `AC-DSH-PIN-004`：全局版本不符时继续选择有效私有/缓存 `rc.7`，来源和实际版本显示正确。
- `AC-DSH-PIN-005`：用户可以复制固定 rc.7 全局安装命令并打开可见 PowerShell；Desktop 不自动执行、不静默提权。
- `AC-DSH-PIN-006`：用户完成全局更新并重新检查后，诊断和启动使用同一 rc.7 候选。
- `AC-DSH-PIN-007`：旧私有 rc.6 不冒充 rc.7；新私有 rc.7 失败时不覆盖旧 active 状态。
- `AC-DSH-PIN-008`：npm `latest` 变化不修改验证版本、lockfile、活动安装或启动参数。
- `AC-DSH-PIN-009`：Owned/External 所有权、Job Object、loopback 身份、命令转义、日志脱敏和轻量发布门禁无回归。

## 11. 测试要求

### 11.1 单元测试

- 全局版本探测接受精确 rc.7，拒绝 rc.6、rc.8、稳定版、空/多行/超长/非法输出、非零退出和超时。
- 全局不匹配后按私有、缓存 rc.7 顺序回退；全局匹配时仍保持现有最高优先级。
- 私有 active/backup 的版本和 lock hash 匹配；旧 rc.6、错误 hash、错误 bin/入口和 reparse 候选拒绝。
- `_npx` 只接受精确 rc.7 包名、版本、bin 和固定入口，不硬编码 cache id。
- About/安装引导的实际版本、验证版本、latest、固定命令和 `CanExecute` 文案测试。
- npm latest 为 rc.7、rc.8、较旧版本或失败时不产生安装、状态或配置副作用。

### 11.2 集成与发布验证

- 在临时 PATH 放置可控 `dsh.cmd`，覆盖 rc.7 接受、版本不符回退、超时进程回收和特殊路径转义。
- 在唯一临时私有根验证 rc.6 状态不复用，rc.7 staging/smoke/activate 成功，失败不覆盖 active。
- 使用空 npm cache 完成一次 rc.7 私有安装，再证明第二次启动不执行 npm、不访问 registry。
- 完整运行 UnitTests、IntegrationTests 和 `eng/Verify-Release.ps1`，继续验证 DSH lock、30 MB ZIP、5 MB EXE、CoreCLR/Node/npm/npx/node_modules 禁入项。
- Windows 10/11 x64 手工执行固定全局更新命令，重新检查后验证实际来源、版本、启动、停止和重启。

## 12. 文档与版本要求

实现时同步 `README.md`、`docs/installation.md`、开发/详细设计、`AGENTS.md`、`CLAUDE.md`、`code_rule.md` 和新验证记录，说明：

- Auto 固定 `rc.7`，npm latest 仍只读。

- 手动更新由用户在可见 PowerShell 执行，Desktop 不自动全局安装。

本文和开发计划属于方案文档，不递增应用版本。实际修改代码、测试、lockfile、发布脚本或用户交付文档并重新生成发布物时，统一递增一次 Desktop patch 版本，同步 manifest 和版本历史。

## 13. 完成定义

只有同时满足以下条件，才可宣称 DSH 已固化到 `0.1.0-rc.7`：

1. rc.7 完整依赖图通过空 cache 安装、真实身份 smoke、进程树回收和第二次免下载验证。
2. 全局、私有和缓存候选都在启动前验证为精确 rc.7；不匹配候选不会执行。
3. 用户能通过固定命令手动更新全局 DSH，Desktop 不自动执行 npm 或提升权限。
4. npm latest 仍为只读信息，不能改变生产 lockfile或启动版本。
5. 旧 rc.6 私有状态不冒充 rc.7，rc.7 失败不会破坏旧状态或用户数据。
6. 所有验收项有自动化或人工证据，现有 DSH 所有权、安全、轻量发布和隐私门禁全部通过。
