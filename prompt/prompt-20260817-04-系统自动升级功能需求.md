## 2. 使用方式与术语

将本文作为系统自动升级功能后续设计、实现和验收的完整输入。执行者必须先读取届时的当前实现、项目文件、发布脚本、相关测试、`AGENTS.md`、`CLAUDE.md`、`code_rule.md`、开发文档、详细设计、安装说明和最新验证记录，再依据真实类型与接口实施，不得仅根据本文猜测代码结构。

本文中的“系统”或“Desktop”特指 `DeepSeek Harness Desktop` 桌面宿主，不是 DSH/npm 包。现有关于窗口中的 npm `latest` 查询仍是 DSH 信息查询，不能复用其文案、结果模型或安装行为冒充 Desktop 升级。

本需求所称“自动升级”采用以下安全语义：

1. 应用按固定周期自动检查本项目的稳定发行版，不阻塞启动。
2. 发现新版后在应用内提示，由用户明确选择是否下载。
3. 下载、签名验证和暂存可以在应用内自动完成，但退出并替换程序前必须再次明确确认。
4. 安装通过受控的外部更新进程完成，成功后自动重启新版本；启动失败时自动回滚旧版本。
5. 不静默终止 DSH、不在用户不知情时重启 Desktop、不强制升级，也不自动提升权限。

## 3. 当前基线与主要缺口

本文编写时的仓库事实如下，实施前必须重新核对：

- Desktop 以 `win-x64`、self-contained、single-file ZIP 发布，ZIP 仅包含 `DeepSeekHarnessDesktop.exe` 和 `README.md`。
- `eng/Publish-Release.ps1` 从 `AppVersion` 生成 `DeepSeekHarnessDesktop-<version>-win-x64.zip`。
- `eng/Verify-Release.ps1` 已计算 ZIP SHA-256，但哈希只写入本地验证报告，没有可供客户端验证的签名更新清单。
- 项目 GitHub 地址为 `https://github.com/yxwu97/DeepSeekCLI`，关于窗口只能打开项目页面或 Releases，由用户手工下载。
- `AboutViewModel` 的“检查更新”当前只查询 `@deepseek-ai/dsh` 的 npm `latest`，不检查 Desktop。
- 应用是当前用户单实例；真正退出会保存设置、释放 WebView2/DI、停止 Owned DSH，并通过 Job Object 回收子进程树。
- 主 EXE 运行期间不能可靠地原地覆盖自身，当前也没有独立更新器、升级事务、启动确认或回滚协议。
- 应用清单为 `asInvoker`，现有发布方式不保证用户把 ZIP 解压到可写目录。

主要缺口是：缺少可信发行元数据、自动检查调度、下载与暂存、运行中退出协调、原子替换、失败回滚、升级进度 UI、配置兼容和端到端发布验证。

## 4. 目标与非目标

### 4.1 目标

1. 自动发现本项目 GitHub Releases 中高于当前版本的最新稳定 `win-x64` 发行版。
2. 让用户在 Desktop 内完成检查、下载、验证、确认安装、正常退出、替换、重启和结果反馈。
3. 对发布元数据和 ZIP 建立独立于 HTTPS 的密码学真实性与完整性验证，校验失败时 fail closed。
4. 保留现有设置、日志、WebView2 profile、Chat 登录态、工作目录和外部 DSH；升级安装不得把用户数据打入或移出发布目录。
5. 安装前通过现有退出路径停止 Owned DSH；`RunningExternal` 永远不因升级被停止或接管。
6. 新版本无法启动或未按期报告就绪时，自动恢复旧版本并给出稳定、可诊断、已脱敏的结果。
7. 自动检查、手动检查、下载、取消、退出、安装和应用关闭之间有确定的并发与资源释放行为。
8. 发布门禁能生成并验证客户端实际消费的更新资产，而不只验证本地 ZIP。

### 4.2 非目标

- 不自动升级 Node.js、WebView2 Runtime、DSH/npm 包或其他第三方依赖。
- 不实现后台 Windows Service、计划任务、常驻系统级更新代理或无人值守强制升级。
- 不支持用户配置任意更新源、仓库、镜像、代理凭据、资产 URL 或公钥。
- 不接受网页、命令行或更新清单提供的任意 Shell 命令、脚本、目标目录或可执行文件名。
- 首期不实现差分补丁、P2P、断点续传、多发布通道、降级安装或跨 RID 更新。
- 不绕过 Windows ACL、企业策略、杀毒软件、SmartScreen 或 UAC；受保护目录不能安全写入时提供手动升级入口。
- 不因“自动升级”放宽 GitHub 之外的 WebView2 导航、远程内容或宿主对象能力。

## 5. 产品行为

### 5.1 自动检查与手动检查

- 新增“自动检查 Desktop 更新”设置，默认开启；关闭后不发起周期网络请求，但关于窗口中的手动检查仍可用。
- 主窗口可交互且启动初始化完成后延迟约 30 秒执行首次自动检查。检查不得阻塞主窗口、DSH 启动或 Chat 初始化。
- 同一进程内每 24 小时最多自动检查一次；持久化最近一次成功检查时间，应用重启后仍遵守间隔。失败检查不进入紧密重试，至少采用有限退避。
- 手动检查忽略 24 小时间隔，但与自动检查复用同一个操作门、请求和结果模型；并发触发只产生一个网络请求。
- 自动检查失败只记录脱敏摘要，不弹阻塞窗口、不改变 Harness 状态。用户主动检查失败时显示可操作的中文提示。
- 自动检查只查询稳定发行版；GitHub draft 和 prerelease 必须忽略。当前版本大于或等于候选版本时显示已是最新版本，不允许降级。

### 5.2 新版提示与用户选择

发现新版后使用非模态提示和关于窗口的“Desktop 更新”区域显示：当前版本、新版本、发布时间、已清理的简短发行说明以及固定 GitHub Release 页面入口。

用户至少可以选择：

- “下载更新”：开始下载并显示字节进度，下载期间可取消。
- “稍后提醒”：当前进程不重复打扰；下一个自动检查周期仍可提示。
- “跳过此版本”：持久化精确版本，只跳过该版本；更高版本仍提示。手动检查仍显示被跳过版本并允许恢复下载。
- “查看发行说明”：交给受控系统浏览器打开固定仓库对应的 Release HTTPS 页面。

不得把 DSH 的 npm `latest`、Desktop 更新、版本历史三个概念混在同一字段或模糊文案中。

### 5.3 下载、确认与安装

- 只有用户点击“下载更新”后才下载 ZIP；首期不在后台静默预下载。
- 下载成功并完成全部验证后，显示“退出并安装”和“稍后安装”。“稍后安装”只保留已验证暂存包，不自动退出应用。
- 用户点击“退出并安装”时必须再次说明：Desktop 将退出；Owned DSH 会按正常退出流程停止；外部 DSH 不受影响；成功后 Desktop 会自动重启。
- 生命周期正在 Starting/Stopping/Restarting、应用正在退出或升级操作未达到可安装状态时，安装命令不可用。下载可以与正常 DSH 运行并存，但不能改变 lifecycle generation 或 operation token。
- 用户确认安装后进入不可重入的 `Installing` 展示状态，禁止新的生命周期命令、重复退出和第二个更新事务；随后通过统一退出协调路径关闭应用。
- 普通窗口关闭仍只隐藏到托盘。只有明确“退出并安装”才触发升级退出，不能因准备好更新而改变托盘语义。

### 5.4 安装目录不满足条件时

首期自动替换只支持本地、非 reparse point、当前用户可写且包含当前运行 EXE 的安装目录。以下情况拒绝自动安装并提供固定 Release 页面与手工说明：

- EXE 位于只读或受保护目录，当前 `asInvoker` 权限无法创建、替换和恢复文件。
- 安装目录位于 UNC、断开的可移动介质、符号链接、junction 或无法稳定解析的路径。
- 当前文件名不是受控的 `DeepSeekHarnessDesktop.exe`，或目录中现有文件身份与产品元数据不匹配。
- 安全软件占用导致预检无法证明替换和回滚均可完成。

不得为提升成功率静默请求管理员权限，也不得把任意下载内容写入其他受保护应用目录。

## 6. 更新源、版本和签名协议

### 6.1 固定发行源

- 唯一生产源是 `yxwu97/DeepSeekCLI` 的 GitHub Releases。
- Release 列表请求、资产选择和发行说明页均使用代码中的固定 owner/repository，不进入 `AppSettings`。
- GitHub API 响应只能用于发现候选 tag 和精确命名资产，不能直接授权执行内容。
- 网络请求不携带 Cookie、API Key、GitHub Token、DSH 凭据或用户环境信息。设置明确的产品 `User-Agent`、15 秒元数据超时、有限重定向和响应体上限。
- 每一次 HTTP 重定向都重新验证 HTTPS、无 UserInfo、目标 host 属于经审计的 GitHub 资产 host 集合，并限制跳转次数。不得接受 HTTP 降级或把响应最终地址持久化成新源。

### 6.2 版本规则

- Git tag、更新清单版本、ZIP 文件名、ZIP 内 EXE `ProductVersion`/`FileVersion` 和 `Directory.Build.props` 必须相互一致。
- 使用 `NuGet.Versioning` 解析和比较 SemVer，不使用字符串比较。
- 候选必须严格高于当前版本、RID 精确为 `win-x64`、清单 schema 受当前客户端支持。
- draft、prerelease、版本缺失、资产重复、名称大小写不精确或元数据冲突均视为不可安装。
- 更新清单可以声明 `minimumUpdaterVersion`。当前客户端低于该版本时只引导手工升级，不尝试解释未知协议。

### 6.3 发布资产

每个可自动升级的稳定 Release 必须包含精确且唯一的三项资产：

```text
DeepSeekHarnessDesktop-<version>-win-x64.zip
DeepSeekHarnessDesktop-<version>-win-x64.update.json
DeepSeekHarnessDesktop-<version>-win-x64.update.sig
```

`update.json` 至少包含：

- `schemaVersion`
- `version`
- `runtime`
- `assetName`
- `assetBytes`
- `assetSha256`
- `publishedAt`
- `minimumUpdaterVersion`
- `signingKeyId`

清单使用确定的 UTF-8 无 BOM 字节作为签名输入。字段顺序、换行和序列化方式由发布脚本唯一生成，客户端验证原始字节后再解析，不能重新序列化后验证。

### 6.4 密码学验证

- 生产更新清单必须使用离线或 CI Secret 中的私钥生成 detached signature，建议采用 RSA-3072 + SHA-256/PSS 或经安全评审后冻结的等强标准算法。
- 客户端只内置公钥和稳定 `signingKeyId`，绝不包含私钥。生产私钥、明文导出和签名口令不得进入仓库、日志、ZIP、测试快照或验证报告。
- 客户端先验证清单签名，再信任其中的版本、长度和 SHA-256；随后流式下载 ZIP 并同时验证长度和 SHA-256。
- 签名无效、未知 key id、哈希不符、长度不符、资产重复或清单冲突时必须删除临时文件并拒绝安装，不能提供“仍然继续”。
- 公钥轮换采用先在旧版本加入新公钥、后切换发布签名的两阶段流程。移除旧公钥前必须评估仍在使用的旧客户端；不能用远程清单无条件替换信任根。
- 测试私钥只能位于测试临时目录或测试夹具，不得作为生产受信公钥使用。发布门禁缺少生产签名材料时必须明确失败，不能生成看似可自动升级但无法验证的 Release。

## 7. 下载、暂存与归档安全

- 更新工作目录固定在 `%LOCALAPPDATA%\DeepSeekHarnessDesktop\updates`，按事务 ID 和目标版本隔离；不得写入仓库、当前工作目录或 WebView2 数据目录。
- 下载先写唯一 `.tmp` 文件，设置总大小上限并流式计算 SHA-256；验证通过后原子重命名为暂存 ZIP。
- 响应长度未知或超过清单/客户端上限时拒绝。网络失败、取消和哈希失败后清理未验证临时文件。
- 同一版本已存在暂存包时必须重新验证签名、长度和哈希，不能只因文件名相同而复用。
- ZIP 仅允许发布门禁冻结的精确根级文件集合；首期为 `DeepSeekHarnessDesktop.exe` 与 `README.md`。拒绝绝对路径、`..`、目录、重复项、大小写冲突、alternate data stream、reparse/symlink 属性、加密项和超出解压上限的内容。
- 解压到新的事务暂存目录，不直接覆盖安装目录。解压后验证 EXE 文件名、PE 产品名、`ProductVersion`、`FileVersion`、架构和清单版本一致。
- 发行说明和 README 属于不可信文本：限制长度，UI 仅按纯文本展示，不解析 HTML、图片、脚本或 Markdown 外链。
- 成功、失败和取消后清理过期事务；最多保留当前待安装版本和有限诊断元数据，不无限累积 ZIP、备份或日志。

## 8. 外部更新器与回滚事务

### 8.1 更新器入口

运行中的 EXE 不原地覆盖自身。实现时从当前可信 Desktop EXE 复制出临时更新器，使用同一程序集的严格内部模式或独立最小 helper 执行替换。无论采用哪种形式，都必须满足：

- 更新器在 WPF/DI/单实例正常启动之前识别内部模式，不启动主窗口、WebView2 或 DSH。
- 只通过 `ProcessStartInfo.ArgumentList` 传递固定参数；`UseShellExecute=false`，不经 `cmd.exe`、PowerShell 或 Shell 字符串。
- 更新器只读取由当前应用创建、位于固定更新根目录、schema 受支持的本地事务描述；网络清单不能提供安装目标。
- 目标始终绑定发起升级的当前 EXE 和相邻 `README.md`，不能用参数指定任意目录、文件名或第三方进程。
- 更新器不获取管理员权限，不继承网页或更新包提供的环境变量和命令。

### 8.2 正常退出与替换

1. Desktop 创建持久事务记录和回滚所需信息，启动更新器并取得明确的“已接管”握手。
2. Desktop 通过统一升级退出原因进入现有清理路径：取消后台检查/下载，保存设置，停止 Owned DSH，释放 WebView2、托盘、DI、单实例管道和 Job Object。
3. 更新器等待父进程退出和当前用户单实例 Mutex 释放，使用有限超时；超时则不替换并报告失败。
4. 更新器再次验证签名、ZIP/已解压文件哈希、安装根、目标文件和可写性，然后备份旧 EXE/README。
5. 新文件先复制到安装目录内的临时文件并 flush，再使用同卷重命名/替换提交；任何一步失败立即恢复全部旧文件，不能留下新旧混合版本。
6. 更新器启动新 EXE，并传入受控事务 ID。新应用在单实例、设置、DI、主窗口和关键服务初始化成功后，通过当前用户可访问的固定握手通道报告就绪。
7. 新版本在有限时间内未就绪、提前退出或报告版本不符时，更新器终止仅由它创建的新进程，恢复旧文件并重启旧版本。
8. 新版本确认成功后提交事务、删除备份和敏感临时描述，保留有限的脱敏升级结果供 UI 展示。

更新日志必须能区分下载成功、等待退出、替换、重启确认、回滚成功和回滚失败。回滚失败属于高优先级错误，保留旧文件备份路径的可操作说明，但不得记录用户名、网络响应或任意命令行秘密。

### 8.3 崩溃恢复

- 事务状态必须以原子写入的 journal 表达，至少包含 `Prepared`、`Replacing`、`AwaitingStartup`、`Committed`、`RolledBack`。
- 更新器或 Windows 在替换中断后，下次启动必须先检查与当前安装根匹配的未完成事务，按文件哈希和 journal 状态完成提交或恢复旧版本。
- 不得仅根据 `.old` 文件存在就覆盖当前 EXE；所有恢复操作必须验证事务 ID、版本和哈希。
- 同时只允许一个更新事务。旧事务未完成或无法安全判断时阻止新安装，并给出人工恢复说明。

## 9. 状态、并发和生命周期边界

- Desktop 更新使用独立的更新状态模型，例如 `Idle`、`Checking`、`UpdateAvailable`、`Downloading`、`ReadyToInstall`、`Installing`、`Failed`；不得向 `HarnessRuntimeState` 添加升级状态。
- 自动检查、手动检查、下载、安装准备和清理由一个可取消的更新协调器串行管理。状态提交使用 operation generation，过期网络/哈希/进度结果不得覆盖新状态。
- 下载取消只清理更新临时文件，不停止 DSH、不导航 WebView2、不修改设置中的工作目录或 Service URI。
- 应用普通退出时取消检查和下载；安装退出时先完成更新器接管，再走同一应用清理路径。
- `RunningExternal` 升级期间只停止 watcher 和宿主资源，绝不结束外部进程。`RunningOwned` 必须通过现有 coordinator/Dispose 和 Job Object 收尾，不能让更新器按 PID 杀进程树。
- 安装确认与 Harness 生命周期操作之间必须有明确门禁。不能在旧端点尚未释放或 lifecycle operation 未收尾时开始文件替换。
- 所有 `HttpResponseMessage`、流、哈希对象、文件句柄、CTS、timer、事件订阅、`SemaphoreSlim` 和子进程必须在成功、失败、取消与退出路径成对释放。

## 10. 配置、隐私、日志与错误

### 10.1 配置

实现时预计新增：

- `AutoUpdateEnabled`，默认 `true`
- `LastSuccessfulDesktopUpdateCheckAt`，可空 UTC `DateTimeOffset`
- `SkippedDesktopVersion`，可空合法 SemVer

字段落地必须递增 `SchemaVersion`，使用现有统一迁移管线同时迁移主配置和 `.bak`。旧配置默认开启自动检查；损坏、未来 schema、非法日期或非法版本按现有配置策略安全回退。下载路径、资产 URL、签名、公钥、安装目录、事务密钥和进度不得写入 `AppSettings`。

### 10.2 隐私和日志

- 自动检查会向 GitHub 暴露常规网络元数据，必须在安装说明和设置文案中如实说明并允许关闭。
- 日志记录更新阶段、版本、字节计数、稳定错误码、HTTP 状态分类和耗时，不记录完整响应、签名原文、release body、重定向 query、代理信息、环境变量或用户凭据。
- 更新目录和安装路径只在诊断确有必要时以现有脱敏策略记录；UI 不展示任意服务返回的本机路径。
- 发布说明按有限纯文本处理后才能进入 UI；外部文本继续规范化、限长和脱敏。

### 10.3 错误码

新增独立 `UPD-E7xx` 号段，实施阶段 0 冻结具体语义并同步维护规则和详细设计。至少区分：

| 建议错误码 | 语义 |
| --- | --- |
| `UPD-E701` | 无法查询 Desktop 更新 |
| `UPD-E702` | 发行元数据或版本不一致 |
| `UPD-E703` | 更新清单签名无效或 key 不受信 |
| `UPD-E704` | 更新包下载失败或被取消以外中断 |
| `UPD-E705` | 更新包长度、哈希或归档结构无效 |
| `UPD-E706` | 当前安装目录不支持自动替换 |
| `UPD-E707` | 更新器无法接管或等待旧进程超时 |
| `UPD-E708` | 文件替换失败但旧版本已恢复 |
| `UPD-E709` | 新版本未能启动，已回滚旧版本 |
| `UPD-E710` | 回滚失败，需要人工恢复 |

用户取消属于预期结果，不显示为失败错误。所有用户提示使用简明中文；技术消息必须可检索、已脱敏且保留内部 cause。

## 11. UI 与可访问性

- 设置窗口增加清晰的“自动检查 Desktop 更新”复选框，不与 DSH/npm 版本策略混淆。
- 关于窗口将“Desktop 更新”和“DSH/npm latest”分成不同区域或页签，按钮明确命名为“检查 Desktop 更新”和“查询 DSH latest”。
- 主窗口只在有新版或有待安装更新时显示紧凑、非模态的更新提示，不使用营销式弹屏，不遮挡 Code/Chat/WebView2 主操作。
- 下载展示确定进度；无法取得总长度时显示不确定进度，但仍显示已下载字节和阶段。哈希验证、等待退出、安装和回滚使用文字阶段，不能只依赖颜色。
- “退出并安装”是明确命令；“取消下载”“稍后安装”“重试”“打开 Releases”在对应状态可用，重复点击被抑制。
- 更新准备失败不关闭关于窗口、不清除已显示的错误，也不影响 Code/Chat 当前焦点和 Harness 操作。
- 控件提供 ToolTip、Automation Name、键盘焦点和屏幕阅读器可理解的状态。在 820x600 以及 100%、125%、150%、200% DPI 下不得重叠、裁切或被 WebView2 覆盖。

## 12. 验收标准

### 12.1 检查与版本

- `AC-UPD-CHECK-001`：自动检查默认开启、延迟执行、不阻塞窗口和 DSH，并遵守持久化的 24 小时间隔。
- `AC-UPD-CHECK-002`：关闭自动检查后无周期 GitHub 请求，手动检查仍可用。
- `AC-UPD-CHECK-003`：自动与手动并发触发只产生一个请求；失败有退避且不改变 Harness 状态。
- `AC-UPD-VERSION-001`：只接受固定仓库、稳定、非 draft、严格高于当前版本且 RID/schema 受支持的 Release。
- `AC-UPD-VERSION-002`：tag、清单、资产名、EXE 版本任一不一致时拒绝安装，不允许降级或 prerelease 自动升级。

### 12.2 信任与下载

- `AC-UPD-TRUST-001`：客户端先验证受信公钥签名，再信任清单字段；未知 key 或篡改清单被拒绝。
- `AC-UPD-TRUST-002`：ZIP 长度和 SHA-256 与已签名清单完全一致，单字节篡改即失败并删除临时文件。
- `AC-UPD-TRUST-003`：HTTP 降级、未批准 host、过多重定向、重复资产、超大响应和异常 Content-Length 均被拒绝。
- `AC-UPD-ZIP-001`：路径穿越、绝对路径、重复/大小写冲突条目、symlink/reparse、额外文件和解压炸弹均不能进入安装目录。
- `AC-UPD-DOWNLOAD-001`：下载显示进度、可取消、取消后无半成品且 DSH/WebView2/设置不变。

### 12.3 安装、回滚与所有权

- `AC-UPD-INSTALL-001`：安装前有明确二次确认；普通窗口关闭仍隐藏到托盘。
- `AC-UPD-INSTALL-002`：Owned DSH 通过现有退出路径停止并回收完整进程树；External DSH 在升级前后保持运行。
- `AC-UPD-INSTALL-003`：更新器等待旧进程和单实例资源释放后才替换，且从不执行 Shell 文本或网络提供的目标路径。
- `AC-UPD-INSTALL-004`：替换成功后新版本自动重启、报告正确版本并提交事务，设置和 WebView2/Chat profile 保留。
- `AC-UPD-ROLLBACK-001`：模拟新 EXE 启动失败、就绪超时和版本错误时，旧 EXE/README 完整恢复并可重新启动。
- `AC-UPD-ROLLBACK-002`：在每个 journal 阶段中断后，下次启动可确定提交或回滚，不产生新旧混合安装。
- `AC-UPD-PATH-001`：只读、UNC、reparse 或不可恢复目录不尝试自动替换，不请求静默提权，并提供手工升级路径。

### 12.4 UI、配置与隐私

- `AC-UPD-UI-001`：Desktop 更新与 DSH latest 文案、状态、按钮和结果模型明确分离。
- `AC-UPD-UI-002`：新版提示非模态；检查、下载、验证、待安装、安装和失败状态可通过文字及键盘识别。
- `AC-UPD-CFG-001`：旧 schema 主配置和 `.bak` 均可迁移；非法更新时间/跳过版本不会破坏其他设置。
- `AC-UPD-PRIVACY-001`：设置可关闭自动 GitHub 请求；日志、配置、事务、验证报告和 ZIP 不含私钥、凭据、Cookie、Token、完整响应或用户数据。

## 13. 测试要求

### 13.1 单元测试

- SemVer stable/prerelease/draft、当前相同/更高、tag/manifest/asset/EXE 版本一致性。
- 固定仓库、精确资产名、GitHub API 限长、重定向 host/scheme/UserInfo/次数和 HTTP 错误映射。
- 使用测试密钥覆盖有效签名、篡改清单、未知 key、错误算法、截断签名和公钥轮换。
- 流式长度/SHA-256、取消、超限、未知 Content-Length、临时文件原子提交和过期清理。
- ZIP 路径、重复项、大小写、ADS、reparse、额外条目、解压上限和 EXE 元数据校验。
- 自动检查延迟、24 小时间隔、失败退避、手动合并、跳过版本和 `TimeProvider` 可控时间测试。
- 更新状态机、operation generation、取消、重复点击、退出竞争和 Dispatcher 更新测试。
- 配置 schema 迁移、主文件损坏后 `.bak` 迁移、非法字段和原子保存。
- ViewModel 文案、命令 `CanExecute`、Desktop/DSH 更新隔离和关闭后事件解绑。

### 13.2 Windows 集成测试

- 使用本地 fake GitHub server/自定义 handler 和测试签名资产完成检查、下载、验证，不访问真实 GitHub。
- 在唯一临时“安装目录”复制 TestHarness/测试 EXE，验证更新器等待父进程、替换、启动握手、成功提交与清理。
- 在 `Prepared`、`Replacing`、`AwaitingStartup` 注入确定性故障，验证回滚和下次启动恢复。
- 验证替换一个文件失败时不会留下 EXE/README 混合版本。
- 验证新版本立即退出、握手超时、版本不符、更新器超时和回滚失败映射。
- 验证 Owned 测试进程树升级退出后被回收，外部 TestHarness 进程保持运行。
- 测试目录、进程、Mutex、pipe、journal、ZIP 和备份必须在 `finally`/Dispose 中清理，不能操作真实安装目录或用户更新缓存。

### 13.3 外部人工验证

- 从真实 GitHub 私有/草稿演练 Release 验证三资产发现、签名、下载和发行说明展示，再用正式稳定 Release 验证升级链。
- Windows 10/11 x64 的可写普通目录、带空格/中文路径和长路径升级。
- Windows 受保护目录、UNC、reparse、文件占用、磁盘空间不足、断网、代理、TLS 拦截和杀毒软件阻拦的安全失败路径。
- Owned/External DSH、Code/Chat、托盘隐藏、第二实例激活、安装确认和升级后 Chat 登录态保留。
- 820x600 与 100%、125%、150%、200% DPI 的提示、进度、错误、关于和设置布局。
- 生产私钥只在受控发布环境使用；验证记录只能保存公钥 ID、资产哈希和结果，不能保存私钥材料。

实现时必须同步：

- `README.md` 与 `docs/installation.md`：自动检查开关、联网说明、下载/安装、受保护目录手工路径、回滚和故障恢复。
- `docs/deepseek-harness-desktop-development.md`：产品边界、更新状态、数据位置和生命周期关系。
- `docs/deepseek-harness-desktop-detailed-design.md`：协议、签名、密钥轮换、更新器、journal、启动握手、错误码和时序。
- `AGENTS.md` 与 `CLAUDE.md`：新增系统更新的固定源、签名、目标路径、无静默提权、Owned/External 边界和 `UPD-E*` 约束，并保持两文件完全一致。
- `code_rule.md`：补充更新脚本、签名材料、归档解析、文件替换和回滚规则。
- `eng/Publish-Release.ps1` 与 `eng/Verify-Release.ps1`：生成、签名并独立验证三项资产，发布缺少生产签名时 fail closed。
- `docs/validation/`：新增带日期的系统升级验证记录，不回写历史结果。

## 15. 完成定义

只有同时满足以下条件，系统自动升级功能才算完成：

1. 自动检查、手动检查、下载、验证、确认、退出、替换、重启和结果反馈形成可用闭环。
2. 任何可执行更新都由内置受信公钥验证的清单授权，并通过长度、SHA-256、归档和 EXE 版本多重校验。
3. 新版本启动失败和替换中断有确定的自动回滚或恢复证据，不留下混合版本。
4. 更新器不能执行任意 Shell、网络目标或任意本机路径，不静默提权。
5. Owned DSH 正常回收，External DSH 不受影响，Harness 状态机和 WebView2 导航边界没有被更新状态污染。
6. 自动请求可关闭；配置、日志、发布资产和验证材料不泄露凭据、私钥或用户数据。
7. 所有相关单元、Windows 集成、更新器故障注入、WPF/DPI 和真实 Release 演练均有通过证据。
8. 发布脚本和门禁消费与客户端相同的资产、签名和协议，缺少生产签名不能发布自动升级版本。
9. 文档、维护规则、版本、安装说明和新验证记录与实际行为一致。
10. 未修改或提交 `bin/`、`obj/`、`TestResults/`、更新缓存、备份、日志、用户配置、WebView2 profile 或密钥材料。
