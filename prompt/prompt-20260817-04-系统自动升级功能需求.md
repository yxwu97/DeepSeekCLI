## 2. 使用方式与术语

将本文作为系统自动升级功能后续设计、实现和验收的完整输入。执行者必须先读取届时的当前实现、项目文件、发布脚本、相关测试、`AGENTS.md`、`CLAUDE.md`、`code_rule.md`、开发文档、详细设计、安装说明和最新验证记录，再依据真实类型与接口实施，不得仅根据本文猜测代码结构。

本文中的“系统”“Desktop”或“应用版本”特指 `DeepSeek Harness Desktop` 桌面宿主，不是 DSH/npm 包。现有关于窗口中的 npm `latest` 查询仍是 DSH 信息查询，不能复用其文案、结果模型或安装行为冒充 Desktop 升级。

本文中的“自动升级”采用以下安全语义：

1. 应用按固定周期自动检查本项目 GitHub Releases 中的稳定版本，不阻塞启动。
2. 发现新版后由用户明确选择是否下载，首期不静默预下载。
3. 下载、签名验证和版本目录暂存可以自动完成，但切换版本前必须再次取得用户确认。
4. 用户确认后，Desktop 正常退出，稳定启动器原子切换到完整的新版本目录并启动新版本。
5. 新版本启动探测失败时，稳定启动器把版本指针切回旧目录并重启旧版本。
6. 不静默终止 DSH、不强制升级、不自动提升权限，也不在运行中逐文件覆盖应用依赖。

## 3. 当前基线与差距

本文修订时的仓库事实如下，实施前必须重新核对：

- Desktop 面向 Windows 10/11 x64，目标框架为 `.NET Framework 4.8`。
- 发布物是 net48 轻量 ZIP，不携带 CoreCLR、Node.js、npm、npx、`node_modules` 或完整 DSH。
- 当前 ZIP 是多文件应用，包含主 EXE、EXE config、托管依赖、WebView2Loader、README 以及 `dsh-runtime/package.json` 和精确 lockfile；不是 single-file。
- `eng/Verify-Release.ps1` 已执行版本、锁定 DSH 资源、禁入项、ZIP 30 MB 上限和主 EXE 5 MB 上限检查，并运行真实私有 DSH 首次安装及二次免下载 smoke。
- 项目固定 GitHub 地址为 `https://github.com/yxwu97/DeepSeekCLI`；当前只能由用户手工打开 Releases 下载。
- `AboutViewModel` 的 npm `latest` 只表示 `@deepseek-ai/dsh`，不检查 Desktop。
- 当前应用是当前用户单实例；真正退出会保存设置、释放 WebView2/DI、停止 Owned DSH，并通过 Job Object 回收其子进程树。
- 仓库已有 net48 的 `TimeProvider`、任务等待、进程退出和 Windows 参数转义兼容层；net48 没有 `ProcessStartInfo.ArgumentList`。
- 当前发布布局没有稳定启动器、版本目录、安装文件清单、升级事务或启动回滚协议。

主要差距是：缺少可长期兼容的启动入口、可信发行元数据、自动检查调度、下载与暂存、版本目录切换、升级探测、配置写入屏障、失败回滚和双版本发布验证。

## 4. 目标与非目标

### 4.1 目标

1. 自动发现固定 GitHub 仓库中高于当前版本的最新稳定 `win-x64` Desktop 发行版。
2. 让用户在应用内完成检查、下载、验证、确认、退出、版本切换、重启和结果反馈。
3. 对发布元数据和 ZIP 建立独立于 HTTPS 的密码学真实性与完整性验证，任一验证失败都 fail closed。
4. 采用稳定启动器与版本化应用目录，确保断电发生在提交前后时，启动器总能选择一个完整版本，而不是新旧 DLL 混装。
5. 保留设置、日志、WebView2 profile、Chat 登录态、工作目录和外部 DSH；更新包不得包含或迁移这些用户数据。
6. 安装前通过现有退出路径停止 Owned DSH；`RunningExternal` 永远不因升级被停止或接管。
7. 新版本无法完成只读启动探测时，自动恢复旧版本指针，且旧版本仍能读取原设置。
8. 发布门禁生成并验证客户端实际消费的 ZIP、签名清单和 detached signature。
9. 保持 net48 轻量发布约束和现有私有 DSH 安装/复用验证。

### 4.2 非目标

- 不自动升级 Node.js、WebView2 Runtime、DSH/npm 包或其他第三方系统依赖。
- 不实现 Windows Service、计划任务、常驻系统级代理、无人值守强制升级、差分补丁、P2P 或多更新通道。
- 不支持用户配置任意更新源、仓库、镜像、资产 URL、公钥或签名算法。
- 不接受网页、命令行或更新清单提供的任意 Shell、脚本、目标目录或可执行文件名。
- 不在自动升级事务中替换稳定启动器或信任根。启动器协议或公钥必须升级时，发布新的手工 Bootstrap 包。
- 不支持降级安装、跨 RID 更新、自动请求管理员权限或绕过 ACL、企业策略、杀毒软件、SmartScreen 和 UAC。
- 不把 CoreCLR、Node、npm、npx、`node_modules`、DSH 缓存或用户数据加入发布包。
- 不因系统更新放宽 Code/Chat WebView2 导航或宿主能力。

## 5. Bootstrap 与发布布局

### 5.1 两版本引导策略

当前版本没有更新客户端或稳定启动器，无法自行升级到第一版自动升级实现。因此功能必须按两个发行版验收：

1. `0.11.0` 或届时 minor 版本作为 Bootstrap。用户至少手工安装一次，获得稳定启动器、内置受信公钥、版本目录布局、更新客户端和本地安装清单。
2. Bootstrap 后的下一个 patch（例如 `0.11.1`）作为首个自动升级目标，必须从真实已安装的 Bootstrap 版本经 GitHub Releases 完成自动检查、下载、切换、重启和回滚演练。
3. 未完成 `N -> N+1` 两版本真实升级前，不得把自动升级功能标记为已完成。
4. 旧于 Bootstrap 的版本只能显示手工 Releases 入口，不能宣称可自动升级。

### 5.2 稳定启动布局

Bootstrap 安装后的运行布局如下。实际命名可在阶段 0 冻结，但职责不得混合：

```text
DeepSeekHarnessDesktop.exe                  # BCL-only net48 稳定启动器/更新 worker
README.md
.desktop-update/current.json                # 原子维护的当前版本指针
.desktop-update/manifests/<desktop-version>/# 自动更新保存的外部签名清单与签名
versions/<desktop-version>/
  DeepSeekHarnessDesktop.App.exe            # WPF 主应用
  DeepSeekHarnessDesktop.App.exe.config
  *.dll
  WebView2Loader.dll
  runtimes/win-x64/native/WebView2Loader.dll
  dsh-runtime/package.json
  dsh-runtime/package-lock.json
  version.files.json                        # 构建时生成的本版本文件库存
```

约束如下：

- 根目录 `DeepSeekHarnessDesktop.exe` 只负责严格参数解析、读取当前指针、启动主应用、执行更新 worker 和恢复未完成事务。
- 启动器只依赖 Windows 自带的 .NET Framework 4.8 BCL，不引用 NuGet 包、WPF、WebView2、DI、Serilog、System.Text.Json 或版本目录 DLL；实现 Job Object、reparse/path 校验和耐久提交所需的受控 Windows SDK P/Invoke 允许使用，并必须通过 SafeHandle、固定常量和错误映射封装。它必须在应用版本目录损坏时仍能运行。
- 主应用及其全部依赖位于单一版本目录。运行时不得从根目录或其他版本目录加载依赖。
- `version.files.json` 随 ZIP 生成并纳入外部签名清单的 `files[]`；它不包含 ZIP 自身哈希，避免循环依赖。自动更新成功后，worker 将已验证的外部 `update.json`/`update.sig` 保存到本地 manifests 目录；手工 Bootstrap 的首启库存由发布门禁验证过的 `version.files.json` 建立。
- 新版先完整写入新的版本目录并验证，最后才原子切换 `current.json`。提交前旧指针不变；回滚只切回旧指针，不逐文件拼回旧版本。
- 自动升级不替换稳定启动器。更新清单通过单调递增的正整数 `minimumLauncherProtocol` 声明协议要求；当前启动器协议号不足时只允许手工 Bootstrap，不在启动器内实现另一套 SemVer 比较。
- 根 README 可以在提交后尽力更新，但文档替换失败不得破坏运行版本或触发应用文件回滚。
- 成功提交后最多保留当前版本和一个已验证旧版本。只清理由本应用事务创建、路径和清单均匹配的版本目录，绝不删除安装根中的未知用户文件。

## 6. 产品行为

### 6.1 自动检查与手动检查

- 新增“自动检查 Desktop 更新”设置，默认开启；关闭后不发起周期 GitHub 请求，但关于窗口中的手动检查仍可用。
- 主窗口可交互且当前版本初始化完成后延迟约 30 秒执行首次自动检查，不阻塞主窗口、DSH 启动或 Chat 初始化。
- 同一进程和跨重启每 24 小时最多自动检查一次。持久化最近一次成功检查时间；失败采用有限退避，不紧密重试。
- 手动检查忽略 24 小时间隔，但与自动检查复用同一个操作门和请求；并发触发只产生一个网络请求。
- 自动检查失败只记录脱敏摘要，不弹阻塞窗口、不改变 Harness 状态。用户主动检查失败时显示可操作中文提示。
- 只查询 stable、非 draft Release。当前版本大于或等于候选时显示已是最新版本，不允许自动降级或安装 prerelease。

### 6.2 新版提示与用户选择

发现新版后使用非模态提示和关于窗口的“Desktop 更新”区域显示当前版本、新版本、发布时间、受限纯文本发行说明和固定 Release 页面入口。

用户至少可以选择：

- “下载更新”：开始下载并显示进度，下载期间可取消。
- “稍后提醒”：当前进程不重复打扰，下一个自动周期仍可提示。
- “跳过此版本”：只持久化精确版本，更高版本仍提示；手动检查仍显示被跳过版本并允许下载。
- “查看发行说明”：由受控系统浏览器打开固定仓库对应的 HTTPS Release 页面。

Desktop 更新、DSH npm `latest` 和本地版本历史必须使用独立模型、状态和文案。

### 6.3 下载、确认与切换

- 首期只有用户点击“下载更新”后才下载 ZIP，不静默预下载。
- 下载和全部验证完成后显示“退出并安装”和“稍后安装”。待安装包位于固定 LocalAppData 更新目录，不自动退出。
- “退出并安装”前再次说明：Desktop 将退出；Owned DSH 会按正常退出停止；外部 DSH 不受影响；成功后 Desktop 自动重启。
- Harness 正在 Starting/Stopping/Restarting、应用正在退出或事务不可安装时，安装命令不可用。下载不得改变 lifecycle generation。
- 用户确认安装后进入不可重入状态，禁止新的生命周期命令、重复退出和第二更新事务；稳定启动器接管成功后，应用才通过统一退出协调路径关闭。
- 普通窗口关闭仍隐藏到托盘，不能因已有待安装版本改变该语义。

### 6.4 不支持自动切换的环境

自动升级只支持本地、非 reparse point、当前用户可写的 Bootstrap 安装根。以下情况只提供固定 Releases 手工入口：

- 尚未安装稳定启动器或缺少合法本地安装清单。
- 启动器协议号低于清单 `minimumLauncherProtocol`，或需要轮换受信公钥。
- 安装根位于只读/受保护目录、UNC、不可用可移动介质、符号链接或 junction。
- 当前用户无法创建新版本目录、原子替换指针并恢复旧指针。
- 安全软件或文件占用使预检不能证明提交和回滚均可完成。

不得静默提权，也不得把下载内容写入其他应用目录。

## 7. 更新源、版本和签名协议

### 7.1 固定发行源与网络边界

- 唯一生产源是 `yxwu97/DeepSeekCLI` 的 GitHub Releases，owner/repository 不进入配置。
- GitHub API 只用于发现候选 tag、Release 页面和精确命名资产，不能授权任意执行内容。
- 请求不携带 Cookie、API Key、GitHub Token、DSH 凭据或环境信息；设置产品 User-Agent、15 秒元数据超时、有限重定向和响应上限。
- 每次重定向重新验证 HTTPS、无 UserInfo、host 属于阶段 0 真实验证的 GitHub 资产 host 集合，并限制跳转次数；拒绝 HTTP 降级。

### 7.2 版本与资产

- 使用 `NuGet.Versioning` 比较 SemVer，不使用字符串比较。
- Git tag、清单 Desktop 版本、ZIP 名、版本目录名和主应用 Product/File Version 必须一致。
- 候选必须严格高于当前 Desktop 版本，RID 精确为 `win-x64`，layout/schema 受当前客户端和启动器支持。
- draft、prerelease、资产重复、名称大小写不精确、元数据冲突或未来 schema 均不可自动安装。
- 每个稳定 Release 必须有且只有以下资产：

```text
DeepSeekHarnessDesktop-<version>-win-x64.zip
DeepSeekHarnessDesktop-<version>-win-x64.update.json
DeepSeekHarnessDesktop-<version>-win-x64.update.sig
```

### 7.3 签名清单与文件库存

`update.json` 至少包含：

- `schemaVersion`
- `layoutVersion`
- `desktopVersion`
- `runtime`
- `assetName`
- `assetBytes`
- `assetSha256`
- `publishedAt`
- `minimumLauncherProtocol`：单调递增的正整数
- `signingKeyId`
- `files[]`：每项包含规范化相对路径、角色、字节数和 SHA-256

文件角色至少区分 `launcher`、`application`、`documentation` 和 `pointerTemplate`。`files[]` 按 Windows OrdinalIgnoreCase 检查唯一性，按 Ordinal 固定排序。ZIP 每个文件必须与清单一一对应，不允许遗漏、额外文件、重复项或大小写冲突。

主应用、启动器和发布门禁必须共享同一受限 BCL 清单读取实现。实现优先使用 net48 的 `JsonReaderWriterFactory`/`DataContractJsonSerializer` 与 `XmlDictionaryReaderQuotas`，在解析前严格解码 UTF-8 并拒绝 BOM；显式限制原始字节数、嵌套深度、键/字符串长度、数组与 `files[]` 数量以及整数范围，并拒绝重复字段、未知必需字段、非规范路径和溢出。不得为此手写通用 JSON 解析器；使用可复现的畸形输入与属性测试语料覆盖边界，无需建设独立长期 fuzz 平台。

生产清单使用固定字段顺序、LF、无多余空白的 UTF-8 无 BOM 字节。发布工具必须直接对最终原始字节签名；客户端先验证原始字节签名，再解析 JSON。不得重新序列化后验证。

### 7.4 密码学与密钥生命周期

- Bootstrap 协议优先采用 .NET Framework 4.8 BCL 和 Windows 10/11 均稳定支持的 RSA-3072 + SHA-256 PKCS#1 v1.5 detached signature。若阶段 0 改用 PSS，必须先证明 net48 启动器、客户端和发布环境使用同一实现并冻结算法编号。
- 主应用和稳定启动器内置相同生产公钥与 `signingKeyId`；私钥只存在于离线环境或受控 CI Secret，绝不进入仓库、ZIP、日志、测试快照或验证报告。
- 客户端先验证清单签名，再信任版本、文件库存、ZIP 长度和哈希；下载后流式验证 ZIP 长度和 SHA-256。
- 启动器在提交前再次验证清单签名、ZIP/解压文件哈希、目录边界和 `minimumLauncherProtocol`，不能只信任主应用传递的“已验证”状态。
- 签名无效、未知 key、长度/哈希不符、库存冲突时删除临时文件并拒绝安装，不提供“仍然继续”。
- 稳定启动器不自动替换，因此信任根轮换需要新的手工 Bootstrap。旧 key 泄露时停止自动发布，不能通过旧 key 签名的远程清单无条件安装新信任根。
- 测试 key 只能存在于测试夹具或临时目录，生产启动器不得信任测试 key。

### 7.5 Windows 代码签名策略

RSA detached signature 是更新协议的信任根；Authenticode 用于 Windows 发布者身份、时间戳以及 SmartScreen、Defender、WDAC/企业策略兼容性，二者不可互相替代。阶段 0 必须根据证书、时间戳服务和发布环境冻结以下一种策略，不预先限定 EV 或 OV：

- `Required`：根启动器和 WPF 主应用均须有效 Authenticode 签名并带可信时间戳；发布门禁验证签名、证书链、文件版本和时间戳，缺失或失效时阻断正式发布。
- `Advisory`：协议实现仍可推进，RSA 清单签名继续 fail closed；发布前必须在目标 Windows 环境记录未签名/低信誉二进制的 SmartScreen、Defender 和适用企业策略结果，明确残余风险和手工降级路径，不得把未执行的外部验证宣称为通过。

证书采购不是协议和本地实现的先决条件，但所选策略、实际产物和发布说明必须一致。

## 8. 下载、暂存和归档安全

- 更新根固定为 `%LOCALAPPDATA%\DeepSeekHarnessDesktop\updates`，按事务 ID 和目标版本隔离；不写入仓库、工作目录或 WebView2 数据目录。
- 下载先写唯一 `.tmp`，设置客户端总大小上限并流式计算 SHA-256；验证后原子重命名。
- 响应长度未知或超过清单/上限时拒绝。网络失败、取消、哈希失败后清理未验证文件。
- 已存在暂存包每次复用仍重新验证签名、长度、ZIP 哈希和完整文件库存。
- ZIP 拒绝绝对路径、`..`、目录穿越、ADS、重复/大小写冲突、symlink/reparse 属性、加密项和解压炸弹。
- ZIP 必须继续满足 net48 轻量发布门禁：不含 CoreCLR、Node、npm、npx、`node_modules`、DSH 缓存、设置、日志或用户数据，并保持 ZIP/启动器/主应用体积上限。
- 自动安装只把 `application` 角色文件解压到新的 `versions/<desktopVersion>` 临时目录，验证所有文件后原子改名为最终版本目录。不得把包内路径直接拼接到安装根。
- 包内 launcher 仅供手工 Bootstrap 安装；自动事务验证其元数据但不覆盖当前根启动器。
- 发行说明和 README 视为不可信文本，限制长度，UI 不解析 HTML、图片、脚本或任意 Markdown 链接。

## 9. 稳定启动器、事务与回滚

### 9.1 启动器入口

- 正常模式只读取受控 `current.json`，验证版本名和路径位于 `versions/` 直接子目录，然后启动固定主应用文件。
- 更新模式必须在任何 WPF/主应用初始化前识别，使用严格的固定参数 schema；未知参数、额外参数、非法事务 ID 或路径均拒绝。
- net48 不使用 `ProcessStartInfo.ArgumentList`。所有原生进程参数逐项通过仓库 `ProcessStartInfo.AddArgument` 兼容层转义，`UseShellExecute=false`，不经 cmd、PowerShell 或 Shell 字符串。
- 启动器只读取位于固定 LocalAppData 更新根的事务描述，网络清单不能指定安装根、任意文件名或第三方进程。
- 启动器不管理 DSH，不扫描端口，不结束未由它创建的进程。

### 9.2 单实例与更新事务所有权

- 现有 WPF 主应用继续持有当前用户应用 Mutex `Local\DeepSeekHarnessDesktop-<CurrentUserSid>` 和固定 `Activate` pipe；正常 launcher 不持有或向下继承该 Mutex，启动 core 后退出。
- 第二次启动仍由新 core 通过现有应用 Mutex 和 `Activate` pipe 激活主实例，不在 launcher 复制另一套激活协议。
- probe 与正常 core 竞争同一个应用 Mutex。worker 永不持有应用 Mutex，只等待旧 core 释放后才允许切换指针。
- worker 使用按“当前用户 SID + 规范化安装根”派生的独立更新 Mutex；同一安装根只能有一个 worker，不同用户或安装根不得互相阻塞。
- 根 launcher 正常启动前先检查匹配安装根的 journal 和更新 Mutex；事务活跃或待恢复时先等待/恢复，不得启动竞争的旧 core。Mutex、pipe 命名、ACL、超时和释放顺序必须在阶段 0 冻结并覆盖双开/崩溃测试。

### 9.3 提交序列

1. 主应用创建原子事务 journal，完成包和目标版本目录验证，启动根目录稳定启动器的 update worker 模式。
2. worker 验证事务、当前安装根、当前版本指针、父进程身份和包签名，并向主应用发送“已接管”握手。
3. 主应用以 `InstallUpdate` 退出原因进入统一清理：停止 scheduler、保存当前旧 schema 设置、停止 Owned DSH、释放 WebView2/托盘/DI/管道/Mutex；External DSH 不被结束。
4. worker 等待旧主应用退出和单实例 Mutex 释放，超时则不切换指针。
5. worker 再次验证完整新版本目录，原子写入 `current.json.tmp` 并用阶段 0 已验证的同卷 Windows 提交原语切换指针；旧版本目录保持不变。
6. worker 启动新主应用的受控“升级探测模式”，传递事务 ID；新进程取得单实例并完成设置只读迁移、DI 和关键启动检查，但不启动 Owned DSH、不开放主操作，也不持久化新 schema。
7. 新主应用报告准确 Desktop 版本和 readiness。worker 将 journal 耐久标记 `Committed` 后发送提交确认；新应用只有收到确认才解除写入屏障并继续正常初始化。若 worker 在写入 `Committed` 后、确认送达前退出，probe 超时后必须无持久写入地退出；下次根 launcher 根据 `Committed` 启动已提交新版本。
8. 新应用提前退出、超时、版本不符或报告失败时，worker 原子切回旧指针，只结束自己创建的新主应用并重启旧版本。
9. 成功后异步清理超额旧版本目录和暂存；回滚后保留有限脱敏错误和已验证新包供诊断/重试。

### 9.4 Journal 与断电恢复

- journal 至少包含 `Prepared`、`WaitingForExit`、`PointerSwitched`、`AwaitingStartup`、`Committed`、`RolledBack`、`RecoveryRequired`。
- journal、指针和事务元数据均使用临时文件、`FileStream.Flush(true)` 和阶段 0 实测冻结的同卷 Windows 提交原语。优先验证 `File.Replace`/`ReplaceFile` 与 `MoveFileEx(MOVEFILE_WRITE_THROUGH)` 的适用边界；仅在目标 Windows/文件系统确认支持时使用父目录句柄 `FlushFileBuffers`。若无法证明所声明的断电语义，该目录不得自动切换并降级为手工安装。
- 新版本目录在切换前必须完整；旧版本目录在提交确认前不得删除。因此断电后 `current.json` 只能指向完整旧版或完整新版。
- 下次用户启动根启动器时，启动器先检查匹配当前安装根的未完成 journal，再决定继续探测或切回旧指针；恢复不依赖主应用 DLL 能否加载。
- 不得只根据目录名、`.old` 或单一文件存在推断恢复。版本、指针、manifest、签名和文件哈希必须一致。
- 同一安装根只允许一个事务。无法确定安全终态时进入 `RecoveryRequired`，保持最后一个已验证可启动指针并显示人工恢复说明。

### 9.5 配置反向兼容屏障

- 升级探测模式只读加载并在内存中迁移设置，不得写回更高 `SchemaVersion`、窗口状态或其他用户数据。
- 只有 worker 提交事务并确认后，新版本才可持久化新 schema。
- 探测失败回滚时，旧版本看到的主设置与 `.bak` 必须保持升级前字节或保持旧版本可读。
- 后续新增会在启动时修改 WebView2 profile、私有 DSH 或其他持久状态的迁移时，必须纳入同一“提交前禁止不可逆写入”规则并补回滚测试。
- probe DI 只能包含明确无持久副作用的服务。集成测试对应用控制的安装根、AppData、LocalAppData、WebView2 profile 和私有 DSH 根做前后快照 diff；提交确认前仅允许事务 journal/握手标记和专用、有界、脱敏的 probe 诊断日志发生变化，其他新增文件或字节变化均使测试失败。后续服务加入 probe DI 时必须更新副作用审查和显式 allowlist。

## 10. 状态、并发和生命周期边界

- Desktop 更新使用独立状态，例如 `Idle`、`Checking`、`UpdateAvailable`、`Downloading`、`Verifying`、`ReadyToInstall`、`Installing`、`Failed`；不得向 `HarnessRuntimeState` 添加升级状态。
- 自动检查、手动检查、下载、安装准备和清理由单一更新协调器串行管理。状态提交使用 operation generation，过期网络/哈希/进度结果不得覆盖新状态。
- 下载取消只清理更新临时文件，不停止 DSH、不导航 WebView2、不修改工作目录、Service URI 或私有 DSH。
- 普通退出取消检查和下载；安装退出必须先取得 worker 接管握手，再走现有清理。
- `RunningExternal` 只停止 watcher/宿主资源，不结束外部进程。`RunningOwned` 通过现有 coordinator/Dispose 和 Job Object 收尾，worker 不按 PID/端口杀 DSH。
- 安装确认与 Harness 生命周期操作之间有明确门禁，不能在旧 lifecycle operation 未收尾时切换版本。
- HTTP 响应、流、哈希、文件句柄、CTS、timer、事件、SemaphoreSlim、Process、pipe 和 Mutex 在所有终态成对释放。

## 11. 配置、隐私、日志和错误

### 11.1 配置

预计新增：

- `AutoUpdateEnabled`，默认 `true`
- `LastSuccessfulDesktopUpdateCheckAt`，可空 UTC `DateTimeOffset`
- `SkippedDesktopVersion`，可空合法 SemVer

实施时从当前 schema 显式递增，复用主配置与 `.bak` 的统一迁移管线。非法日期/版本不得破坏其他字段。下载路径、URL、签名、公钥、安装根、事务和进度不写入 `AppSettings`。

### 11.2 隐私与日志

- 自动检查会向 GitHub 暴露常规网络元数据，设置和安装说明必须如实说明并允许关闭。
- 日志记录阶段、Desktop 版本、字节计数、稳定错误码、HTTP 状态分类和耗时，不记录响应正文、签名原文、release body、重定向 query、代理信息、环境变量或凭据。
- 路径按现有策略脱敏。事务文件不得包含私钥、Token、Cookie、API Key 或任意 Shell。
- 外部发行说明先规范化、限长和脱敏，再进入 UI；文件日志不记录全文。

### 11.3 错误码

新增独立 `UPD-E7xx` 号段，阶段 0 冻结并同步维护规则和详细设计。至少区分：

| 建议错误码 | 语义 |
| --- | --- |
| `UPD-E701` | 无法查询 Desktop 更新 |
| `UPD-E702` | Release、版本、layout 或资产不一致 |
| `UPD-E703` | 清单签名无效或 key 不受信 |
| `UPD-E704` | 更新包下载失败 |
| `UPD-E705` | ZIP 长度、哈希、文件库存或归档结构无效 |
| `UPD-E706` | 当前安装布局/目录不支持自动升级 |
| `UPD-E707` | 稳定启动器无法接管或等待旧进程超时 |
| `UPD-E708` | 新版本目录准备或指针提交失败，旧版仍有效 |
| `UPD-E709` | 新版本探测失败，已切回旧版本 |
| `UPD-E710` | 无法确认安全终态，需要人工恢复 |
| `UPD-E711` | 当前启动器或信任根过旧，需要手工 Bootstrap |

用户取消不是错误。用户提示使用简明中文；技术消息可检索、已脱敏并保留内部 cause。

## 13. 验收标准

### 13.1 Bootstrap、检查与版本

- `AC-UPD-BOOT-001`：Bootstrap ZIP 安装后，根启动器可在不加载任何应用依赖时启动当前版本目录。
- `AC-UPD-BOOT-002`：旧于 Bootstrap 的版本不宣称自动升级；启动器/信任根过旧时只提供手工入口。
- `AC-UPD-CHECK-001`：自动检查默认开启、延迟执行、不阻塞窗口/DSH，并遵守持久化 24 小时间隔。
- `AC-UPD-CHECK-002`：关闭自动检查后无周期 GitHub 请求，手动检查仍可用。
- `AC-UPD-CHECK-003`：自动与手动并发只产生一个请求；失败退避且不改变 Harness 状态。
- `AC-UPD-VERSION-001`：只接受固定仓库、stable、非 draft、严格更高、RID/layout/schema/launcher 兼容的 Release。
- `AC-UPD-VERSION-002`：tag、清单、ZIP、目录名或主应用版本不一致即拒绝。

### 13.2 信任、文件库存与下载

- `AC-UPD-TRUST-001`：主应用和启动器都先验证受信公钥签名，再信任清单；篡改或未知 key 被拒绝。
- `AC-UPD-TRUST-002`：ZIP 和每个库存文件的长度/SHA-256 匹配；单字节篡改即失败。
- `AC-UPD-TRUST-003`：HTTP 降级、未批准 host、过多重定向、重复资产、超大响应均被拒绝。
- `AC-UPD-TRUST-004`：发布冻结并执行 `Required` 或 `Advisory` Authenticode 策略；策略、两个 EXE 的实际签名/时间戳、Windows 外部验证证据和风险说明一致。
- `AC-UPD-ZIP-001`：路径穿越、ADS、重复/大小写冲突、symlink/reparse、额外文件和解压炸弹不能进入版本目录。
- `AC-UPD-ZIP-002`：发布包继续满足 net48 禁入项、DSH lock 哈希和体积门禁。
- `AC-UPD-DOWNLOAD-001`：下载有进度且可取消；取消后无可执行半成品，DSH/WebView2/设置不变。

### 13.3 切换、断电恢复与所有权

- `AC-UPD-INSTALL-001`：安装前二次确认；普通窗口关闭仍隐藏到托盘。
- `AC-UPD-INSTALL-002`：Owned DSH 由现有退出路径回收完整树；External DSH 在升级前后保持运行。
- `AC-UPD-INSTALL-003`：worker 等待旧应用和 Mutex 释放后才切换指针，不执行 Shell 或网络目标路径。
- `AC-UPD-INSTALL-004`：新版本目录完整后才通过阶段 0 验证的耐久提交原语切换；新版本探测成功并提交后继续正常初始化。
- `AC-UPD-INSTALL-005`：应用 Mutex/Activate pipe、按用户与安装根隔离的更新 Mutex 及 launcher/core/probe/worker 所有权符合冻结协议；双开和事务恢复不会启动竞争旧 core 或并行 worker。
- `AC-UPD-ROLLBACK-001`：新主应用退出、超时、错版本或探测失败时原子切回旧指针并重启旧版。
- `AC-UPD-ROLLBACK-002`：在每个 journal 阶段模拟中断后，根启动器可选择完整旧版或完整新版，不依赖损坏的应用 DLL。
- `AC-UPD-ROLLBACK-003`：探测失败前没有持久化新配置 schema，旧版回滚后仍读取原设置。
- `AC-UPD-ROLLBACK-004`：worker 在 `Committed` 写入后、确认送达前退出时，probe 超时且不越过写入 allowlist；下次 launcher 启动已提交新版本，不回切已提交事务。
- `AC-UPD-PATH-001`：只读、UNC、reparse、无 Bootstrap 或启动器过旧时不尝试自动切换、不静默提权。

### 13.4 UI、配置与隐私

- `AC-UPD-UI-001`：Desktop 更新与 DSH latest 的模型、按钮和文案明确分离。
- `AC-UPD-UI-002`：检查、下载、验证、待安装、探测、提交、回滚和手工 Bootstrap 状态可通过文字及键盘识别。
- `AC-UPD-CFG-001`：旧 schema 主配置和 `.bak` 均迁移；非法更新时间/跳过版本不影响其他设置。
- `AC-UPD-PRIVACY-001`：可关闭自动请求；日志、配置、journal、验证报告和 ZIP 不含私钥、凭据、用户数据或响应正文。

- 解决方案与发布脚本：新增最小启动器项目，主 WPF 应用进入版本目录；发布 ZIP 继续满足轻量门禁。
- `Publish-Release.ps1`/`Verify-Release.ps1`：生成并独立验证 ZIP/json/sig、完整库存、签名、Bootstrap 布局、DSH lock、禁入项和体积。
- `docs/validation/`：分别记录 Bootstrap 安装和 `N -> N+1` 自动升级，不回写历史记录。
- 实现按兼容新功能递增 minor；首个自动升级演练按 patch 递增，均同步 AppVersion、manifest 与版本历史。

## 16. 完成定义

只有同时满足以下条件才算完成：

1. 用户手工安装 Bootstrap 后，自动检查、下载、验证、确认、退出、目录切换、探测、提交和结果反馈形成闭环。
2. 真实稳定 Release 完成 `N -> N+1` 自动升级，不用仅同版本或本地假包代替。
3. 主应用和稳定启动器都通过共享受限 BCL reader 验证受信签名、ZIP 和完整文件库存；任何冲突 fail closed，Authenticode 产物与冻结策略一致。
4. 断电和进程终止后，根启动器通过已验证的 Windows 耐久提交原语始终选择完整版本目录，不出现跨版本 DLL 混装。
5. 新版探测失败时指针和配置均可回滚；`Committed` 后确认丢失时恢复新版且 probe 不越过写入 allowlist。
6. 启动器不执行 Shell、不接受任意路径、不管理 DSH、不静默提权，也不自动更新自身或信任根。
7. Owned DSH 正常回收，External DSH 不受影响；更新/Harness/Code/Chat 状态互相隔离。
8. net48 轻量 ZIP、体积、禁入项、DSH lock 和私有 DSH smoke 门禁全部保留。
9. 所有单元、Windows 集成、journal/Mutex/confirm-loss 故障注入、WPF/DPI 和真实 Release 验证有证据。
10. 文档、维护规则、版本和安装说明一致，仓库及产物不含密钥、更新缓存、journal、备份、日志、配置或用户数据。
