## 2. 使用方式与需求优先级

将本文作为托管 DSH 运行时、自动故障识别、自修复和发布验收的完整输入。执行者必须先读取届时当前实现、项目文件、相关测试、`AGENTS.md`、`CLAUDE.md`、`code_rule.md`、开发文档、详细设计、安装说明和最新验证记录，再依据真实类型与接口实施，不得根据本文编造 API、DSH 入口或 npm 行为。

本文基于 `0.6.1` 新设备故障证据，取代以下已经被实测否定的启动假设：

1. 固定顶层 `@deepseek-ai/dsh@0.1.0-rc.6` 即可固定完整 DSH 运行时。
2. 用户机器上的 `npx` 能在所有受支持 Node/npm 组合上可靠完成首次依赖解析。
3. 一个覆盖下载、解析、安装、进程启动和 HTTP 健康检查的总超时足以准确分类故障。
4. 超时后提供手动 npx 命令可以满足 Desktop 自动完成准备的产品目标。

本文与较早 Prompt/Plan 冲突时，涉及 DSH 版本解析、客户端 npx、运行时封装和自动恢复的部分以本文为准。`prompt/plan-20260817-04` 的 Desktop 系统自动升级需求是独立能力，不得把 Desktop 更新和 DSH 托管运行时混为一个状态机、错误码或发布事务。

## 3. 已确认故障事实

附件日志来自新设备，关键事实如下：

- 使用 `node@v24.19.0` 和 `npm@11.17.0`。
- npm 成功访问 `https://registry.npmjs.org/`，顶层包元数据请求返回 HTTP 200，后续大量元数据来自本机缓存。
- 命令顶层版本为 `@deepseek-ai/dsh@0.1.0-rc.6`，但 DSH 包的传递依赖大量使用 `^0.1.0-rc.6`。
- npm 实际把 `@deepseek-ai/dsh-fs`、`dsh-agent`、`dsh-base`、`dsh-client-*` 等大量子包解析为 `0.1.0-rc.7`。
- 日志停在 `idealTree buildDeps` / `placeDep`，没有进入完成安装、启动 DSH 或正常退出阶段。
- npx 进程保持存活，现有 `NpmFailureClassifier` 只在进程退出时基于 stderr 分类，因此最终只能由健康等待返回通用 `DSH-E203`。

由此确认：顶层精确版本不能约束发布者声明的范围型传递依赖；实时 npx 解析会受上游新版本、用户 npm 版本、缓存和解析器行为影响。该问题不是 GitHub 不可达，也不能通过延长健康检查超时从根本上解决。

## 4. 目标与非目标

### 4.1 目标

1. 新设备安装 Desktop 后，不要求用户安装 Node.js、执行 npx、确认 npm 提示、清理 npm 缓存或修改 `.npmrc`。
2. 发布阶段冻结并验证完整 DSH 依赖图，在用户设备上不重新解析 npm semver 范围。
3. Desktop 使用应用私有、版本化、可校验、可原子替换的 Node + DSH 运行时，不写入全局 npm 或系统 PATH。
4. 首次准备、完整性验证、运行时启动和 DSH HTTP 身份确认使用独立阶段、进度、期限和错误码。
5. 对中断解包、私有缓存损坏、文件缺失、完整性失败和新运行时启动失败自动恢复，不让用户手工处理目录。
6. 自动恢复只作用于 Desktop 创建的暂存目录、托管运行时和 Owned 进程，绝不删除用户 npm 缓存或结束外部进程。
7. 保留现有 lifecycle 单操作门、generation、取消、Job Object、loopback 身份验证和 WebView2 同源边界。
8. 发布门禁在空缓存构建环境中证明完整运行时可重建，并在无 Node.js、无 npm 缓存的干净 Windows 用户环境完成端到端启动。

### 4.2 非目标

- 不在客户端运行 `npm install -g`、`npx` 或无 lockfile 的 `npm install`。
- 不修改用户或机器 PATH、`.npmrc`、npm registry、代理、证书或全局 npm 缓存。
- 不静默安装系统级 Node.js，不使用管理员权限、系统包管理器、Windows Service 或计划任务。
- 不接受用户提供的包名、版本、registry、tarball URL、Node 路径、任意 Shell 文本或生命周期脚本。
- 不扫描 npm `_npx` 目录并复制未知缓存作为可信运行时。
- 不为修复启动而降低 DSH HTTP 身份标记、loopback、重定向、WebView2 导航或进程所有权限制。
- 不在首期提供 slim/online 安装模式；首期发布包必须包含可离线准备的完整托管运行时。
- 不承诺自动绕过磁盘不足、ACL、杀毒软件隔离、企业应用控制或损坏安装介质；这些情况必须安全失败并给出明确诊断。

## 5. 冻结产品与架构决策

### 5.1 默认启动来源

Auto 模式优先使用 Desktop 托管运行时，不再优先使用用户 PATH 中的全局 `dsh.cmd`，也不再回退到实时 `npx`。全局 DSH 只作为诊断信息展示；需要使用用户自备 DSH 时必须进入现有受控自定义模式，并继续只接受已存在的 `.exe` 或 `.com`，不得把 `.cmd`、`.bat` 或任意命令行加入自定义入口。

该调整按兼容新功能使用 minor 版本：默认 Code 工作流、工作目录、服务地址和 Web UI 能力保持不变，只把不确定的 Auto 解析来源替换为随 Desktop 验证的托管运行时。仍需使用外部 DSH 的用户可以先在外部终端启动并由 Desktop 连接为 `RunningExternal`，或使用已有的受控原生自定义入口；文档必须明确不再自动采用 PATH 中的全局 `dsh.cmd`，不能把这项行为变化隐藏在升级说明中。

托管运行时启动必须使用发布清单中固定的私有 Node 可执行文件和 DSH CLI 入口。优先通过原生 `ProcessStartInfo.ArgumentList` 直接运行私有 `node.exe` 与已验证 CLI 文件；若真实包结构只能使用生成的 `.cmd`，必须扩展 `CmdCommandLineBuilder` 的精确受控模板并覆盖所有转义测试，不能执行拼接 Shell 文本。

### 5.2 发布阶段冻结完整运行时

发布工程必须在隔离目录、空 npm 缓存和固定 Node/npm 工具链中执行 lockfile 驱动的确定性安装，产出完整托管运行时归档。至少包含：

- 固定版本的便携 Node.js LTS x64 运行时。
- 经过验证的 DSH 顶层包和全部传递依赖。
- npm lockfile，所有依赖使用精确版本、resolved 来源和 integrity。
- `dsh-runtime-manifest.json`，记录 schema、runtime id、Desktop 兼容范围、Node/npm/DSH 版本、入口、文件清单、长度、SHA-256 或 SHA-512、总展开大小和文件数量。
- 第三方许可证与 NOTICE 汇总，满足 Node.js 和所有随包分发依赖的许可要求。

发布构建不得依赖开发机已有 `_npx` 缓存。lockfile 中出现未批准 host、git/GitHub 依赖、浮动版本、缺失 integrity、路径依赖、生命周期脚本副作用或 `rc.6`/`rc.7` 非预期混用时必须失败。

### 5.3 发布包形态

首期使用“完整离线运行时”形态：运行时归档作为编译资源嵌入 single-file Desktop EXE，或作为发布 ZIP 中固定名称、固定相对位置的受校验资产。阶段 0 必须通过真实尺寸、single-file 提取行为、杀毒软件误报、启动耗时和许可审计决定二者之一，并同步发布脚本的精确包内容断言。

无论采用嵌入还是 sidecar，用户启动后不得访问 npm 或 GitHub 才能准备 DSH。Desktop 系统自动升级后可携带新的托管运行时，但 DSH 运行时不能独立读取 npm `latest` 后切换。

### 5.4 应用私有存储与原子提交

托管运行时存储在：

```text
%LOCALAPPDATA%\DeepSeekHarnessDesktop\runtime\active.json
%LOCALAPPDATA%\DeepSeekHarnessDesktop\runtime\versions\<runtime-id>\
%LOCALAPPDATA%\DeepSeekHarnessDesktop\runtime\staging\<transaction-id>\
```

该同父目录结构是本需求的冻结口径，取代早期草案中平级 `runtime\<runtime-id>` 与 `runtime-staging\<transaction-id>` 的表达，确保 staging 与 versions 位于同一受控卷和根下。

要求如下：

- `<runtime-id>` 只能来自编译进应用的受信清单，不接受用户或网络输入。
- 归档解析阶段拒绝绝对路径、`..`、冒号/ADS 名称、重复条目和大小/数量超限；解包落盘阶段逐层确认目标父目录与最终文件没有 reparse point，且解析后的绝对路径仍位于固定私有根内。
- 所有字节先写唯一暂存目录，逐文件校验并 flush；全部成功后使用同卷原子 rename/replace 提交。
- 完成标记必须包含 runtime id、清单摘要和成功状态；只有完整标记与文件校验同时通过才可复用。
- 中断、取消或失败只删除当前事务暂存目录；删除前必须再次验证路径位于私有根。
- 保留当前运行时和最多一个上一已验证运行时；清理不能触及活动版本、用户工作目录、npm 缓存、WebView2 或日志。

### 5.5 准备、启动与健康阶段分离

生命周期不得再用单一“正在通过 npx 自动准备并启动 DSH”覆盖全部阶段。至少区分：

1. `EnvironmentPreflight`：检查操作系统、架构、磁盘、私有根和目标工作目录。
2. `RuntimeInspecting`：读取并验证已提交运行时及完成标记。
3. `RuntimeExtracting`：把随包运行时解到唯一暂存目录。
4. `RuntimeVerifying`：校验文件清单、版本和安全属性。
5. `RuntimeCommitting`：原子提交并更新活动指针。
6. `ProcessStarting`：创建私有 Node + DSH Owned 进程并立即加入 Job Object。
7. `ServiceWaiting`：等待端口并执行 DSH HTTP 身份确认。
8. `Running`：已确认并加载 WebView2。

运行时准备期限和 DSH 服务启动期限必须独立。准备阶段基于文件/字节进度设置总期限和无进展 watchdog；服务阶段从 Owned 进程创建后重新计时。测试使用可注入时钟和短期限，不真实等待生产时长。

### 5.6 自动检测、自修复与回退

系统必须自动执行以下恢复顺序：

| 故障 | 自动动作 | 终止条件 |
| --- | --- | --- |
| 无运行时或完成标记缺失 | 从随包受信归档重新解包 | 成功提交或明确准备失败 |
| 暂存事务残留 | 校验私有根后删除残留事务，再重新准备 | 单次清理后仍失败则停止 |
| 活动运行时文件缺失/摘要不符 | 隔离损坏版本，从随包归档重建 | 重建一次 |
| 解包长时间无字节/文件进展 | 取消当前事务、释放句柄、重建一次 | 第二次无进展停止 |
| 新运行时 DSH 立即退出或身份失败 | 停止本次 Owned 树，尝试上一已验证运行时 | 回退最多一次 |
| 上一运行时 manifest 与当前 Desktop 不兼容 | 禁止启动该运行时，记录兼容范围拒绝 | 直接按无可用回退处理 |
| 上一运行时成功 | 标记新运行时故障，保持旧运行时活动 | 不在同一启动周期再次尝试新版本 |
| 当前与上一运行时均失败 | 停止自动循环，保留脱敏诊断 | 等待用户重试或 Desktop 更新 |

自动恢复不得删除未知目录、修改用户全局环境、关闭安全软件、降低 integrity 检查或无限重试。每个启动周期最多一次重建和一次回退，generation 过期、用户取消或应用退出必须立即阻止后续提交。

### 5.7 端口、工作目录与进程所有权

- 工作目录继续通过 `ProcessStartInfo.WorkingDirectory` 传入，必须存在且可访问；托管运行时不能写入工作目录作为安装位置。
- 默认端口被未知服务占用时不得结束该服务。首期可保持 `DSH-E205` 明确失败；若实现自动选端口，必须仅为即将创建的 Owned DSH 选择空闲 loopback 端口，并在状态、配置和 WebView2 中提交同一个确认 URI。
- 只停止当前协调器创建并跟踪的私有 Node + DSH 进程树；上一运行时回退也必须先确认当前 Owned 树完整退出。
- 阶段 0/4 必须验证现有 `Process.Start()` 后再 `AssignProcessToJobObject` 的竞态窗口。若快速派生测试可让子进程在 Job 分配前逃逸，生产启动必须采用 `CREATE_SUSPENDED`、进程创建时 Job 属性或等价的先约束后恢复机制；不能仅以“随后立即 Assign”满足进程树所有权要求。
- 运行时目录不得在其进程仍运行时删除、替换或清理。
- `RunningExternal` 不得因托管运行时准备、修复、清理或回退被停止或重启。

### 5.8 UI、日志与诊断包

主窗口和安装引导必须显示真实阶段，不使用“正在创建进程”描述依赖准备。至少显示阶段、当前进度、阶段耗时、总耗时和是否正在执行自动重建/回退。

建议文案包括：

```text
正在检查托管 DSH 运行时
正在准备随应用提供的 DSH 运行时（245 / 812 个文件）
运行时校验失败，正在自动重建（第 1/1 次）
正在启动 DSH 服务
新运行时启动失败，正在回退上一已验证版本
```

日志必须记录 runtime id、阶段、文件计数/总字节、耗时、错误码、重建/回退结果和 Owned PID，但不得记录文件正文、完整环境变量、凭据、用户 npm 配置或工作目录内文件列表。

失败页提供“重试”“复制诊断摘要”“打开日志目录”和“返回”。诊断摘要必须脱敏且有界，包含 Desktop/运行时/Node/DSH 版本、阶段、错误码、重建/回退次数和最近安全日志；不得自动上传。

### 5.9 DSH 运行时更新策略

DSH 更新采用受控发布：

1. 开发或 CI 选择候选 DSH 版本。
2. 在固定工具链和空缓存中生成精确 lockfile 与完整运行时。
3. 完成许可、完整性、进程、HTTP 身份和 UI 冒烟验证。
4. 随新的 Desktop 版本发布新的 runtime id。
5. 新 Desktop 首次启动准备新运行时；失败时回退上一已验证运行时。

“关于”窗口可以只读显示 npm `latest`，但必须明确“可用上游版本”与“Desktop 当前托管版本”不同。查询结果不得修改 lockfile、活动 runtime id 或启动行为。

## 6. 服务与代码职责边界

实施时优先使用可替换服务，实际名称以届时仓库为准：

- 运行时清单解析与纯校验放在无 I/O 或窄 I/O 的独立组件中。
- `IManagedRuntimeStore` 负责私有根、检查、暂存、原子提交、活动/上一版本和安全清理。
- `IManagedRuntimeProvisioner` 负责编排随包归档解包、进度、完整性和单次重建，不启动 DSH。
- `IDshCommandResolver` 只把已确认运行时转换为结构化启动选项，不负责下载、解包或选择任意命令。
- `HarnessLifecycleCoordinator` 继续负责生命周期串行、generation、Owned 启停、回退编排和状态提交，不直接实现 ZIP 遍历或文件哈希循环。
- `HarnessProcessManager` 继续只管理当前 Owned 进程和 Job Object，不扫描端口后结束 PID。
- ViewModel 只绑定阶段、进度和命令，通过 Dispatcher 更新，不直接访问文件、Process、ZIP 或静态 MessageBox。

持有流、锁、事件、CTS、SemaphoreSlim、Process、Job Object 或后台任务的服务必须实现成对释放。不得在 UI 线程进行解包、哈希或长时间同步文件操作。

## 7. 错误模型

保留已有错误码语义，新增稳定错误码建议如下；最终编号在详细设计中冻结后不得复用：

| 错误码 | 语义 | 自动恢复 |
| --- | --- | --- |
| `DSH-E215` | 迁移期旧 npx 依赖解析停滞诊断 | 仅为历史/迁移兼容预留；0.7.0 Auto 路径不得产生或复用该编号 |
| `DSH-E216` | 随包运行时清单或平台不兼容 | 不重试，要求正确 Desktop 包 |
| `DSH-E217` | 托管运行时准备或原子提交失败 | 清理当前暂存并重建一次 |
| `DSH-E218` | 托管运行时完整性验证失败 | 隔离并从受信归档重建一次 |
| `DSH-E219` | 新运行时失败且没有可用上一版本 | 停止自动循环，允许用户重试 |
| `DSH-E220` | 托管运行时磁盘空间或私有目录权限不足 | 不盲目重试，显示路径和空间建议 |

`UserMessage` 使用简明中文；`TechnicalMessage` 只包含脱敏阶段、异常类型、HRESULT/Win32 code、runtime id 和安全路径摘要。不得把 manifest 原文、代理、Token、完整环境或外部文件内容写入错误。

## 8. 安全与供应链要求

- 固定受信运行时只来自当前 Desktop 发布包，不从用户目录、PATH、npm cache 或网络位置发现。
- manifest schema、runtime id、入口、文件名、长度、哈希和展开上限必须严格验证，未知 schema fail closed。
- 发布阶段验证 lockfile 不含 `git+`、GitHub shorthand、file/path、HTTP 明文、未批准 host、浮动 dist-tag 或缺失 integrity。
- 客户端不执行 npm lifecycle scripts；所有必要脚本只能在隔离发布构建阶段执行并进入产物审计。
- 随包 Node 和 npm 必须有版本更新、CVE 响应和许可证 NOTICE 流程。
- 运行时归档不得包含 npm token、`.npmrc`、开发缓存、日志、测试文件、源码仓库元数据、用户路径或凭据。
- 若发布包尚未采用可信代码签名，manifest 哈希仍用于故障和完整性检测，但不能被文档夸大为抵御已能篡改 EXE 的攻击者；后续与 Desktop 签名更新方案结合。
- 解包和删除必须使用结构化路径 API；所有递归删除前解析并复验绝对路径位于固定私有根。

## 9. 验收标准

### 9.1 确定性与环境独立

- `AC-RUNTIME-DET-001`：同一 Desktop 发布包在上游新增 `rc.7`、`rc.8` 后仍启动清单锁定的完整依赖图。
- `AC-RUNTIME-DET-002`：干净设备未安装 Node.js、npm、npx 或全局 DSH 时，Desktop 可准备并启动 DSH。
- `AC-RUNTIME-DET-003`：设备安装 `Node 24/npm 11`、配置自定义 registry 或存在损坏 npm cache 时，托管运行时行为不受影响。
- `AC-RUNTIME-DET-004`：客户端启动和自修复期间没有 npm/GitHub 网络请求，不执行 npx 或 npm install。
- `AC-RUNTIME-DET-005`：发布构建从空缓存按 lockfile 重建两次；归档条目按规范路径排序、时间戳固定、平台相关元数据规范化，运行时清单和归档达到字节级一致。确实无法消除的字段必须进入明确的规范化比较清单，不能用忽略整个归档替代。

### 9.2 准备与原子性

- `AC-RUNTIME-STORE-001`：不存在运行时时，从随包资产解到暂存、全量校验并原子提交，未完成目录永不成为活动运行时。
- `AC-RUNTIME-STORE-002`：归档条目的绝对路径、`..`、冒号/ADS 名称、重复、大小炸弹、文件数超限和摘要错误均被拒绝；落盘目标父链或文件出现 reparse point 时同样拒绝，任何字节均不写出私有根。
- `AC-RUNTIME-STORE-003`：取消、磁盘不足、进程崩溃和任意文件写入失败后，下次启动能识别并安全清理残留暂存。
- `AC-RUNTIME-STORE-004`：运行时进程存活期间不会删除或替换其目录，停止并确认退出后才允许清理。
- `AC-RUNTIME-STORE-005`：只保留活动与上一已验证运行时，清理范围不包含用户 npm、工作区、WebView2、日志和外部 DSH。

### 9.3 自动修复与回退

- `AC-RUNTIME-RECOVERY-001`：活动运行时缺文件或哈希不符时自动重建一次，用户无需运行命令。
- `AC-RUNTIME-RECOVERY-002`：解包无进展、被占用或中断时取消并重建一次，不无限循环。
- `AC-RUNTIME-RECOVERY-003`：新运行时立即退出、健康超时或身份失败时，先回收其 Owned 树再回退上一已验证运行时。
- `AC-RUNTIME-RECOVERY-004`：回退成功后当前启动周期不再尝试故障版本，并在 UI/日志中明确显示结果。
- `AC-RUNTIME-RECOVERY-005`：当前与上一运行时均失败时停止自动动作，保留诊断与重试入口，不修改全局系统状态。
- `AC-RUNTIME-RECOVERY-006`：用户取消、应用退出、Stop/Restart 和 generation 变化与准备/回退竞态时，过期结果不能提交活动运行时或 Running 状态。
- `AC-RUNTIME-RECOVERY-007`：上一运行时 manifest 声明的 Desktop 兼容范围不包含当前版本时禁止回退启动，并按无可用回退运行时进入 `DSH-E219`。

### 9.4 进程、服务与 UI

- `AC-RUNTIME-PROC-001`：私有 Node + DSH 在创建后立即进入 `KILL_ON_JOB_CLOSE` Job Object，退出 Desktop 不遗留其进程树。
- `AC-RUNTIME-PROC-002`：运行时切换只停止应用拥有的进程；`RunningExternal` 从未被停止、重启、替换目录或接管。
- `AC-RUNTIME-PROC-003`：快速派生子进程的 TestHarness 不能在父进程加入 Job 前逃逸；实现采用经验证的先约束后执行机制，或阶段 0 明确阻塞发布而不是接受已知逃逸窗口。
- `AC-RUNTIME-HEALTH-001`：只有 loopback HTTP 状态、HTML 标题和 DSH 身份标记全部通过后才提交 Running 并加载 WebView2。
- `AC-RUNTIME-UI-001`：环境、检查、解包、校验、提交、进程启动、服务等待、自动重建和回退均有准确阶段与进度。
- `AC-RUNTIME-UI-002`：820x600、100%-200% DPI、键盘和屏幕阅读器下，状态、错误和按钮不重叠、不截断关键错误码。
- `AC-RUNTIME-LOG-001`：诊断摘要足以区分准备、完整性、权限、空间、进程和健康故障，同时不包含凭据、完整环境或外部文件正文。

### 9.5 发布与供应链

- `AC-RUNTIME-REL-001`：发布门禁验证 Node/DSH/依赖版本、lockfile、manifest、许可证、文件清单、哈希、入口和包内容。
- `AC-RUNTIME-REL-002`：lockfile 含浮动版本、未批准 host、git/GitHub/file 依赖、缺 integrity 或未审计 lifecycle script 时发布失败。
- `AC-RUNTIME-REL-003`：Windows 10/11 x64 干净用户、无 Node、无 npm cache、离线客户端准备和第二次复用均通过。
- `AC-RUNTIME-REL-004`：附件中的 `Node 24/npm 11 + rc.6 顶层解析到 rc.7 子依赖` 场景成为回归用例，客户端不会进入 npm idealTree。
- `AC-RUNTIME-REL-005`：发布 ZIP/EXE、仓库和验证报告不包含 npm token、`.npmrc`、用户缓存、日志、配置、凭据或未列明第三方文件。

## 10. 测试要求

### 10.1 单元测试

- manifest schema、版本、runtime id、入口、平台、大小、数量、路径和哈希验证。
- ZIP 条目的路径穿越、绝对路径、冒号/ADS 名称、重复、超限和损坏流；落盘目标父链/文件的 reparse point 单独测试。
- 活动/上一版本选择、完成标记、重建次数、回退次数和清理范围。
- 阶段状态迁移、错误映射、进度节流、取消和 generation 过期。
- 私有 Node/DSH 启动选项、ArgumentList、非默认端口和 Shell 特殊字符。
- ViewModel 命令 CanExecute、Dispatcher 更新、释放后无回调及诊断摘要脱敏。

### 10.2 Windows 集成测试

- 从嵌入/sidecar 运行时归档解包、校验、原子提交和本地 DSH TestHarness 启动。
- 进程立即退出、子孙进程、Job Object 回收、取消和退出竞态。
- 文件占用、只读私有根、磁盘空间替身、写入中断、崩溃残留和下一次恢复。
- 当前运行时失败、上一运行时成功/失败的回退矩阵。
- loopback HTTP 身份、未知服务、重定向、端口占用和健康超时。
- 单实例并发准备，确认只有一个事务写入运行时根。

自动测试不得读取或修改用户真实 `%LOCALAPPDATA%`、npm cache、`.npmrc`、工作区内容或真实 DSH 配置。使用唯一临时根、TestHarness、fake archive/fake file system 或自身创建的真实临时文件，并在 `finally`/Dispose 中清理。

### 10.3 发布与人工验证

- 固定工具链、空 npm 缓存生成完整运行时，记录 lockfile 摘要、运行时摘要、Node/npm/DSH 版本和许可证数量。
- 在完全未安装 Node.js 的 Windows 10/11 x64 新用户运行正式发布包。
- 断网后首次准备成功；第二次启动直接复用且不重复解包全部文件。
- 注入损坏文件、残留 staging、文件锁、权限不足、磁盘不足和杀毒隔离等可控故障。
- 检查 100%、125%、150%、200% DPI、最小窗口、托盘退出和第二实例激活。
- 使用网络监测确认客户端准备/修复不访问 npm 或 GitHub。

## 11. 文档、规则、版本与发布

功能实施必须同步：

- `AGENTS.md` 与 `CLAUDE.md`：托管运行时来源、私有目录、精确依赖、无客户端 npm、删除范围和回退所有权规则，两份保持完全一致。
- `code_rule.md`：删除“自动 npx 使用无版本包名模板”的过期规则，增加 lockfile、运行时归档、解包、完整性、私有 Node 和故障注入规则。
- README、安装说明：新设备无需 Node/npm；说明私有运行时目录、空间占用、自修复、诊断和离线行为。
- 开发与详细设计：服务职责、状态图、目录事务、清单 schema、回退时序、错误码和供应链边界。
- 发布脚本：固定工具链、空缓存构建、许可证、manifest、归档和正式包内容验证。
- `docs/validation/`：新增带日期的阶段验证，不改写历史验证记录。
- 按兼容新功能递增 minor；同步 `Directory.Build.props`、app.manifest 和 `VERSION_HISTORY.md`。

## 12. 完成定义

只有同时满足以下条件，托管运行时能力才可标记完成：

1. 所有 `AC-RUNTIME-*` 有自动化或明确人工证据，并可追踪到开发计划任务。
2. 新设备无需 Node、npm、npx、全局 DSH或任何手动命令即可启动。
3. 完整 DSH 依赖图在发布阶段冻结，客户端不会因上游新增预发布版本改变解析结果。
4. 客户端不执行 npm install/lifecycle scripts，不读取或修改用户 npm 配置和缓存。
5. 准备、校验、启动和健康检查状态分离，`DSH-E203` 不再掩盖运行时准备故障。
6. 损坏、中断和新版本失败可自动重建或回退，且每个启动周期重试有界。
7. 所有路径、解包、完整性、凭据、进程所有权和 loopback 身份安全测试通过。
8. Owned 进程树无残留，External DSH 从未被结束或接管，运行时目录无并发删除。
9. 正式发布门禁从空缓存重建并验证运行时，干净 Windows 离线首次启动通过。
10. 许可证、NOTICE、版本、文档、规则和验证记录与实际发布包一致，仓库不含生成运行时、用户缓存或凭据。
