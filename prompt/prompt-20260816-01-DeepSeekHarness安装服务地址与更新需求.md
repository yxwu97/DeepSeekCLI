# DeepSeek Harness 安装引导、服务地址与更新能力需求 Prompt

## 1. 文档信息

- 文档类型：后续设计与开发执行 Prompt
- 适用项目：DeepSeek Harness Desktop
- 编写日期：2026-08-16
- 需求状态：待实现
- 事实基线：DeepSeek Harness developer preview、npm `latest` 为 `0.1.0-rc.6`

## 2. 使用方式

将本文作为后续设计、实现和验收任务的完整输入。执行者必须先读取当前实现、项目文件、相关测试、`AGENTS.md`、`code_rule.md`、开发文档和详细设计，再根据实际类型与接口实施，不得仅依据本文猜测代码结构。

本需求的目标是：

1. 当当前 Windows 用户尚不具备运行 DeepSeek Harness 的条件时，提供可恢复、可重试的安装引导。
2. 允许用户在 UI 中配置非默认的本机 DeepSeek Harness 服务地址。
3. 基于官方 developer preview 现状提供适度的版本检查能力，同时避免静默升级带来的兼容性风险。

## 3. 官方资料与评估依据

截至 2026-08-16，已核对以下官方资料：

- [DeepSeek Harness 官方 Quick Start](https://deepseek-harness.github.io/deepseek-harness/guide/quickstart)
- [DeepSeek Harness 根 README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md#run)
- [DSH CLI README](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md)
- [npm 官方包](https://www.npmjs.com/package/@deepseek-ai/dsh)

确认事实：

- 官方 npm 运行方式是先安装 Node.js，再执行 `npx @deepseek-ai/dsh web`。
- `npx` 可以按需取得 DSH，因此“PATH 中没有全局 `dsh`”不等于“DeepSeek Harness 未安装或不可运行”。
- Web UI 默认监听 `http://127.0.0.1:3080`，启动命令会输出实际访问地址。
- CLI 文档明确支持把 Web 应用参数放在 profile 参数之后，例如 `dsh --profile web --port 8080`。
- DSH 仍处于 developer preview，官方明确提示后续会出现破坏性变更。
- npm 官方注册表在核对时的 `latest` 与 `next` 均为 `0.1.0-rc.6`；当前桌面宿主固定的也是 `0.1.0-rc.6`。

据此作出产品决策：

| 能力 | 本期结论 | 原因 |
| --- | --- | --- |
| 安装引导 | 需要 | 官方运行依赖 Node.js 和 npx，首次下载还依赖 npm 网络，失败类型需要被清楚区分 |
| 自定义服务地址 | 需要 | `3080` 是默认值而不是协议常量，CLI 也允许自定义端口 |
| 手动检查 DSH 更新 | 需要 | developer preview 迭代快，用户需要看见当前版本和可用版本 |
| 后台自动检查 | 暂不需要 | 会引入启动延迟、网络策略、隐私提示和噪声，且不是核心启动路径 |
| 静默或随启动自动升级 | 禁止 | 破坏可复现启动，且新预览版可能与身份特征、参数或 Web UI 不兼容 |
| 任意版本一键升级 | 暂缓 | 必须先具备桌面端兼容版本清单、升级失败回退和针对新版本的验证记录 |

## 4. 必须遵守的边界

1. 桌面宿主只负责运行和承载官方 Web UI，不复制会话、模型、工具、审批、工作区或模型设置界面。
2. 不自动全局安装 Node.js、npm 或 `@deepseek-ai/dsh`，不调用包管理器修改系统级安装。
3. 不运行来自用户输入的 Shell 文本。npm 回退继续使用程序内置、固定且可审计的参数；`.cmd` 继续走 `CmdCommandLineBuilder`。
4. 默认和自定义服务地址本期都只能是绝对的 loopback `http/https` URI，不带用户名或密码。允许的典型地址包括 `http://127.0.0.1:8080/`、`http://localhost:3080/` 和 `http://[::1]:3080/`。
5. 不因本需求直接开放局域网或远程地址。若业务确实需要 `192.168.x.x`、域名或公网地址，必须另立安全需求，补充 TLS、认证、来源信任、导航隔离和凭据泄露威胁模型后再评审。
6. 地址可访问不代表它是 DSH。连接或导航前继续校验 HTTP 响应、HTML 特征和 DSH 身份标记。
7. 外部实例只允许连接和刷新；停止、重启仍只适用于当前桌面应用创建并跟踪的进程。
8. 所有外部输出在进入 UI 日志前必须规范化、限长和脱敏；不得记录 npm 凭据、代理凭据、Token、Cookie 或完整环境变量。

## 5. 功能需求

### 5.1 启动诊断与安装引导

#### 5.1.1 诊断语义

应用启动时应复用或扩展现有依赖诊断，至少区分以下结果，不能只返回笼统的“未安装 DeepSeek”：

| 诊断结果 | 判定示例 | 后续动作 |
| --- | --- | --- |
| 已有可信 DSH 服务 | 配置地址通过健康检查与身份确认 | 直接连接为 `RunningExternal` |
| 全局 DSH 可用 | PATH 中解析到受支持的 `dsh` 启动入口 | 正常启动流程 |
| npx 可用、DSH 需首次下载或缓存状态未知 | Node.js 与 npx 可用，但没有可依赖的全局 DSH | 进入“准备 DSH”步骤，明确可能联网下载 |
| Node.js 或 npx 缺失 | 普通用户环境无法解析或运行 `node`/`npx` | 进入 Node.js 安装指导步骤 |
| 环境存在但版本或执行异常 | 命令存在但无法运行、版本不兼容或返回异常 | 显示具体诊断和修复建议 |
| npm 下载失败 | DNS、代理、TLS、registry、超时或权限错误 | 保留脱敏摘要，允许重试和打开日志 |

不得扫描或硬编码 npm `_npx` 缓存哈希目录。是否可运行应通过公开命令入口与受控启动结果判断。

#### 5.1.2 引导入口

- 自动启动诊断发现 Node.js/npx 缺失时，主内容区进入安装引导状态，而不是直接停留在通用失败页。
- `DSH-E101` 等相关错误页提供“打开安装引导”命令。
- 停止状态或设置中提供“重新检查运行环境”命令，便于安装完成后继续，不要求用户删除配置。
- 用户可以退出引导并返回停止状态；取消不能残留后台进程、等待任务或失效的命令状态。

#### 5.1.3 引导步骤

引导至少包含以下步骤，步骤状态由 ViewModel 驱动，View code-behind 只处理系统 UI 桥接：

1. **环境检查**：显示 Node.js、npx、DSH 启动入口和 WebView2 的检查结果；版本只显示安全、限长的值。
2. **安装 Node.js**：说明 DSH 官方前置条件；提供“打开 Node.js 官方下载页”和“重新检查”按钮。链接交给系统浏览器，桌面应用不代替用户下载、运行安装程序或提升权限。
3. **准备 DeepSeek Harness**：明确告知首次启动会执行固定版本的 `npx -y @deepseek-ai/dsh@<verified-version> web`，可能访问 npm registry 并写入当前用户 npm 缓存。只有用户点击“下载并启动”后才发起该网络和进程操作。
4. **启动与验证**：复用正式生命周期协调器启动进程、解析输出地址、执行身份检查，并在成功后进入官方 Web UI。不得另写一条绕过状态机和进程所有权的安装专用启动链路。

“安装 DSH”在 UI 文案中应解释为“通过 npx 下载到当前用户缓存并启动固定版本”，不得暗示已完成全局安装。

#### 5.1.4 失败与恢复

- Node.js 安装后若当前进程尚未获得新 PATH，UI 应提示重新检查或重启桌面应用，不得误报安装失败。
- npx 执行期间应显示阶段和经过脱敏、限长的实时日志；取消操作必须终止当前应用拥有的整个子进程树。
- 下载失败后保留“重试”“打开日志”“返回上一步”操作。
- 应将缺少依赖、网络失败、命令异常、服务身份不匹配和端口占用映射为不同的稳定错误码或现有错误码语义；不得无迁移地改变已有错误码含义。
- 引导重入、连续点击、关闭窗口、取消和应用退出均不得产生并行安装/启动操作。

### 5.2 自定义服务地址

#### 5.2.1 设置界面

新增或完善设置入口，至少包含：

- “服务地址”输入框，默认值为 `http://127.0.0.1:3080/`。
- “测试连接”命令：不保存配置，先验证 URI，再执行 DSH 身份探测并显示明确结果。
- “保存”命令：只保存格式和安全边界均合法的值。
- “恢复默认值”命令。
- 简明错误提示，区分格式错误、非本机地址、无法访问、远程重定向和服务身份不匹配。

地址应使用结构化 `Uri` 解析和规范化，禁止通过字符串拼接判断 origin、host 或端口。允许省略末尾 `/`，保存时规范化为一致形式。

#### 5.2.2 应用规则

- 应用初始化、启动前探测、健康监控和 WebView2 导航都使用已保存的服务地址，不得在其他层重新硬编码 `3080`。
- 如果配置地址已经运行可信 DSH，连接为外部实例，不再创建新进程。
- 如果桌面应用要创建 owned DSH，且配置使用非默认端口，应通过安全的数值端口参数让启动端口与配置一致。参数使用 `ProcessStartInfo.ArgumentList`，或在固定 `.cmd` 模板中由程序生成；用户输入不得直接进入 Shell。
- DSH 输出的实际 loopback 地址仍可更新候选地址，但必须经过身份检查后才能成为当前服务地址或导航目标。
- owned DSH 正在运行时修改地址，不得直接让状态与实际进程脱节。保存前应提示需要重启；只有用户确认后才能走现有串行重启流程。
- external DSH 连接期间切换地址时，先探测新地址；探测失败则保留原连接和原配置。
- 配置继续通过临时文件、替换和备份策略保存。若字段结构发生变化，递增 `SchemaVersion` 并覆盖旧配置迁移测试。

#### 5.2.3 地址范围示例

| 输入 | 结果 |
| --- | --- |
| `http://127.0.0.1:43124` | 接受并规范化 |
| `http://localhost:3080/` | 接受 |
| `http://[::1]:8080/` | 接受 |
| `https://localhost:3443/` | 格式上接受，但仍需通过证书、健康与身份检查 |
| `http://user:pass@localhost:3080/` | 拒绝 |
| `file:///...`、`javascript:...` | 拒绝 |
| `http://192.168.1.20:3080/` | 本期拒绝，并说明只支持本机服务 |
| `https://example.com/` | 拒绝 |

### 5.3 DeepSeek Harness 更新能力

#### 5.3.1 本期实现范围

实现“手动检查更新”，不实现“自动升级”：

- 在设置或关于窗口显示桌面当前验证的 DSH 版本。
- 提供“检查 DSH 更新”命令，用户触发后才访问 npm 官方注册表查询 `@deepseek-ai/dsh` 的 `latest` dist-tag。
- 使用支持 prerelease 的语义化版本比较，不能按普通字符串比较 `rc` 版本。
- 显示当前版本、最新发布版本、检查时间和结果状态。
- 当前版本已是最新时显示“已是当前验证版本”。
- 发现更新时明确提示：DSH 处于 developer preview，新版可能包含破坏性变更；提供官方仓库/文档入口，但不自动修改固定启动版本、不执行 npm 全局安装。
- 网络、代理、registry、TLS 或响应格式异常时，检查失败不能影响 DSH 的现有启动与使用。

更新查询服务应可替换、可取消、设置合理超时，并只解析所需的包版本字段。响应内容不得直接作为富文本或可执行内容呈现。

#### 5.3.2 后续一键更新的准入条件

只有同时满足以下条件，才能另行实现“下载并切换版本”：

1. 仓库中存在显式兼容版本清单，记录 Desktop 版本、DSH 版本、启动参数、身份标记和验证日期。
2. 新 DSH 版本已通过真实启动、停止、进程树回收、端口参数、身份探测、WebView2 导航和核心 UI 冒烟验证。
3. 更新操作由用户明确触发并确认，不修改全局 npm 包。
4. 保留原固定版本；新版本启动或身份验证失败时，可以自动回到原版本。
5. 更新、回退和取消继续受生命周期单操作门、generation 和进程所有权约束。
6. 有明确、可信的官方版本来源；若官方没有可用变更日志，UI 不得编造更新内容。

在上述条件满足前，界面不得提供看似可执行但实际会把固定版本改成 npm `latest` 的“立即更新”按钮。

## 6. 交互与文案要求

- 用户提示使用简明中文，避免把 npm 缓存称为系统级安装。
- 按钮名称使用明确命令，例如“打开 Node.js 下载页”“重新检查”“下载并启动”“测试连接”“恢复默认值”“检查 DSH 更新”。
- 长时间操作必须有进行中、成功、失败和已取消状态；进行中禁止重复提交。
- 安装引导和设置界面支持键盘焦点顺序，窗口在 125%/150% DPI 下不裁切按钮、地址和错误文本。
- 不在 UI 中展示完整命令环境、registry 凭据、代理密码或未经处理的 stderr。

## 7. 验收标准

### 7.1 安装引导

- `AC-INSTALL-001`：Node.js/npx 均缺失时，启动后进入安装引导并显示官方 Node.js 下载入口。
- `AC-INSTALL-002`：只有全局 `dsh` 缺失但 npx 可用时，不误判为必须全局安装，用户可以通过固定版本 npx 继续。
- `AC-INSTALL-003`：用户未点击“下载并启动”前，不发起 DSH 包下载或安装命令。
- `AC-INSTALL-004`：首次 npx 下载成功后复用正式启动流程进入 `RunningOwned`，进程属于 Job Object。
- `AC-INSTALL-005`：下载失败、取消或窗口关闭不会遗留 owned 子进程树，用户可以重试。
- `AC-INSTALL-006`：所有外部输出进入 UI 和文件日志前满足限长与脱敏要求。

### 7.2 服务地址

- `AC-URI-001`：用户可保存并连接任意合法 loopback 端口，而非只能使用 `3080`。
- `AC-URI-002`：非 loopback、带用户信息或非 HTTP(S) 地址在保存和导航前被拒绝。
- `AC-URI-003`：未知 HTTP 服务即使返回 2xx，也不能被当作 DSH 或加载进 WebView2。
- `AC-URI-004`：已确认的外部 DSH 显示为 `RunningExternal`，停止和重启不可用。
- `AC-URI-005`：owned DSH 使用非默认端口时，启动参数、健康探测、状态快照和 WebView2 地址一致。
- `AC-URI-006`：切换到无效地址失败时，原有可用配置与连接不丢失。

### 7.3 更新检查

- `AC-UPDATE-001`：用户可手动查询 npm 官方注册表并看到当前验证版本与 `latest` 版本。
- `AC-UPDATE-002`：`0.1.0-rc.10` 等 prerelease 版本按 SemVer 正确比较，不按字典序比较。
- `AC-UPDATE-003`：查询失败不会改变固定 DSH 版本、配置、运行状态或现有连接。
- `AC-UPDATE-004`：发现新版时只提示和提供官方资料入口，不静默下载、不全局安装、不自动切换版本。
- `AC-UPDATE-005`：检查请求可取消、超时可控，连续点击不会产生并发请求。

## 8. 测试要求

- 为依赖诊断、URI 规范化、loopback 校验、端口参数、SemVer 比较和更新响应解析补充单元测试。
- 为安装引导 ViewModel 覆盖命令可用性、步骤迁移、取消、重试和过期异步结果丢弃。
- 通过替身命令解析器与本地假 registry/HTTP 服务测试成功、超时、错误响应、身份不匹配和重定向；自动化测试不得修改开发机的 Node.js 或全局 npm 包。
- 为 owned DSH 非默认端口、取消首次下载和进程树回收补充 Windows 集成测试。
- 为设置保存/恢复、旧配置兼容和原子写入失败补充测试。
- 手工检查 WPF 安装引导、设置窗口和错误文本在 100%、125%、150% DPI 下的布局、焦点与取消行为。

## 9. 非目标

- 不制作 Node.js 或 DSH 的自有安装包。
- 不自动提升为管理员权限，不调用 `winget`、Chocolatey 或系统安装器完成静默安装。
- 不支持远程 DSH、局域网 DSH 或公网 DSH。
- 不自动更新 DeepSeek Harness Desktop 本身。
- 不在桌面宿主中实现模型/API Key 安装向导；DSH 启动成功后的模型配置继续由官方 Web UI 提供。

## 10. 执行与交付要求

执行者应先提交设计影响分析，再完成实现、测试和文档同步。交付至少包括：

1. 安装引导与依赖诊断的模型、服务、ViewModel 和 WPF 视图。
2. 服务地址设置、测试连接、保存、应用与非默认端口启动闭环。
3. 可替换的 npm 版本查询服务和手动更新检查 UI。
4. 对应单元测试、Windows 集成测试与手工 UI 验证记录。
5. 与实际行为一致的开发文档、详细设计、安装说明和错误码说明。
6. 按仓库规则更新版本号、manifest 与 `VERSION_HISTORY.md`，并保持 `AGENTS.md` 和 `CLAUDE.md` 完全一致。

实现完成后运行与风险匹配的验证，至少包括 restore、Debug build、Release tests；涉及真实进程和网络探测时运行 IntegrationTests，发布前运行 `eng/Verify-Release.ps1`。不得以仅编译成功作为验收结论。
