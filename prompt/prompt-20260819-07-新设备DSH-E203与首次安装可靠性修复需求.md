## 2. 使用方式与优先级

后续设计、开发、测试和验收必须先读取当前实现、相关测试、`AGENTS.md`、`CLAUDE.md`、`code_rule.md`、本 Prompt、关联 Plan、开发文档、详细设计和最新验证记录，再依据真实接口实施。

本文聚焦当前轻量发布架构，不恢复把 Node、DSH 或 npm 缓存塞进发布 ZIP 的大体积托管运行时方案。若本文与较早的托管运行时 Prompt/Plan 冲突，仅在本次轻量发布、现有安装复用和首次在线准备路径上以本文为准；进程所有权、Job Object、生命周期串行、loopback 身份校验、WebView2 同源限制、日志脱敏和版本政策继续遵守当前仓库规则。

不得仅依据错误码名称猜测根因。`DSH-E203` 是最终表现，首次 npm 准备停滞、DSH 已启动但健康探测被代理影响、服务未监听目标地址等都可能落入该错误。实现前必须通过可重复证据区分阶段。

## 3. 已确认事实

### 3.1 用户现场

- 在一台新设备上，当前轻量 Release 首次启动仍出现 `DSH-E203`。
- 另有一台机器通过手工执行 `npm install -g @deepseek-ai/dsh@0.1.0-rc.6` 安装成功；截至本文本次修订，尚未取得该机器的 Node/npm 版本、registry、cache 状态、安装耗时和规范化依赖图，因此还没有完成与失败空缓存 npx 的一对一比较。
- 较早版本安装引导曾提供“手动安装与启动”区域、复制固定 npx 命令、打开 PowerShell 和 npm 包页面；当前 `InstallationGuideViewModel`/XAML 已移除这些入口，但 `ITerminalLauncher` 及 DI 注册仍存在。用户明确要求手动路径必须保留，不能被新的自动准备方案删除。
- 已安装或已有合格 `_npx` 缓存的设备可以直接启动，说明“复用已有入口”和“全新设备首次准备”是两个不同场景。
- 用户要求应用保持轻量：只负责检查环境、复用已有 DSH，并在确实缺失时逐步安装；不能每次启动重复下载，也不能重新产生 160 MiB 级发布程序。

### 3.2 当前代码路径

1. Auto 依次解析 PATH 中的 `dsh.cmd`、经严格校验的固定版本 `_npx` 缓存、PATH 中的 `npx.cmd`。
2. 缓存命中后使用 PATH 中的 `node.exe` 直接执行固定 `lib/bin.js`，不访问 registry。
3. 无可复用入口时，在用户确认后执行：

   ```text
   npx -y @deepseek-ai/dsh@0.1.0-rc.6 web [--port <数字>]
   ```

4. npx 准备和 DSH HTTP 就绪共用 `StartupTimeoutSeconds`，默认最长 300 秒。
5. `NpmFailureClassifier` 只在 npx 进程退出后根据 stderr 分类 DNS、TLS、registry 和权限错误；进程不退出时无法分类。
6. 等待期结束但 HTTP 身份未确认时，生命周期统一映射为 `DSH-E203`。
7. `HarnessHealthMonitor` 的默认 `HttpClientHandler` 禁用了自动重定向和 Cookie，但当前没有显式禁用系统代理；它实际只访问已验证的 loopback 地址。

### 3.3 本轮隔离空缓存复现

2026-08-18 在开发机使用独立 npm cache 执行与产品相同的固定版本命令，环境为 Node `24.15.0`、npm/npx `11.12.1`，registry 为当前机器配置的 npm 镜像。观察结果：

- 空缓存开始写入，约两分钟后已有约 10 MiB、数百个文件。
- npx/node 进程仍存活并持续消耗 CPU。
- 标准输出和标准错误没有提供可供 Desktop 展示的阶段进度。
- 测试端口没有进入监听状态，DSH HTTP 服务尚未启动。
- 测试由执行者主动取消，相关进程和监听已清理。
- 缓存内容显示顶层包为固定 `dsh@0.1.0-rc.6`，但大量 `@deepseek-ai/*` 传递包解析为 `0.1.0-rc.7`。

该结果与历史 `prompt-20260817-05` 记录的 `idealTree` 停滞模型一致：固定顶层版本并不等于固定完整传递依赖图。它足以证明当前空缓存路径不具备可重复可靠性，但不能单独证明用户设备的每一次 `DSH-E203` 都由同一因素造成。

手工全局安装成功也不能反证上述结论。`npm install -g` 与 npx 都可能根据当时 registry 元数据解析范围型传递依赖，但二者的目标目录、现有依赖树、cache 利用方式、npm 安装上下文和可等待时间不同。只有取得成功机器的环境与实际依赖图，并与“成功既有 `_npx` 缓存”“失败空缓存 npx”做三方比较后，才能判断成功来自命令形态还是环境差异；在此之前不得直接把产品回退改成全局安装。

### 3.4 已确认问题分层

| 层次 | 当前问题 | 结论 |
| --- | --- | --- |
| 发现 | 已有全局或合格缓存时能够复用 | 继续保留，并补真实回归 |
| 首次准备 | npx 每次根据当时 registry 元数据解析传递依赖 | 主要架构缺陷，不能靠固定顶层版本解决 |
| 进度 | npm 长时间无 stdout/stderr 时 UI 无法说明当前阶段 | 必须增加阶段与停滞诊断 |
| 超时 | 安装准备与 HTTP 服务就绪共用一个期限 | 必须拆分并准确归类 |
| 健康探测 | loopback 请求仍可能继承系统代理 | 独立风险，需显式旁路并测试 |
| 错误语义 | npx 未退出的准备停滞最终变成 `DSH-E203` | 错误语义不准确 |

## 4. 根因与约束结论

### 4.1 主要根因

当前首次启动把 `npx -y <顶层固定版本>` 当作可重复安装器，但 npx 仍会在线解析完整传递依赖图。上游范围依赖或 registry 元数据变化后，即使 Desktop 代码和顶层包版本不变，新设备得到的依赖组合也可能不同，并可能在 npm 解析或落盘阶段长时间停滞。

因此以下做法不能关闭本缺陷：

- 只把 300 秒改成更长时间。
- 只增加更多 stderr 关键字。
- 只固定顶层 `@deepseek-ai/dsh@0.1.0-rc.6`。
- 继续用开发机已有 `_npx` 缓存做唯一真实 smoke。
- 把 npx 的准备阶段仍然归为“DSH 服务启动”。

### 4.2 独立风险

loopback 健康检查继承系统代理可能在部分新设备、企业代理或错误代理配置下造成误判。由于健康客户端只允许访问经过 `ServiceUriValidator` 验证的 loopback 地址，默认处理器应显式 `UseProxy = false`。该修复不能替代首次安装修复，也不能在没有证据时宣称它是本次用户现场的唯一根因。

## 5. 产品目标

1. 发布 ZIP 和主 EXE 保持轻量，不携带 CoreCLR、Node、npm、npx、DSH 依赖目录或用户缓存。
2. 每次启动先检查并复用已有可用 DSH；已有安装不得触发下载、安装或 registry 访问。
3. 只有所有受支持的复用来源都不存在时，才向用户明确说明下载内容、目标位置和预计磁盘占用，并取得一次确认。
4. 首次在线准备使用发布时冻结且经过真实验证的完整依赖图，不在用户设备重新解析漂移的传递依赖版本。
5. 首次准备成功后持久化为当前用户安装，后续启动直接复用，不重复下载。
6. 把“环境检查”“下载/安装”“创建 DSH 进程”“等待 HTTP 身份”分成可观察阶段和独立期限。
7. `DSH-E203` 只表示 DSH 进程已进入服务启动阶段，但未在服务期限内通过身份检查；安装停滞不得再使用该错误码。
8. loopback 健康检查不经过系统代理，并继续执行状态、HTML、身份标记和重定向边界验证。
9. 在 Windows 10/11 x64 新用户环境完成真实 Release 首次安装、二次免下载启动和清理验证。
10. 恢复并长期保留手动安装/启动入口：用户可以选择固定版本全局安装，也可以沿用旧版固定 npx 手动启动；自动准备失败不能阻断手动路径。

## 6. 非目标

- 不在本需求中自动安装 Node.js、WebView2 或修改系统 PATH。
- Desktop 不自动执行全局 `npm install -g`，不要求管理员权限，不修改用户全局 npm 配置；但必须保留由用户主动复制并在可见终端中执行固定全局安装命令的手动路径。
- 不接受用户提供的包名、版本、registry 参数、npm 参数或任意 Shell 文本。
- 不把整个 DSH 依赖目录打进发布 ZIP 或 EXE。
- 不删除对全局 `dsh.cmd` 和既有严格 `_npx` 缓存的复用支持。
- 不因端口被占用而结束外部进程，不改变 `RunningExternal` 的只连接语义。
- 不降低 DSH HTTP 身份校验，不因解决代理问题而允许远程地址。
- 不以模拟测试代替空缓存联网验证和新设备验证。

## 7. 冻结方案

### 7.1 Auto 解析顺序

Auto 启动按以下顺序处理，命中后立即停止后续发现：

1. 已确认的 loopback 外部 DSH：进入 `RunningExternal`，不创建或停止任何外部进程。
2. PATH 中可执行的全局 `dsh.cmd`。
3. Desktop 当前用户私有安装根中已完成、版本匹配且入口校验通过的 DSH。
4. 当前用户标准 npm `_npx` 根中经固定包名、版本、bin 和入口校验的 DSH。
5. 以上均不存在时，进入带用户确认的首次在线准备。

发现流程不得访问 registry，不得执行 npm，不得把目录存在直接当成可用。私有安装或 `_npx` 候选损坏时记录有界脱敏原因，继续检查其他候选；不得在普通启动中原地覆盖一个正在被 Owned 进程使用的目录。

### 7.2 手动安装与启动兼容路径

安装引导必须保留可展开的“手动安装与启动”区域，并提供两类固定操作：

1. 持久全局安装：复制 `npm install -g @deepseek-ai/dsh@0.1.0-rc.6`，在当前工作目录打开可见 PowerShell；用户执行完成后点击“重新检查”，Desktop 刷新系统与用户 PATH，发现 `dsh.cmd` 后直接复用，不再下载或迁移。
2. 临时手动启动：保留旧版 `npx @deepseek-ai/dsh@0.1.0-rc.6 web` 固定命令和 npm 包页面入口；用户在可见终端启动并保持运行后，Desktop 通过 loopback 身份检查将其作为 `RunningExternal` 连接，退出 Desktop 时不得停止该外部进程。

Desktop 只允许复制上述代码内固定命令、打开 PowerShell 和官方 npm 页面，不自动向终端粘贴、发送按键或执行命令，不接受用户包名、版本、registry、端口或 Shell 参数。手动区域必须明确区分“全局安装后由 Desktop 启动”和“终端内临时启动外部服务”，避免把两种所有权语义混淆。

手动路径与自动锁定准备并存：用户可以在自动准备前选择手动方式，也可以在 `DSH-E211` 至 `DSH-E214`、`DSH-E221` 后改用手动方式。重新检查一旦发现可用全局 DSH，必须优先复用并停止显示下载提示。不得强制把用户全局安装复制、迁移或重装到 Desktop 私有根。

### 7.3 轻量、锁定、一次性的在线准备

正式发布包只携带小型安装描述和精确 lockfile，不携带 Node 或 `node_modules`。首次准备使用 PATH 中已验证的 Node/npm，在当前用户私有根的唯一 staging 目录执行锁定安装，建议固定结构：

```text
%LOCALAPPDATA%\DeepSeekHarnessDesktop\dsh\
  active.json
  versions\<install-id>\
  staging\<transaction-id>\
```

实施前阶段 0 必须用真实 npm 版本验证最终命令形态。目标语义是等价于基于发布内精确 `package-lock.json` 的 `npm ci --omit=dev`，禁止回退到 `npx -y <包规格>` 或无 lockfile 的 `npm install`。lockfile 必须固定所有包版本、来源和 integrity；更新 lockfile 必须走代码审查和空缓存真实 smoke。阶段 0 同时覆盖 npm 官方 registry 与至少一个受控镜像环境，记录 lockfile `resolved`、npm 的 registry host 替换行为和实际请求 host，证明两类环境都保持相同 integrity 与依赖图；不得在客户端动态改写 lockfile 或接受用户输入的 registry 参数。

安装流程必须：

1. 在 staging 写入受信的固定 `package.json` 和 lockfile。
2. 使用安装专用的受控 `.cmd` command builder 和精确参数 allowlist 启动 npm；工作目录通过 `WorkingDirectory` 传递。可以在严格测试后扩展现有 `CmdCommandLineBuilder`，但优先使用职责单一的安装 builder，禁止增加可接受任意 npm 参数的通用入口。
3. 对下载/安装设置独立、有限的准备期限和无进展期限。两者由代码常量定义，并由阶段 0 的真实空缓存数据冻结；本需求不增加用户设置字段，不触发 `SchemaVersion` 迁移。
4. 安装完成后校验固定顶层包版本、固定入口、lockfile 一致性和真实 DSH smoke。
5. 通过临时文件和同卷原子替换提交 `active.json`。
6. 只有成功提交后才作为可复用安装；失败或取消不得污染活动版本。
7. 二次启动直接使用 `node.exe <固定入口> web`，不运行 npm/npx，不访问 registry。

安装依赖在 `%LOCALAPPDATA%` 占用的磁盘空间必须在确认框和安装文档中如实说明。发布包体积与安装后的 DSH 依赖占用是两个不同指标，禁止用隐藏磁盘占用换取“轻量”宣传。

### 7.4 安装进程与 DSH 进程边界

- npm 安装进程是 Desktop 创建并跟踪的 Owned 准备进程，同样必须纳入 Job Object 或等效的完整进程树回收边界。
- 安装取消、超时或应用退出时，只停止本次 Desktop 创建的安装进程树。
- DSH 服务进程只在安装成功并完成入口校验后创建。
- 安装进程和 DSH 服务进程必须具有不同阶段、日志和超时，不能用一个 PID 或一个状态文本混淆。
- 不因安装失败删除私有根；只清理经路径验证、属于本次事务且未激活的 staging。

### 7.5 进度和停滞判断

npm 不保证持续输出，因此不能仅以“是否有新日志行”判断是否存活。准备服务至少综合记录：

- 阶段开始和结束时间。
- npm 进程是否存活及退出码。
- staging 中有界的文件数/字节数变化或其他不读取文件正文的进展信号。
- 最近一次进展时间。
- 已用时间、准备总期限和无进展期限。

扫描必须节流、可取消并限制目录范围，不在 UI 线程执行。日志只记录汇总值，不记录全部文件名、registry 凭据、`.npmrc` 内容或完整环境变量。

### 7.6 健康探测

- `HarnessHealthMonitor` 默认 handler 对 loopback 请求显式设置 `UseProxy = false`。
- 自定义注入 `HttpClient` 的测试和调用保持现有可替换能力。
- 不修改 `ServiceUriValidator` 允许范围；每次重定向继续重新验证 loopback。
- HTTP 状态、HTML 类型、256 KiB 上限、标题和 `window.__DSH_BOOT__` 双特征继续保留。
- 代理旁路需要自动测试证明，不以开发机默认 `NO_PROXY` 或代理配置作为通过条件。

### 7.7 错误码与用户提示

保持现有错误语义：

| 错误码 | 语义 |
| --- | --- |
| `DSH-E203` | DSH 服务进程已启动，但在服务就绪期限内未通过 HTTP 身份检查 |
| `DSH-E211` | npm DNS/网络连接失败 |
| `DSH-E212` | npm TLS、证书或代理安全连接失败 |
| `DSH-E213` | registry 拒绝请求、包不存在或完整依赖来源不可用 |
| `DSH-E214` | npm 缓存、staging 或私有安装目录权限不足 |

新增 `DSH-E221` 表示“DSH 下载或安装在准备期限内未完成或达到无进展期限”。它必须可重试，用户提示需明确当前失败在安装阶段，并建议检查网络、npm registry 和日志。不得复用历史 `DSH-E215`，也不得改变 `DSH-E203` 的既有服务超时语义。

未知 npm 非零退出继续映射为可诊断的安装失败，技术信息包含脱敏退出码和阶段摘要，不回显完整命令环境。安装成功但 DSH 立即退出仍按现有 `DSH-E201` 及 npm/进程分类处理。

## 8. 状态、并发与职责

- 新增独立安装服务抽象，负责私有安装发现、锁定准备、校验和原子提交；ViewModel 不直接启动 npm 或访问文件系统。
- 提取统一候选发现结果，由 `DependencyDiagnosticsService` 与 `DshCommandResolver` 共同消费；不得继续各自实现全局 DSH、私有安装和 `_npx` 缓存的不同发现顺序。
- `DependencyDiagnosticsResult` 必须表达 DSH 的实际来源和是否需要首次准备，不能再把“Node 与 npx 可用”等同于“DSH 已安装”。
- `DshCommandResolver` 只返回已可执行的 DSH 启动选项，不在解析器中执行长时间安装。
- `HarnessLifecycleCoordinator` 继续保留单操作门、取消令牌和 generation；安装结果提交和 DSH 启动前均检查当前 operation。
- `HarnessLifecycleCoordinator.RequiresInteractivePreparationAsync`、`InstallationGuideViewModel.ContinueAsync` 和主窗口启动/打开引导的判定必须统一改为消费明确的候选/准备结果，不再通过“可执行文件是否为 npx.cmd”或 `HasInstalledDsh` 间接猜测。
- `HarnessProcessManager` 继续只管理当前 Owned DSH；安装进程若使用独立 runner，必须拥有等价的 Job Object、输出、取消和 Dispose 保障，不能与 DSH 当前进程引用互相覆盖。
- `HarnessStateMachine` 是否增加明确准备事件由实现阶段依据状态图决定，但禁止从 `Stopped` 直接拼装 `RunningOwned`。
- 用户重复点击、自动启动和手动启动竞争时只允许一个准备事务和一个 DSH 启动事务。
- 成功提交的私有安装在进程退出后继续保留；只有明确版本升级、损坏恢复或用户发起清理时才改变活动指针。
- `LaunchMode.Custom` 继续只接受现有 `.exe/.com` 规则，跳过 Auto 候选发现和在线准备；本需求不得改变 Custom 参数、确认或生命周期语义。
- `InstallationGuideViewModel` 恢复固定手动命令、复制、打开 PowerShell 和 npm 官方页面命令；`ITerminalLauncher` 继续只打开可见终端，不拥有或跟踪用户随后创建的进程。

## 9. 测试要求

### 9.1 先失败后修复

在修改生产实现前，先建立以下可重复失败证据：

1. 空缓存、无全局 DSH、无私有安装时，旧路径会进入动态 npx 解析。
2. npx 进程保持存活但没有 HTTP 服务时，旧路径最终错误为 `DSH-E203`。
3. 配置一个会截获 HTTP 的代理时，旧默认健康 handler 没有明确旁路代理。
4. 已有合格 `_npx` 缓存时不会调用 npx；该测试必须继续通过。

### 9.2 单元测试

- 解析优先级：外部/全局/私有安装/严格 `_npx` 缓存/首次准备。
- 统一发现结果被 resolver、依赖诊断和安装引导一致解释；诊断状态需区分“已安装可启动”“具备安装条件”和“需要首次准备”。
- 私有安装 manifest、active 指针、固定包版本、入口、reparse point 和路径穿越拒绝。
- lockfile/安装描述资源缺失、损坏或版本不一致时 fail closed。
- 安装专用 `.cmd` builder 只接受冻结的 npm ci 参数；覆盖空格、引号、中文路径及 `& | < > ^ % ! ( )` 拒绝/转义边界。
- 安装阶段与服务阶段的错误映射，特别是 `DSH-E221` 与 `DSH-E203` 不混淆。
- npm DNS、TLS、registry、权限、未知退出和无进展分类。
- 重复启动、取消、过期 generation、原子提交前失败和已激活版本复用。
- `LaunchMode.Custom` 不触发私有安装、npm、npx 或下载确认，并继续拒绝 `.cmd/.bat` 自定义入口。
- 固定全局安装和旧版手动 npx 命令文本不可由用户修改；复制内容、按钮可用性、打开 PowerShell 不自动执行、重新检查后全局 DSH 优先均有测试。
- 手动 npx 启动的真实服务进入 `RunningExternal`，Desktop Stop/Restart/退出不得结束其进程。
- UI 主操作文本、阶段、计时、取消和重试可用性。

### 9.3 Windows 集成测试

- 真实安装 TestHarness 进程树在取消、超时和宿主退出后全部回收。
- staging 安装成功后原子激活，二次启动不再创建安装进程。
- 安装失败不破坏既有活动安装，不删除根目录或其他事务。
- DSH 启动超时仍为 `DSH-E203` 并回收 Owned 树。
- 安装停滞为 `DSH-E221` 并回收安装树。
- 默认健康探测在设置系统代理的测试环境中仍直接访问 loopback；外部重定向继续拒绝。
- 已确认外部 DSH 不触发安装，关闭 Desktop 不停止外部进程。

### 9.4 真实空缓存和新设备验证

真实验证不得读取或污染开发者现有 npm cache，必须使用唯一临时 cache 和私有安装根，并在 `finally` 中清理测试创建的进程与目录。至少覆盖：

1. 对手工全局安装成功机器做只读取证：记录 Windows、Node/npm、配置 registry、安装大致耗时、安装前 cache/全局 DSH 状态、`dsh` 路径与版本，并从全局 DSH 根递归提取仅含 package name/version 的排序摘要和哈希；不得收集 `.npmrc` 正文、Token、完整环境变量或用户文件。
2. 将全局成功图、成功既有 `_npx` 图与失败空缓存 npx 图做三方比较，单独列出 rc.6/rc.7 分布、缺失/新增包、顶层 manifest、是否存在 `npm-shrinkwrap.json` 及实际启动结果。
3. 从完全空 cache 按发布内 lockfile 安装，分别覆盖官方 registry 与受控镜像，记录 Node/npm 版本、配置 registry、实际请求 host、总耗时、下载量、落盘量和最终依赖摘要。
4. 启动真实 `dsh web`，验证 HTTP 200、HTML 类型、标题和 `window.__DSH_BOOT__`。
5. 关闭宿主后确认 Owned DSH 和子进程退出、端口释放。
6. 第二次启动使用已激活私有安装，确认没有 npm/npx 进程、没有 registry 请求、没有下载。
7. Windows 10 x64 与 Windows 11 x64 各至少一台干净用户环境完成相同步骤。
8. 至少覆盖 Node LTS 和当前受支持的较新 Node/npm 组合；不受支持的版本必须在安装前给出明确提示。
9. 代理启用和代理不可用场景分别验证：npm 网络错误准确，loopback 健康请求不走代理。

## 10. 验收标准

- `AC-E203-001`：已有全局 DSH、私有安装或合格 `_npx` 缓存时，启动过程不创建 npm/npx 进程且不访问 registry。
- `AC-E203-002`：全新环境只在用户确认后执行一次锁定安装；安装成功后的第二次及后续启动不重复下载。
- `AC-E203-003`：空缓存安装使用完整精确 lockfile，实际安装图与审核摘要一致，不因 registry 出现新版本而漂移。
- `AC-E203-004`：安装准备超时或无进展返回 `DSH-E221`，不得返回 `DSH-E203`。
- `AC-E203-005`：只有 DSH 服务进程已创建但身份未在期限内确认时返回 `DSH-E203`。
- `AC-E203-006`：loopback 健康探测显式旁路系统代理，仍拒绝外部重定向和未知身份服务。
- `AC-E203-007`：取消、失败、应用退出均只回收当前 Desktop 创建的安装/DSH 进程树，不影响外部实例。
- `AC-E203-008`：Release ZIP 不包含 Node、npm、npx、`node_modules`、DSH cache、用户配置或日志，并满足现有 ZIP/EXE 体积门禁。
- `AC-E203-009`：Windows 10/11 干净用户真实首次安装、HTTP 身份、二次免下载和端口释放全部通过并形成新验证记录。
- `AC-E203-010`：Unit、Integration、Debug/Release 和完整发布门禁通过，0 warnings、0 errors。
- `AC-E203-011`：`AGENTS.md` 与 `CLAUDE.md` 完全一致；实现阶段版本三处一致，安装、开发和详细设计文档与实际行为一致。
- `AC-E203-012`：安装引导保留固定全局安装与旧版手动 npx 启动入口；Desktop 只复制命令和打开终端，不自动执行。全局安装后重新检查可直接复用，手动启动服务按 `RunningExternal` 处理。

## 11. 发布与文档

实现完成时必须：

## 12. 完成定义

只有同时满足以下条件才能宣称修复完成：

- 已用自动测试复现旧行为，并证明新实现准确区分安装与服务超时。
- 已从真正空缓存完成锁定安装和真实 DSH HTTP 身份 smoke。
- 已证明已有安装启动不下载，且第二次启动不下载。
- 已证明 loopback 健康检查不走系统代理。
- 已证明固定手动安装/启动入口存在、可用且不自动执行命令；全局安装和手动外部服务分别遵守 Owned/External 语义。
- 安装与 DSH 进程树在成功、失败、取消和退出路径均无残留。
- 发布包保持轻量且不包含运行时依赖目录。
- Windows 10/11 新设备验收记录齐全，不以开发机已有缓存替代。
- 所有相关代码、测试、文档、版本和仓库规则一致。
