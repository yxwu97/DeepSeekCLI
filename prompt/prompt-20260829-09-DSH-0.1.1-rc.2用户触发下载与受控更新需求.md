# DeepSeek Harness Desktop DSH 0.1.1-rc.2 与后续版本无代码适配需求 Prompt

## 1. 文档信息

- 文档类型：后续设计、开发与验收执行 Prompt
- 适用项目：DeepSeek Harness Desktop
- 编写日期：2026-08-29
- 需求状态：待实现
- 当前 Desktop 基线：`0.10.3`
- 当前验证 DSH：`@deepseek-ai/dsh@0.1.0-rc.7`
- 首个目录验证 DSH：`@deepseek-ai/dsh@0.1.1-rc.2`
- 建议 Desktop 目标版本：`0.11.0`（新增用户可见下载与更新能力，按 minor 升版）
- 关联计划：`plan/plan-20260829-09-DSH-0.1.1-rc.2用户触发下载与受控更新开发计划.md`

本文只形成需求方案，不修改应用代码、lockfile、发布资源或版本记录。实际实施时按仓库版本政策统一升版一次。

## 2. 执行指令

将本文作为后续实现的完整输入。开始前必须读取届时的 `AGENTS.md`、`CLAUDE.md`、`code_rule.md`、当前代码、测试、发布脚本、安装说明和最新验证记录，以实际实现为准，不得机械替换版本字符串。

实现目标是让用户在应用内明确点击“下载并更新”，先把 DSH 更新到签名目录验证的精确版本 `0.1.1-rc.2`，并让后续符合既有运行协议的 DSH 版本无需修改或重新发布 Desktop 代码即可采用。这里的“手动”表示由用户主动触发并确认，不表示让用户输入任意包名、版本、registry 或 Shell 命令，也不表示后台无条件跟随 npm `latest`。

## 3. 结论

采用“已验证版本 + 用户触发 + 受控私有安装”方案：

1. Desktop 发布时内置精确锁定 `0.1.1-rc.2` 完整依赖图的 `package.json` 和 lockfile。
2. 用户点击“下载并更新”并确认后，Desktop 才在私有 staging 中执行唯一允许的 `npm ci --omit=dev`。
3. 下载完成后校验 lock hash、包名、版本、bin 映射、固定入口和目录边界，再用独立 loopback 端口做真实 DSH 身份 smoke。
4. 全部通过后原子切换私有 active 指针；失败或取消保留旧安装和原活动状态。
5. 更新完成后重新发现候选并启动精确 rc.2。旧全局 rc.7 不得遮挡新私有 rc.2。
6. npm `latest` 继续只用于发现。可安装目标必须来自内置 Bootstrap 描述符或有效签名目录；latest 更高但目录尚未批准时显示“等待验证”。

rc.2 同时作为无代码适配能力的 Bootstrap 样本。`0.11.0` 一次性内置固定更新源、公钥和受限目录协议；后续版本由独立验证流水线生成精确 package/lock 资源、完成真实 smoke 并发布签名目录条目。Desktop 获取并验签目录后显示“可更新版本”，用户确认才下载和激活，因此后续 DSH 升级不要求修改 Desktop 源码、常量或 AppVersion。

npm `latest` 只是发现线索，不是授权。即使 npm 出现新版本，签名目录尚无兼容条目时也只能显示“等待验证”。本方案不允许把 `npm install -g @deepseek-ai/dsh@latest`、动态 `npx` 或客户机运行时生成 lockfile 接入生产更新路径。上游发布频繁不降低供应链和回归门禁。

## 4. 当前版本立即可用的人工路径

当前 Desktop 仍精确验证 rc.7，不能把手工安装的 rc.2 当作 Auto Owned 候选。需要立即试用 rc.2 时，仅支持外部人工验证：

1. 从托盘退出 Desktop，确保 Owned DSH 已停止。
2. 在可见 PowerShell 中执行：

   ```powershell
   npm install -g @deepseek-ai/dsh@0.1.1-rc.2
   dsh --version
   dsh web
   ```

3. 确认版本输出精确为 `0.1.1-rc.2`，并确认服务只监听预期 loopback 地址。
4. 重新打开当前 Desktop；服务通过 HTTP/HTML DSH 身份校验后，只能按 `RunningExternal` 连接。Desktop 不拥有、停止或重启该手工进程。

也可以用 `npx @deepseek-ai/dsh@0.1.1-rc.2 web` 做一次性外部验证，但仍不属于 Auto Owned 启动。

`npm pack @deepseek-ai/dsh@0.1.1-rc.2` 只下载顶层 tarball，不包含完整传递依赖图，不能直接替换 `eng/dsh-runtime` lockfile，也不能作为 Desktop 私有安装完成的证据。

## 5. 背景与问题

- 当前唯一验证版本为 rc.7；全局、私有和 `_npx` 缓存候选均要求精确匹配。
- 当前发布包内 lockfile 固定了完整 rc.7 DSH 依赖图，私有安装通过 lock digest 和真实入口校验后才激活。
- 历史验证已经证明：只固定顶层 DSH 版本时，范围型 DSH 子包可能漂移到其他预发布版本，甚至形成不可运行的混合依赖图。
- 关于窗口已经能查询 npm latest，但查询结果没有也不应获得安装权限。
- 现有首次私有安装只有在没有可复用候选时进入。用户已有 rc.7 候选时，缺少一个明确的“下载新验证版本并切换”入口。
- 全局安装修改用户环境，且可能受 PATH、权限和多个 Node 前缀影响；Desktop 的正式更新优先使用应用私有目录，不自动修改全局 npm。

## 6. 目标

1. 将 Auto 的 Bootstrap 选择版本升级为精确 `@deepseek-ai/dsh@0.1.1-rc.2`，后续允许切换到签名目录批准的兼容版本。
2. 在关于窗口或安装引导提供明确的“下载并更新”命令，仅由用户主动触发。
3. 即使已有旧全局、私有或缓存 DSH，也允许用户准备新的 rc.2 私有安装。
4. 下载、验证、smoke、激活和重新发现形成一个可取消、可重试、不可并发的事务。
5. 下载失败、取消、进程启动失败或身份验证失败时，旧安装、活动指针和正在运行的 DSH 均不被破坏。
6. 更新完成后，Auto 只启动实际版本精确等于“当前选择版本”的全局、私有或缓存候选。
7. npm latest 高于当前选择版本时先提示；只有形成可信 lockfile、验证记录和签名目录条目后才允许用户采用。
8. 保持进程所有权、Job Object、loopback/同源、命令转义、日志脱敏和轻量发布边界。
9. 建立固定来源、固定公钥、可回放防护的签名 DSH 更新目录，使后续兼容版本不需要 Desktop 代码发布。
10. 自动监测 npm latest 与签名目录；只把目录中高于当前选择版本且兼容当前 Desktop 协议的条目列为可更新。
11. 用户检查更新不会改变当前选择版本；只有下载、验证、smoke 和原子提交全部完成后才切换目标版本。
12. DSH 若改变 CLI、入口、身份标记、Node 要求或其他宿主协议，目录以 `minimumDesktopVersion`/`runtimeProtocol` 拒绝无代码适配并要求先升级 Desktop。

## 7. 非目标

- 不后台自动下载，不静默更新，不在应用启动时强制升级。
- 不实现“始终跟随 latest”、版本范围、任意版本输入框或 prerelease 通道选择器。
- 不运行 `npm install -g`、`npm update`、动态 `npx`、`npm pack` 或 registry 返回的命令。
- 不在客户机上动态生成、修补或信任新的生产 lockfile。
- 不把未经签名目录批准的 npm latest 作为生产更新候选。
- 不承诺任意未来 DSH 都能无代码适配；破坏现有宿主协议的版本必须升级 Desktop。
- 不接受用户配置的包名、registry、tarball、入口、cache id 或额外 npm/Shell 参数。
- 不自动删除全局 DSH、npm cache、旧私有版本或用户数据。
- 不结束或接管 `RunningExternal` DSH。
- 不把 Node、npm、npx、`node_modules` 或 DSH tarball打进发布 ZIP。

## 8. 用户体验

### 8.1 版本展示

关于窗口继续分开显示：

- 当前实际使用版本及来源；
- 当前选择版本，初始为 `0.1.1-rc.2`；
- npm 当前 latest；
- 签名目录当前批准的最高兼容版本；
- 当前选择版本是否已下载并通过验证。

不得把“npm latest”写成“将要启动的版本”。latest 高于当前选择版本但尚无签名条目时显示“上游有尚未验证版本，当前继续使用已选择版本”。

服务职责保持分离：`DshReleaseService` 只读取 npm latest 元数据；新的 catalog 服务只负责固定源下载、验签、解析和兼容性判断；更新检查协调服务合并两者为一个不可变 UI 结果。`AboutViewModel` 不自行拼接两个异步结果，也不让任一服务直接改变当前选择版本。

### 8.2 下载并更新

当以下条件同时成立时启用“下载并更新”：

- WebView2 不影响下载按钮，但 Node.js 和 npm 均可用；
- 没有其他准备/启动/停止/重启/退出操作正在执行；
- 目标来自内置 Bootstrap 描述符或签名验证成功的目录条目；
- 目标 package/lock 资源长度和 SHA-256 与签名条目一致；
- 当前没有该目标版本的已验证私有安装，或用户明确选择重新准备已损坏版本；
- 目标高于当前选择版本且兼容当前 `runtimeProtocol`，或者用户正在修复同一选择版本。

点击后展示确认信息：精确版本、来源为 npm registry、目标为 `%LOCALAPPDATA%` 私有目录、预计磁盘占用、最长等待、可取消，以及不会修改全局 npm。用户确认后才开始网络访问。

### 8.3 完成与失败

- 下载阶段显示有限进度文本，不把原始 npm 输出直接进入 UI。
- 安装完成后显示“已准备 rc.2”，重新诊断并根据候选优先级决定是否立即启动。
- 若当前是 Owned rc.7，先通过现有生命周期协调器正常停止，确认端点释放后再启动 rc.2；不得绕过状态机。
- 若当前是 External DSH，不停止外部进程。端口被占用时保留已下载 rc.2，并提示用户退出外部服务后再启动。
- 失败、取消或超时时显示稳定错误码和脱敏原因；不切换 active，不删除旧版本。

## 9. 下载与供应链约束

### 9.1 可信资源

- Bootstrap 的 `DshPackageMetadata`、`eng/dsh-runtime/package.json` 和 lockfile 根依赖必须一致为 rc.2；运行时目标版本来自已提交的受信版本描述符，不再依赖每版修改编译期常量。
- lockfile 必须为 v3，所有 `node_modules/@deepseek-ai/dsh*` 已解析条目必须使用同一经审计的 rc.2 发布族；若上游真实依赖图合法包含不同版本，必须先形成显式例外清单、依据和发布门禁，不能直接放宽为任意版本。
- 每个 registry 资源继续依赖 lockfile 中的 `resolved` 和 `integrity`，只允许阶段 0 验证后的官方 host。
- 发布门禁比较源码与发布包内 package/lock SHA-256，并执行真实空 cache 安装。

### 9.2 签名更新目录

- 更新源固定为项目控制的 HTTPS 位置，host、路径前缀和资产命名不进入用户配置；阶段 0 可冻结为固定 GitHub Releases 资产。
- Desktop 内置 RSA-3072/SHA-256 验签公钥和单调协议号。生产私钥只存在于离线或受控签名环境，不进入仓库、应用、日志、测试快照或发布包。
- 对目录最终 UTF-8 无 BOM 原始字节做 detached signature。先验签，再用受限 JSON reader 解析；限制总字节、深度、字段长度、条目数和整数范围，拒绝重复/未知关键字段。
- 目录至少包含 `schemaVersion`、单调递增的 `catalogSequence`、`generatedAt`、`signingKeyId` 和版本条目。每个条目至少包含精确包名/版本、发布时间、`runtimeProtocol`、`minimumDesktopVersion`、Node 版本范围、package/lock 资产 URL、长度与 SHA-256。
- 目录不能提供命令、工作目录、入口路径、registry、环境变量或任意 Shell 文本；固定入口和 npm 命令仍由 Desktop 代码定义。
- 资产下载只允许目录固定来源的 HTTPS host，每跳重新校验 scheme、host、UserInfo、重定向次数、长度和 hash。资源写入 LocalAppData 唯一 staging，验证前不进入私有 Store。
- 本地原子保存最近成功验签的 `catalogSequence`；拒绝较小 sequence、签名无效、未知 key、未来 schema、重复版本、降级版本和不兼容 Desktop 协议。离线时可显示已缓存目录，但仍需重新验证签名和资产 hash。
- 公钥轮换、目录 schema 或运行协议升级需要新的 Desktop 发布；普通 DSH package/lock 条目发布不需要。

### 9.3 目录发布流水线

- 独立流水线监测 npm latest，但发现新版本只创建候选，不自动签名发布。
- 候选在隔离环境生成精确 lockfile，检查完整 DSH 图、registry host、integrity、install scripts、license、Node 范围和入口。
- 使用空 cache `npm ci --omit=dev`，再执行固定入口 `--version`、真实 loopback Web 身份、停止回收和第二次零 npm 复用。
- 自动化全部通过后由维护者审核并签名目录条目；发布 package/lock 资产、目录和签名。用户端随后无需更新 Desktop 即可发现。
- 目录撤销通过发布更高 `catalogSequence` 标记版本 `revoked`。已安装且被撤销版本不被静默删除或停止，但 UI 阻止新安装并给出升级提示；紧急强制处置需单独安全设计。
- 对每个候选执行启用/禁用 npm lifecycle scripts 的对照安装与真实 smoke。若 `--ignore-scripts` 可运行，目录协议 v1 固定禁用 scripts；若必须执行 scripts，实施前必须形成威胁模型，并在签名条目中固定允许执行脚本的 package path、version、integrity 集合，客户端发现集合漂移时拒绝安装。不得仅因 npm 退出成功就默认允许所有未来脚本。

### 9.4 受控执行

- 仅通过 `NpmCommandLineBuilder` 构造 `npm ci --omit=dev`，工作目录由 `ProcessStartInfo.WorkingDirectory` 传递。
- staging 必须位于应用私有根的受控同卷目录，拒绝 reparse point、越界路径和已存在的非受控目录。
- npm 子进程加入本次操作的 Job Object；取消、超时、宿主退出时回收其进程树。
- npm 子进程必须使用专用环境策略：`NPM_CONFIG_USERCONFIG` 与 `NPM_CONFIG_GLOBALCONFIG` 指向受控空文件，staging 拒绝项目 `.npmrc`，registry/cache/offline/prefer-offline/audit/fund/replace-registry-host 和最终 scripts 策略均显式固定。不得只传空 overrides 后继承用户配置。
- 明确代理兼容策略：允许系统 HTTPS 代理时仍保持 TLS、固定 registry host、lock integrity 和日志脱敏；若禁用代理则提供可操作错误。清除或覆盖可能携带凭据、改变脚本解释器或改写 npm 行为的 `NPM_CONFIG_*`、`NODE_AUTH_TOKEN`、`NPM_TOKEN` 等子进程变量，不记录原值。
- stdout/stderr 先规范化、限长、分类和脱敏，再进入 UI 或日志。

### 9.5 激活与回退

- 安装后校验根包版本、manifest `name/version/bin`、固定 `lib/bin.js`、lock hash、祖先路径和 reparse 状态。
- 用 PATH 中受控 `node.exe` 直接执行固定入口的 `--version` 和 `web --port <数字>`，验证版本与 HTTP/HTML 双身份。
- smoke 成功后才写完成标记并原子切换 `active.json`；提交前失败保留旧 active。
- rc.7 和更旧目录默认保留，不在本需求中新增自动清理。
- 更新成功后的候选重新发现必须精确选择 rc.2，不能复用更新前的过期 discovery 结果。

## 10. 候选优先级

更新后的 Auto 使用“当前选择版本”而不是 npm latest。初次为内置 rc.2；用户完成一次签名目录更新后，选择版本与该条目的原始签名/hash 证据一起原子保存。仅检查目录不会改变选择版本。

候选顺序保持：

1. PATH 全局 `dsh.cmd`，但 `--version` 必须精确等于当前选择版本，且该版本来自内置或有效签名描述符；
2. 已激活且完整校验通过的 Desktop 私有选择版本；
3. 标准 `_npx` 根直接子目录中严格校验的选择版本；
4. 没有候选时进入用户确认后的私有下载。

为了让旧全局 rc.7 不阻止私有更新，诊断必须把“不匹配全局候选”与“可准备私有 rc.2”同时返回。下载完成后旧全局仍被拒绝，私有 rc.2 成为有效候选。

## 11. 状态、并发与所有权

- 下载/更新使用独立单操作门和 `CancellationTokenSource`，并与 Harness 启停操作通过协调器建立明确互斥顺序。
- 不能在 UI 线程使用 `.Wait()`、`.Result` 或同步 npm I/O；后台状态回调必须切回 Dispatcher。
- 必测检查 latest、用户点击下载、取消、应用退出、Owned 立即退出、smoke 完成和 active 提交之间的竞态。
- generation 校验必须阻止旧下载/诊断结果覆盖新状态。
- Desktop 仅停止自己创建并跟踪的 Owned DSH。下载事务不得按端口或进程名结束外部进程。
- 所有事件订阅、CTS、SemaphoreSlim、Process、Job Object 和临时目录句柄成对释放。

## 12. 错误语义

优先复用现有 `DSH-E211` 至 `DSH-E214`、`DSH-E221` 和身份错误。若新增错误码，建议：

- `DSH-E223`：内置或目录下载的 DSH 更新资源与受信描述符不一致；禁止下载或继续安装。
- `DSH-E224`：已下载 DSH 的版本、lock、manifest 或入口验证失败；禁止激活。
- `DSH-E225`：新 DSH smoke 未通过；保留旧活动安装。
- `DSH-E226`：DSH 更新目录签名、sequence、schema 或来源无效；忽略远程目录。
- `DSH-E227`：目录中的 DSH 需要更高 Desktop/运行协议；要求先更新 Desktop。

不得复用这些错误码表示 Desktop 自身更新，也不得改变已有错误码含义。

## 13. 验收标准

- `AC-DSH-UPD-001`：代码常量、package、lock 根依赖、完整 DSH 锁图、UI 和发布门禁统一为 rc.2。
- `AC-DSH-UPD-002`：用户明确点击并确认后才访问 registry；没有静默或后台下载。
- `AC-DSH-UPD-003`：已有 rc.7 全局/私有/缓存时仍能准备 rc.2 私有安装，旧版本不被执行或删除。
- `AC-DSH-UPD-004`：空 cache `npm ci --omit=dev`、`--version`、真实 Web 身份 smoke、停止回收和第二次零 npm 复用通过。

## 15. 文档与版本

实际实现时：

1. `AppVersion` 从届时版本升一个 minor，当前基线建议 `0.11.0`。
2. `app.manifest` 同步为 `<AppVersion>.0`。
3. `VERSION_HISTORY.md` 顶部新增当天记录。
4. 同步 `README.md`、`docs/installation.md`、开发文档、详细设计和新的阶段验证记录。
5. 将 `AGENTS.md` 与 `CLAUDE.md` 中唯一验证 DSH 更新为 rc.2，并逐字节比较一致。
6. 不批量改写历史验证记录中的 rc.6/rc.7；过时设计段落应标明历史上下文或由当前事实章节取代。

`0.11.0` 实现目录协议时按 minor 升版。以后只发布兼容 DSH 的签名目录/lock 资产不修改应用文件，因此不递增 Desktop AppVersion；目录自身使用独立 `catalogSequence` 和 DSH SemVer 留痕。若更新公钥、schema、CLI/身份协议或应用行为，仍必须修改代码并按正常版本政策发布 Desktop。

本 prompt 与配套 plan 是内部执行方案，本次只新增方案文档，不改变应用行为，因而不单独递增应用版本。

## 16. 完成定义

只有以下条件全部满足，才能宣称 Desktop 支持“手动下载 rc.2 并对后续兼容 DSH 做无代码适配”：

1. rc.2 完整锁图经独立审查、空 cache 安装和真实 Web smoke。
2. 用户主动触发且确认后才下载；取消和失败可恢复。
3. 安装只进入 Desktop 私有目录，旧版本和全局环境不被自动修改。
4. 原子激活后重新发现并启动精确的当前选择版本，所有其他 Auto 版本被拒绝。
5. latest 仍是只读信息，未来版本不能绕过验证与 lockfile。
6. 自动化、Windows 人工验收、文档、版本和完整发布门禁均有证据。
7. Bootstrap 后已用另一个目录版本证明无需重编译 Desktop 的发现、手动确认、下载、验证、原子切换和回退闭环。
